# Orchestration audience and authority

## 0. Product

An organization member may see and gather only orchestrations owned by that organization and an agent assigned to the member. Tenant input may not choose a server filesystem path. Gateway-global orchestration progress remains available only to an authenticated operator connection with the explicit `operator.admin` scope until the event producer carries a trustworthy server-owned audience.

This slice completes the open orchestration part of GW-005 and records the source-confirmed manifest/API/path bypass as GW-025 (P1). GW-025 is distinct because it affects list, detail, gather, cleanup, and create even if the live event is disabled. The two findings share one authority boundary and therefore ship and qualify together.

**Out of scope:** tenant access to `pi-agent.subagents.list/kill/steer`; changing the orchestration task scheduler or provider semantics; making live orchestration progress tenant-visible; redesigning the Hub agent page; a non-Linux implementation of the descriptor-relative filesystem primitive; merge, deployment, or production migration.

## AS-IS

### GW-005: the progress bridge has no audience

`src/agents/subagents/orchestration/orchestration-events.ts` defines `OrchestrationEvent` as `type`, `orchestrationId`, `timestamp`, and unconstrained `data`. It has no organization, user, agent, session, or server-owned audience. `startGatewayServer` installs a singleton bridge that calls `broadcast("pi-agent.orchestration-progress", payload)` without a scope guard. A forged `orgId` or `agentId` inside `data` is ordinary untrusted payload.

No production source currently calls `orchestrationEvents.emit`; only tests invoke it. The live bridge and advertised event name are nevertheless installed. A future emitter would immediately reach every authenticated tenant connection unless the recipient boundary is fixed. The bus also writes the full event into the structured event store; GW-005 already makes that store and its live `events.new` feed platform-admin-only.

The only external runtime consumer found is Hub `src/lib/services/gateway.svelte.ts`, which shows start/completion toasts and dispatches a browser `CustomEvent` containing the payload. No request waits for the progress event. Site and Paperclip have no runtime consumer. Gateway CLI list/get use RPCs instead of this event.

### GW-025: a shared workspace is treated as tenant authority

`src/gateway/server-methods/orchestrations.ts` scans every manifest under the selected agent workspace for `pi-agent.orchestrations.list` and joins a caller-provided `orchestrationId` into a path for `get`. Both methods are tenant read-scoped. `src/gateway/server-methods/pi-agent.ts` exposes `pi-agent.orchestrate` to tenant write scope and runs it from the shared `agent:<agentId>:main` session. None of these paths has an organization owner.

The dispatcher checks an agent assignment only when the request already contains `agentId`. The handlers choose the default agent after authorization when the field is absent. Even with an explicit assigned agent, two organizations may share canonical agent `main`, so assignment cannot separate their manifests.

Hub legitimately calls list and get for its selected assigned agent from `pi-agent-state.svelte.ts` and `PiAgentOrchestrations.svelte`. Hub does not call `pi-agent.orchestrate`. It silently treats an isolated orchestration-list failure as an empty list, and detail failure as an empty expanded panel. Site and Paperclip have no callers. The CLI uses list/get through an admin connection and also has local inspect/cleanup commands.

The in-agent `subagents` tool is another production entry point. Its `orchestrate` action accepts a model-supplied optional `orchestrationId`; `gather` joins a supplied ID into the workspace path, reads files named by mutable manifest state, and may recursively delete that directory; `orchestrations` scans the whole agent workspace. A tenant-owned agent session can therefore collide with, read, or delete another tenant's orchestration when both use the same agent workspace.

`createOrchestrationDir` uses `path.join(agentWorkspace, "orchestrations", orchestrationId)` and recursive `mkdir` without validating a single path segment or containment. Direct get, gather, aggregation, crash recovery, and local inspect similarly trust joined paths. A mutable manifest's absolute `task.outputDir` can point outside the orchestration root. Fixed `manifest.json` and `status.json` reads can follow symlinks. Manifest/status/README writers use joined paths and in-place `writeFileSync`; parallel task completions can each read an old manifest and overwrite the other's fields, while an ancestor or file swap can redirect or truncate the write. These filesystem-selector defects are part of GW-025 because the same untrusted ID/manifest crosses the new authority boundary.

Manifests cannot become the ownership source: they live in an agent-writable workspace, have no organization field, and can be edited independently of the Gateway. Existing manifests also predate organization ownership, so inferring ownership from directory, agent assignment, current JWT, or first reader would let one tenant claim another tenant's history.

## TO-BE

### 1. Principal and compatibility policy

1. A **tenant principal** is a validated JWT connection with a non-empty `orgId`, no `operator.admin`, and an explicit assigned `agentId`. Tenant list/get are preserved through scoped authority records. Tenant `pi-agent.orchestrate` is denied before task parsing or filesystem access because its current parent session is the organization-ambiguous `agent:<agentId>:main`; no current Hub/Site/Paperclip caller depends on this RPC. Tenant orchestration creation remains available through the in-agent tool after the requester's session has authoritative GW-002 ownership.
2. A **platform principal** is an authenticated operator connection with explicit `operator.admin`. This includes a correctly admitted token, admin service account, persisted admin device-token connection, or legacy shared-token operator with that scope. It preserves global RPC list/get/orchestrate and recovery access.
3. Role `node`, a non-admin device-token/operator, and a non-admin service account do not receive the global event and do not gain platform manifest access. Authentication mechanism alone grants nothing; role plus explicit scope decides platform authority.
4. Tenant requests must include a non-empty canonical `agentId`. Missing `agentId` is `INVALID_REQUEST`; it never selects the default after authorization. The agent must be present in `assignedAgentIds`, including for an organization administrator. Platform callers retain the existing optional/default-agent behavior.

### 2. Gateway-owned orchestration authority

1. Add a Gateway-owned authority database under `stateDir`, outside all agent workspaces, mode `0600`. Use the existing `better-sqlite3` dependency with a versioned schema, `journal_mode=WAL`, `synchronous=FULL`, a 5-second busy timeout, and transactions that acquire the write lock before checking/inserting. Opening a foreign schema, failed `quick_check`, unreadable database, failed commit, or failed durable WAL sync makes tenant orchestration authority `UNAVAILABLE`; code must not replace, truncate, or silently recreate the evidence.
2. The immutable key is `(canonical agentId, orchestrationId)`. A row records authority class (`tenant` or `platform`), tenant `orgId` when applicable, source (`tenant-session`, `platform-rpc`, `platform-session`, or `operator-migration`), canonical requester session key when applicable, one random immutable run generation, creation time, and admission state (`reserved`, `materialized`, `interrupted`, `cleanup-prepared`, `cleanup-quarantined`, or `tombstoned`). Owner class, organization, agent, source, run generation, and creation time never change. State transitions compare the expected prior state and cleanup generation in one transaction.
3. New IDs are generated by the Gateway as lowercase RFC 4122 UUID v4 values. Callers and models cannot choose a new ID. The database reservation commits before orchestration directory creation, manifest writes, child-session creation, provider invocation, progress publication, or aggregation. Manifest creation completes before the row may transition to `materialized`; child/provider work starts only after that transition commits. Failure to reserve has zero workspace or provider effects. Failure after reservation remains an explicit recoverable row and never permits ID reuse.
4. On startup, bounded reconciliation compares authority rows with safe workspace entries. A reserved row with no manifest becomes `interrupted`; a materialized row with a missing, malformed, mismatched, or unsafe manifest is unavailable and observable to its owner and platform recovery tooling. A pending file publication follows section 5.5 and a cleanup row follows section 5.8. Reconciliation never assigns an owner and never deletes an authority key. Existing crash recovery may mark a running manifest interrupted only after the safe path and authority record agree.
5. One Gateway process owns the live database handle. Local import uses SQLite locking against that same database; concurrent attempts converge by primary key and immutable-owner checks. A reconciliation/request scans at most 10,000 workspace entries and a list returns at most 1,000 matching rows with a truthful `truncated` flag. Overflow is observable and never represented as a complete list.
6. Capacity is an admission invariant, not cleanup advice. In the same `BEGIN IMMEDIATE` transaction that checks the immutable key, reservation/import takes and updates persisted counters and enforces all of: at most 5,000 live rows globally, 1,000 live rows per tenant organization or the single platform bucket, 256 live rows per `(owner bucket, agentId)`, 50,000 retained keys globally, 10,000 retained keys per owner bucket, 64 MiB of deterministic logical authority bytes globally, and 16 MiB per owner bucket. `reserved`, `materialized`, `interrupted`, `cleanup-prepared`, and `cleanup-quarantined` are live; every state, including `tombstoned`, is retained. Logical bytes are the UTF-8 lengths of every stored variable field plus the schema-versioned fixed row charge; the formula and maximum row charge are shared by admission, every state/pending-publication update, import, reconciliation, and a startup full recount. An insert or update reserves its worst-case new charge before effects. Counter mismatch, overflow, an actual database-plus-WAL footprint above 128 MiB, or inability to checkpoint within five seconds makes admission `UNAVAILABLE`; saturation returns the stable `orchestration_capacity_exceeded` result before an ID, directory, child session, provider call, publication, or event is exposed. No process-local counter or delete-on-full fallback exists.
7. Terminal compaction is transactional and lossless for authority. It may replace bulky cleanup/provenance fields with a schema-versioned minimal retained record, but it always keeps the exact `(agentId, orchestrationId)`, owner class/organization, source digest, creation time, terminal state, and cleanup receipt. The compact record remains included in retained-row/byte counters and the uniqueness check, so export, `VACUUM`, age, or operator cleanup never makes an ID reusable. There is no automatic purge. Reaching the retained cap blocks new reservations until a separately reviewed capacity migration expands or moves the complete exact-key index; copying an archive and deleting its local keys is not accepted as reclamation.
8. The database schema uses checks/triggers so a direct internal SQL insert cannot bypass counter accounting. Startup recomputes global and owner counters from rows, compares them with persisted counters, validates every field bound, and refuses tenant authority on mismatch. Real two-process tests race the last global, owner, agent, row, and logical-byte slots; exactly the admitted transaction may proceed, and restart retains the same decision.

### 3. Tenant list, detail, gather, and create

1. Tenant `pi-agent.orchestrations.list` first resolves explicit assigned agent and authenticated organization, queries only matching tenant authority rows, then reads only their safe manifests. It does not scan and filter foreign manifests into memory. Existing status/since/until/template filters run after ownership selection.
2. A tenant list checks the bounded directory index for unbound legacy entries. Any safe or unsafe workspace entry with no authority row makes the result explicitly `UNAVAILABLE: orchestration ownership migration required`; it does not return an empty or apparently complete subset. Rows bound to another organization are ignored without revealing count, ID, status, or existence. An own row whose manifest is absent or invalid produces an explicit unavailable/recovery state rather than disappearing.
3. Tenant `get` requires explicit assigned agent plus an exact authority match on authenticated `orgId`. Missing and foreign IDs return the same content-free denial. Authority is checked before any path is built or manifest is read. The manifest's embedded ID must equal the requested canonical ID; mismatch is unavailable and no manifest fields are returned.
4. The in-agent tool classifies each call from `requesterSessionKey` through a strict GW-002 ownership resolver that distinguishes a healthy store with no tenant owner from an unhealthy/ambiguous store. A known session audience produces tenant authority `{orgId, agentId}`; orchestrate reserves that owner before effects, and orchestrations/gather use the same owner filter. A healthy, provably unowned legacy/local session produces a platform-class record and retains current local automation because GW-002 prevents tenant admission to an unowned session. If ownership inspection is corrupt, unreadable, or ambiguous, every internal orchestration create/list/gather operation fails closed; absence is never inferred from an error. This dependency receives an end-to-end regression.
5. Tenant `pi-agent.orchestrate` returns `FORBIDDEN: tenant orchestration requires an owned agent session` before parsing tasks, resolving a workspace, or spawning. Platform callers retain the RPC, but their new runs receive a platform authority row before effects. Dry runs create no row or files and return an ephemeral server-generated ID that cannot be used for get/gather.
6. In-agent `gather` authorizes before reading or aggregation and rejects every `cleanup: true` request, including calls from tenant-owned and unowned local/platform agent sessions. Only the explicit local operator cleanup command may enter the durable cleanup state machine in section 5.8. Failed or interrupted cleanup stays visible to platform recovery and never makes the ID reusable. Platform/local sessions may inspect platform and legacy records; tenant sessions never receive platform or foreign records.

### 4. Legacy qualification and recovery

1. Existing directories remain byte-compatible and platform-admin/local CLI readable after path validation. They are not tenant-readable until explicitly qualified. Unknown legacy ownership is not inferred from the current reader, current agent assignment, timestamps, manifest text, or workspace location.
2. Add a local operator command that imports a versioned migration manifest into the authority database. Each entry supplies exact safe `agentId`, exact safe `orchestrationId`, `orgId` or explicit `platform`, and 1-256 bytes of provenance. Linux packages install the fixed inbox `/etc/minion/orchestration-authority-imports`, owned by root and the exact Gateway service group, mode `0750`; every path component from `/` through the inbox is root-owned and not group/world writable. A container uses an equivalent root-owned read-only secret volume and proves the same owner/mode/mount identity at startup. An entry is a root-owned, single-link regular file, mode `0440`, no larger than 2 MiB, with a safe one-segment name. The command accepts only that name plus a required lowercase SHA-256 digest. The native resolver pins `/`, opens every inbox component descriptor-relative with no symlink or magic-link traversal, and opens the entry once with `O_RDONLY|O_NOFOLLOW`. It validates mode, owner, link count, device, inode, size, mtime, and ctime from that held descriptor, streams at most 2 MiB from the same descriptor while enforcing at most 10,000 entries and a 30-second monotonic budget, verifies the caller-supplied digest, repeats `fstat`, and confirms through the still-held inbox descriptor that the name still selects the captured device/inode before `BEGIN IMMEDIATE`. It never reopens bytes by pathname and invokes no parser/plugin callback while descriptors or database locks are held. An ancestor/name exchange, same-size replacement, metadata change, digest mismatch, invalid entry, or unsupported inbox detected before the authenticated input snapshot makes the whole import unavailable and writes zero rows. After the final identity check, only the bounded bytes and digest captured from that one held descriptor are import authority; a later path exchange cannot change them. The transaction then admits every row and its worst-case logical charge under the section 2 capacities. Duplicate identical entries are idempotent; conflicting, over-capacity, over-budget, or invalid batches write zero rows. The command prints the migration digest and imported/already-present counts without manifest content.
3. The import never changes workspace bytes and never makes an unknown entry tenant-visible on partial failure. The original manifest remains operator evidence. An explicit platform qualification preserves legacy/local behavior but does not expose the record to any tenant.
4. Admin RPC/CLI recovery can list raw legacy entries and authority health with content-free warnings. Existing shared-token and admin device-token CLI workflows remain compatible. Tenant Hub receives a stable error code for migration/corruption and renders an unavailable/retry/admin-contact state instead of replacing its previous rows with an empty list.

### 5. Filesystem selector contract (GW-025)

1. A shared resolver is the only way to create, read, gather, aggregate, inspect, recover, or delete an orchestration directory. New IDs must be canonical UUID v4. Qualified legacy IDs may be 1-128 bytes and exactly one path segment, excluding `.`, `..`, separators, NUL/control bytes, and platform alternate separators. The workspace comes only from the server-owned agent configuration. The resolver opens and pins that configured workspace without following any ancestor symlink, creates or opens its direct `orchestrations` child relative to that descriptor, and proves every orchestration target is a direct child. Creation is relative to the held root, uses exclusive single-directory creation rather than recursive `mkdir`, and validates the new inode before publishing its path; swapping the configured workspace or `orchestrations` ancestor cannot redirect a write.
2. This contract depends on the separately reviewed GW-022A package `@minion-stack/linux-fs-atomic`, extended with a versioned orchestration API for descriptor `flock`, relative exclusive `openat`/`mkdirat`, constrained `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS)`, bounded `getdents64`, `fstat`, same-parent `renameat2(RENAME_NOREPLACE|RENAME_EXCHANGE)`, `unlinkat` traversal, `fdatasync`, and file/directory `fsync`. The first accepted ABI is exact-pinned as `@minion-stack/linux-fs-atomic@0.1.0` with no range; any ABI/capability change requires a new exact version and package review. The Gateway lockfile pins the package and platform artifact integrity. CI builds and installs checksum-pinned Linux x64/arm64 glibc and musl artifacts, and tests the production package on its target kernel/filesystem. Startup performs a bounded same-filesystem capability probe before advertising tenant orchestration. Missing addon, wrong checksum, unsupported syscall/flag/filesystem, macOS, or Windows makes filesystem-backed orchestration explicitly unavailable before reservation; Node `fs`, string-path `rename`, shell commands, `realpath`, or check-then-open are not fallbacks. GW-005/GW-025 cannot be called implemented until this prerequisite is merged and the packaged Gateway artifact passes the probe.
3. Existing targets, `manifest.json`, `status.json`, task directories, and gathered files must be regular entries beneath that canonical root. Symlinked orchestration directories, manifests, status files, task directories, and files are rejected. Security-sensitive reads hold no-follow descriptors from the pinned root and verify type, device, inode, size, allocated blocks, and stable metadata before returning bytes or metadata. Manifest `outputDir`, `childSessionKey`, `runId`, labels, and embedded orchestration ID are data, never authority to another session or resource. The output directory must identify the expected direct task directory beneath the authorized orchestration; run/result correlation is restricted to runs already owned by the same authoritative requester; any mismatch is unavailable. No host-absolute path is returned to a tenant; gathered file paths are orchestration-relative.
4. Parsing and enumeration are bounded before allocation. `manifest.json` is at most 1 MiB and contains at most the existing `MAX_TASKS_PER_ORCHESTRATION` value of 20 tasks; `status.json` is at most 256 KiB, its `outputFiles` has at most 128 one-segment names of at most 128 UTF-8 bytes, and its summary, error, and encoded metrics are respectively at most 64 KiB, 64 KiB, and 64 KiB. Every other accepted manifest string is at most 4 KiB unless a smaller protocol bound applies. One task directory contains at most 128 direct regular output files; gather never recurses below that one task level. One output file is at most 32 MiB logical and allocated size, one orchestration exposes at most 2,048 output-file metadata records and 128 MiB aggregate logical output size, one file contributes at most 64 KiB inline, and one gather response contributes at most 1 MiB inline plus 512 KiB encoded metadata. The existing caller `maxInlineBytes` is clamped to 0..64 KiB and cannot raise aggregate caps. The native iterator stops at limit-plus-one without materializing the remainder. Sparse files, unsupported file types, over-limit names/counts/bytes, integer overflow, or a file/directory that changes inode/size/allocated blocks/mtime during the held-descriptor read fails the whole operation with a typed unavailable/too-large result; it never skips entries into an apparently complete response.
5. Every Gateway-owned publication of `manifest.json`, `README.md`, `status.json`, task/stage directories, and task-output files goes through the held resolver; production orchestration code may not reopen an absolute path. Spawned workers receive an opaque output capability bound to the immutable authority/run generation, child session/run, and task index; a scoped output-publication tool accepts only a validated relative one-segment filename and bounded byte stream and invokes this writer. File-generation advancement never invalidates a sibling publication capability; cleanup, child/run settlement, or authority-generation mismatch does. Gateway publishes validated worker status through the same path. The existing template/raw `outputDir` is no longer a publication authority. A worker-created file that bypasses the capability remains untrusted workspace input, cannot appear in declared `outputFiles`, advance completion, or be returned by gather. One native per-orchestration lock keyed outside the writable workspace plus one process queue serializes all publications, cleanup, and recovery. Lock acquisition is at most four seconds; admission allows at most 64 queued publications per orchestration and 512 globally, with saturation rejected before buffering bytes. Before manifest mutation, the writer rereads the latest bounded manifest through its descriptor and merges only the named task/final-status fields, so concurrent distinct-task completions cannot overwrite each other. The authority row stores a monotonic file generation and at most one bounded pending-publication record containing an immutable attempt ID, kind, mode (`initial` or `replacement`), phase (`planned`, `prepared`, or `replacement-cleanup`), relative target/temp names, expected-absent marker or captured incumbent device/inode/digest, new digest/size, captured temp device/inode after preparation, and generation. A durable CAS installs `planned` only while the row is in the expected non-cleanup state. The writer then creates an unpredictable same-parent temp with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode `0600`, writes exactly the prevalidated bounded bytes, verifies size and digest, calls `fdatasync`, and fsyncs the parent so the temp name is durable. A second CAS changes the same attempt to `prepared` and records the temp device/inode before namespace publication. A symlink, inode/digest/generation mismatch, unexpected incumbent, stale writer, or cleanup state rejects without following or truncating the incumbent.
6. Initial and replacement publication use distinct durable phases. In `planned`, exact complete temp bytes may be verified and promoted to `prepared`; a missing or incomplete temp while the expected target is still absent/old proves no namespace effect. For an initial file, `prepared` records that the target was absent and identifies the exact temp inode; `RENAME_NOREPLACE` publishes that inode, the writer fsyncs the parent, and one CAS clears pending and advances file generation. Recovery may resume from absent target plus the exact new temp. Exact new target with the captured temp inode/digest plus absent temp proves the rename and may be parent-fsynced and finalized. Absent target plus absent or incomplete temp atomically clears pending without advancing generation, moves the authority row to `interrupted` with the bounded `publication_interrupted_no_effect` code, and only then removes an exact owned incomplete temp and fsyncs the parent. Any unexpected target or second entry is conflict. For replacement, `planned` captures the complete incumbent and `prepared` additionally captures the complete new temp. Exact old target plus exact new temp may perform `RENAME_EXCHANGE`; after exchange and parent fsync, a CAS advances file generation and changes pending to `replacement-cleanup`, with the exact new inode at target and exact captured incumbent under the owned temp name. A crash after exchange but before parent fsync or that CAS therefore remains `prepared` with exact new target plus exact old incumbent under the temp name; recovery verifies both captured identities/digests, fsyncs the parent, performs the same generation-and-phase CAS to `replacement-cleanup`, and only then continues. Any mismatch in that tuple is conflict. Only `replacement-cleanup` may unlink the exact old temp; it fsyncs the parent before the final CAS clears pending. Recovery in `replacement-cleanup` accepts exact new target plus exact old temp, or exact new target plus absent temp when unlink already completed, and finishes cleanup/finalization. In replacement `planned` or `prepared`, exact old target plus absent or incomplete temp terminalizes as the same durable no-effect interruption; exact new target plus absent temp before `replacement-cleanup` is conflict because cleanup cannot precede the phase CAS. Every other target/temp/inode/digest tuple is conflict and performs no rename/delete. Thus every initial and replacement crash point yields complete old bytes, complete new bytes, or a durable proved-no-effect interruption; it never guesses replay from a missing temp and never exposes partial JSON. `README.md` is a derived projection: manifest publication is authoritative, and a crash before README replacement leaves an explicit stale projection that recovery regenerates from the committed manifest before serving it. Completion waits for all queued task publications. Cleanup may transition to `cleanup-prepared` only with no pending publication and after acquiring the same lock; a stale completion after cleanup begins cannot install a pending record or publish. Capability removal, child completion, shutdown, or cleanup rejects new output publications and drains or marks the bounded existing queue uncertain under lifecycle ownership.
7. List/index work has a five-second budget and gather/detail has a three-second budget, measured from authority selection through the last descriptor read. Scans run in a lifecycle-owned worker pool of exactly two threads; the native iterator receives the monotonic deadline and checks it between every entry/read, and worker messages enforce the same encoded result cap before allocation on the main thread. A third scan returns `orchestration_scan_busy`; an expired scan returns `orchestration_scan_timeout` without partial data. A timed-out native call remains lifecycle-owned and holds its worker/concurrency slot until it returns; shutdown waits only its registered bounded phase and reports uncertainty rather than starting another scan against the same root. These bounds supplement, rather than replace, the byte/count limits.
8. Model/tenant gather no longer performs recursive cleanup; `cleanup: true` is rejected with no delete. Explicit local operator cleanup first opens and verifies the authorized canonical directory and records its device/inode. In one durable authority transaction it generates and stores a same-parent quarantine name of at most 128 ASCII bytes plus random UUID cleanup generation and transitions the expected row to `cleanup-prepared` before rename. The native package then performs same-parent no-replace rename through the pinned parent descriptor and fsyncs the parent; a CAS marks `cleanup-quarantined`. Descriptor-relative recursive deletion may touch only that stored quarantine inode and fsyncs each changed directory. Each worker pass deletes at most 1,000 entries and runs for at most three seconds; reaching either bound leaves `cleanup-quarantined` and a visible next-pass requirement rather than blocking startup or reporting success. After the quarantine is confirmed absent, a final durable CAS writes the minimal retained `tombstoned` record. Startup/retry handles every crash point idempotently: prepared with canonical present/quarantine absent retries rename; prepared with canonical absent/matching quarantine present advances; quarantined with matching partial quarantine deletes another bounded batch; quarantined with both absent finalizes the tombstone. Both present, neither present before a proved rename, inode mismatch, a replacement canonical entry, malformed state, or foreign quarantine is explicit recovery conflict and deletes nothing. The cleanup name/generation cannot be reused, and no generic age-based reaper touches it.
9. Local `orchestrations inspect`, RPC get, the in-agent tool, crash recovery, aggregation, publication, and cleanup use the same native resolver; no raw `path.join(..., suppliedId)`, in-place `writeFile`, or independent recursive delete remains at an access boundary. Public tool input no longer exposes `orchestrationId` for new orchestration creation. Existing resume semantics, if implemented later, require a separately authorized existing row and cannot reuse the create parameter. Tests may inject deterministic ID/temp factories only through private dependencies.

### 6. Live event boundary (GW-005)

1. `pi-agent.orchestration-progress` is an explicit `operator.admin` event in the central broadcaster. It is evaluated for ordinary broadcast and targeted connection sets. Payload fields and target connection IDs cannot grant authority.
2. Any authenticated operator connection with explicit `operator.admin`, including an admin device-token connection, receives the unchanged frame. Tenant users/org administrators, role `node`, non-admin device-token operators, and non-admin service accounts receive zero frames. This matches the existing CLI/device compatibility model instead of adding an `authMethod` ban.
3. The event name, payload shape, sequencing, slow-consumer behavior, and lifecycle disposal remain unchanged. The bridge stays global. Tenant progress requires a future server-owned audience carried separately from the payload and is not synthesized in this slice.

## Consumer and release impact

- **Hub:** list/get remain available for tenant-owned or operator-qualified manifests. The current silent partial-failure behavior must become explicit unavailable/retry UI and generation-fenced state. No Hub code calls tenant RPC create. The global toast/`CustomEvent` consumer becomes admin-only input.
- **Site:** no orchestration RPC or event consumer found.
- **Paperclip:** no orchestration RPC or event consumer found. Its raw agent-event compatibility is unrelated and remains governed by GW-023.
- **CLI:** admin gateway list/get and local inspect/cleanup remain compatible on a capability-probed supported Linux artifact after safe path validation. On macOS, Windows, a missing addon, or an unsupported kernel/filesystem, filesystem-backed orchestration commands report the stable unavailable state and perform no path operation. The new local import command is the only way to qualify legacy rows for tenants. Persisted admin device-token connections remain valid administrators when they carry `operator.admin`.
- **Protocol:** method and event names and existing success payload fields remain compatible. List may add `truncated`; failures use existing error envelopes. Authorization and authority records stay server-side, so no shared package release is required.
