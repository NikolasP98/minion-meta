Missing/deleting/inactive/nonmember yields the same generic operator_principal_inactive before any role rows are returned. Do not rely on token validity or a surviving membership alone. Plain mode uses the identical selected predicates without locks, inside caller's RR snapshot.

Return only the closed selected structure below. Never return names, email, phones, auth users, arbitrary profile JSON or a raw table row. ## Exact return and adapter contract

```ts
export interface OperatorAuthorityRows {
  version: 1;
  orgId: string; profileId: string;
  organizationStatus: 'active'; deletionPending: false;
  roleModel: string | null; defaultRoleKey: string | null;
  membershipRole: string | null; // organization_members.role is nullable in some schemas (not provable from repo migrations); null = legacy viewer fallback, same as the legacy adapter
  assignedRoleKeys: string[];
  localRoleKeys: string[];
  rules: CapabilityOverrideRow[];
  authorityRows: { table: string; key: string[]; rowHash: string }[];
}
```

The closed table set is organizations/profiles/organization_members/member_roles/org_roles/permission_rules. assignedRoleKeys are this actor's actual member_roles.role_key; localRoleKeys are this org's org_roles.key; rules are this org's exact existing role_key/module/can_view/create/edit/delete/export/manage/if_owner/field_level fields with existing null semantics. Preserve legacy/new role-model selection, union/override behavior and effective-authority narrowing. Stable sort assignment/local keys, rules by `(role_key, module)`, row digests by `(table, key)`, with C collation on SQL text keys; duplicate logical keys/inconsistent source schema fail rather than choose an arbitrary row. rowHash is encode(pg_catalog.sha256(pg_catalog.convert_to(pg_catalog.to_jsonb(row)::text,'UTF8')),'hex') computed IN SQL under UTC; raw profile rows are never returned. This built-in hash form already appears in pinned notification_audience_projection.sql:375,954.

Count before aggregating: at most 128 assigned keys, 128 local keys and 10,000 permission rows; limit+1, or selected key/module text longer than 256 UTF-8 bytes, fails `operator_authority_limit` without truncated output. The final selected JSON must be at most 2,097,152 UTF-8 bytes; otherwise fail. These are explicit new operator-path safety bounds, not changes to legacy/cached RBAC limits or measured performance. The same complete bound applies in both modes. No successful empty-capability fallback on decode/SQL/ACL/function-unavailable failure.

CapabilityOverrideRow is a type-only import from rbac.service.ts; active-operator-principal.ts must not value-import that service. This preserves the runtime dependency direction from RBAC adapters to the bridge helper.

## Resolved implementation decisions (R6, 2026-11-17)

- CD-03 FORCE RLS: baseline `schema.sql` sets FORCE ROW LEVEL SECURITY on `member_roles` (3272), `org_roles` (3638), `organization_members` (3653) and `permission_rules` (3748). The only viable function owner is therefore a superuser or BYPASSRLS role (the Supabase `postgres` role has BYPASSRLS in production). The migration preflight requires one common owner of all six tables and, when any is FORCE, `rolsuper OR rolbypassrls` for that owner; otherwise it raises and nothing is created. The "table owner without FORCE" alternative is retained in the code only for a schema with no FORCE table. Release prerequisite (OWNER, read-only): run `select rolname,rolsuper,rolbypassrls from pg_roles where rolname=(select tableowner from pg_tables where schemaname='public' and tablename='member_roles')` on production; if neither flag is true the migration fails closed and the owner decides between granting BYPASSRLS to that role or explicit policies (a separate approval). The native test proves the success path with the controller superuser owner and the failure path with a non-bypass owner.
- IR-09 migration-seed pairing: the PR carries the `seed-unaffected` label with the reason "adds one SECURITY DEFINER function, no table/seed data". qa-stack applies `supabase/migrations/` through `scripts/qa/db-bootstrap.ts`; its owner preflight is the migration's own `do $preflight$` block, which the local QA owner (a superuser) passes.
- IR-13: the read-only entrypoint calls the bridge (`p_lock_rows => false`) and then `composeFreshCapabilitiesFromAuthorityRows`; it issues no direct SELECT on `organizations`/`profiles`. This supersedes the "uncached nonlocking SELECTs" wording in audit-cli.md.
- IR-15: `principalStateHash` = SHA-256 of `JSON.stringify` of `{orgId,profileId,membershipRole,roleModel,defaultRoleKey,authorityRows}` in the bridge's stable order. `verifiedAt` is bounded by the snapshot `transaction_timestamp()`.
- Bridge `authorityRows` order: `(table, key joined with U+001F)` in C collation. The TS validator checks structure/bounds only, not order.
- CD-07: "existing F3 caller", "existing eight-case file" and "thirteen-case suite" mean artifacts proposed by spec 124 / task T003; none exists at the pinned source.
- CD-08: `FreshCapabilitySnapshot` is exported from `rbac.service.ts` (`{capabilities,roles,membershipRole,realCapabilities,realRoles}`).
- Audit amendment: the TypeScript adapters preserve the SQLSTATE on the error for retryable codes (`55P03`, `40P01`, `40001`: rethrown unchanged so the caller's retry wrapper sees them); every other SQL failure is `operator_authority_unavailable`. Callers map only `operator_principal_inactive` and `operator_scope_invalid` to a refusal (403); everything else is a retryable 503.
