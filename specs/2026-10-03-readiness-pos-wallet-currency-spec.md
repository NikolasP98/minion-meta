# Currency-isolated stored value

## 0. Product

HS-009, HS-012 and HS-029 protect a client's stored value: amounts in different currencies cannot fund one another, a payment method's spelling cannot silently spend a wallet, and ordinary application access cannot rewrite ledger history. This slice builds on the exact decimal work in HS-028/HS-017; it does not replace its currency policy.

## Out of scope

No foreign-exchange conversion, historical ledger rewriting, payment-provider integration, tax/emission policy change or production migration is included. Ticket/top-up idempotency (HS-010/011), plan concurrency (HS-013/014), and stock/booking transaction ownership remain separate slices. Explicit drawsOnCredit must not change historical void behavior: reversals use persisted ledger rows and their original currencies.

## AS-IS

- `pos-accounts.logic.ts:ledgerBalance`, `pos-accounts.service.ts:creditBalance/listClientAccounts` and `pos.service.ts:chargeClientCredit` sum signed amounts without separating currencies. The current exact-money adoption validates each currency but still adds nominal PEN and USD together. For example, 100 PEN plus 100 USD can appear as a 200-unit spendable balance.
- `pos.service.ts:CREDIT_METHOD_ID` and the browser sell workflow infer wallet spending from `method === 'credit'`. A custom credit-card method with that ID spends the wallet. Other custom IDs cannot declare wallet behavior. The default method set contains cash/card/yape/plin/transfer, not credit, so an existing credit identifier is a custom configuration whose intent cannot be safely inferred.
- `validateTicketMoney` validates method existence and tender behavior but does not reject a now-disabled method. A stale client can still submit it.
- `widenClient` trusts a caller-supplied party/contact pair without checking the bridge, chooses an arbitrary contact for a party that has several, and `clientMatch` ORs both facets. `chargeClientCredit` locks the caller's pre-widen key. The same wallet can therefore take different locks, while a conflicting pair can merge two clients' rows.
- `submitTicket` reads payment methods and currency before opening its money transaction. `addLedgerEntry` also resolves an omitted currency before its transaction. A settings write can therefore commit first while either operation continues under stale tender or currency policy. The request carries no settings revision, so a stale browser can also submit an identifier whose meaning changed from external tender to stored value.
- The account detail route launches balance, ledger, grant and plan reads in independent transactions, then performs one transaction per plan for progress. It cannot return one database snapshot. The account list groups ledger, grants, plans and pending tickets under one arbitrarily selected contact key; existing `contact:<uuid>` deep links depend on those keys.
- `crm_contacts.party_id` is a soft reference. A raw `parties` INSERT, DELETE or `id`/`org_id` change can make a previously dangling link valid or invalid without changing `crm_contacts`, so a contact-only trigger does not fence every identity-map transition.
- `20260914000000_pos_packages_plans.sql` grants SELECT/INSERT/UPDATE/DELETE on pos_client_ledger to app_ledger despite the append-only service invariant. Current non-test source has no ledger UPDATE/DELETE caller; corrections and voids append opposing rows.

## TO-BE

1. Every balance is identified by canonical ISO currency. Account list and detail return the exact same bounded projections: `balancesByCurrency: Array<{ currency, balance }>` and `openPlansByCurrency: Array<{ currency, count, total }>` in supported-currency order. Compatibility `balance`, `balanceCurrency`, `openPlans` and `openPlanTotal` describe only the current POS currency; `totalOpenPlans` may separately count all currencies. A caller must not pair an all-currency count with a current-currency amount. Do not show a cross-currency nominal total. Every displayed bucket calls `formatMoney(value, bucket.currency)` rather than relying on its PEN default.

   `pos_package_grants` has no currency column, so its immutable money authority is the required same-organization `source_ticket_id -> pos_tickets.currency` relation, never current POS settings. Grant creation validates that source in the sale transaction before INSERT. Every grant read joins or batch-loads the exact source ticket under the organization fence, validates its persisted currency and returns `GrantView.currency`; a missing, foreign or invalid source is typed `invalid_stored_amount`, not PEN/default fallback. `ClientAccountDrawer`, `BookingDetailDrawer` and every other unit-value display call `formatMoney(grant.unitValue, view.currency)`.

   The forward migration makes that authority durable. A grant INSERT or change to `org_id`/`source_ticket_id` must reference a ticket with the same organization. A referenced ticket cannot be deleted or have its `id`, `org_id` or `currency` changed; status/void fields remain mutable. Trigger functions are schema-qualified with fixed `pg_catalog` search path and cover raw/owner SQL as well as services. No historical grant currency is copied from current settings or inferred from the drawer locale.

   Both sides serialize on the same versioned `grant-source` advisory key derived from organization plus source-ticket ID. This class follows settings, identity and wallet locks and precedes relational row locks; multi-ticket operations acquire its complete distinct key set in binary order. Known application writers acquire the blocking transaction lock in a statement before grant/ticket mutation and re-read the source relation in a later statement, so a waiter validates against a post-wait `READ COMMITTED` snapshot. The grant and ticket statement triggers are the raw-SQL backstop: they call `pg_try_advisory_xact_lock` for every sorted old/new key and fail with a typed serialization conflict rather than waiting under the statement's stale snapshot. A service transaction already holding the key succeeds reentrantly. This no-wait fallback prevents write skew without creating a trigger-order deadlock; a raw caller may retry the complete transaction after the winner commits. Trigger validation uses fresh post-lock database reads, including when a raw mutation statement began before the competing commit but reaches the try-lock only after the key was released. The implementation must prove this PostgreSQL snapshot behavior with the actual trigger; a successful try-lock alone does not prove freshness.

2. Credit redemption uses only rows in the ticket's currency inside the same transaction as ticket/ledger persistence. An empty wallet in that currency has zero available credit even when another currency is positive. Positive/negative adjustments, void reversals, account detail/list and cashier availability use the same grouping rule. No caller silently converts money.
3. Balance aggregation occurs in PostgreSQL with organization/client predicates and `GROUP BY currency`, then bounded exact DTO conversion; do not load an unbounded ledger into JavaScript. Currency count is bounded by the server-authoritative supported-currency policy. Replace the current permissive widening with one transaction-owned wallet identity resolver. Its mutation mode requires every supplied facet to be active in the organization and rejects a supplied party/contact pair unless that exact non-deleted contact currently points to that party. A verified party is the canonical account; an active unlinked contact is its own canonical account. All new POS account-owned rows use the canonical party when one exists and retain a presented contact only as provenance. This applies to ledger rows, payment plans, package grants and tickets used by the account projection, so one source cannot reintroduce the current OR-match merge.

   Persisted `party_id` is authoritative for every historical POS account-owned row, even when its provenance contact is later relinked. Only a row whose `party_id is null` follows the contact's current active bridge. A party projection therefore includes rows stamped with that party plus contact-only rows for all active contacts currently linked to it. A relink moves contact-only history under the serialized new bridge; it never moves a row already stamped with a party. A conflicting historical dual-facet row stays with its persisted party and does not become visible through the provenance contact's new party.

   List responses emit one canonical `party:<uuid>` key for a linked client and `contact:<uuid>` only for an active unlinked contact or a contact-only orphan. Existing `contact:<uuid>` URLs remain read aliases. A successful alias read returns both `requestedClientKey` and the canonical `clientKey`, and the account page replaces its selection with the canonical key without opening a second account. Multiple contacts linked to one party never select `min(contact)` or create duplicate list rows.

   HC035 durable plan creation uses the same authority before it generates an operation UUID or writes local durable admission. A narrow authenticated resolver, guarded by active POS plus `pos:create`, takes the shared organization identity lock, validates the submitted party/contact pair and returns the exact canonical facets plus `clientKey`. The frozen plan intent stores that canonical `clientKey`, party and provenance contact; an account continuation stores the same canonical key. For a new operation, the plan POST includes the key, takes the ordered settings and shared identity locks in its money transaction, resolves the facets again and requires an exact match before any operation-row or plan insertion. A contact relink/link/unlink between preparation and first dispatch therefore returns typed `wallet_identity_changed` with zero operation, plan or external effect. The existing-operation replay check below precedes this mutable-authority validation. A conflicting dual-facet request never reaches durable admission.

   HC035 first takes its existing operation lock and checks the same-actor cancellation tombstone and committed request receipt before reading current settings or resolving current identity. An exact committed replay must still return its original plan after contact relink/deletion, settings changes or plan cancellation; it never creates again or revalidates mutable admission rules. Keep the exact lock SQL and key bytes already used by create and cancel: `pg_advisory_xact_lock(hashtextextended(JSON.stringify(['pos-plan-operation-v1', orgId, operationId]), 0))`, with JSON serialized by the existing helper and bound as a SQL parameter. Do not migrate this lock to the new JSONB helper or alter its namespace while old create/cancel processes may coexist.

   Keep the version-1 request serializer and hash byte-compatible for existing rows and legacy retry requests. New canonical requests use an explicit version-2 intent/hash contract that includes the canonical client key and facets; persist the version with a forward migration whose default for existing rows is 1. Receipt matching chooses the persisted version and rejects a mismatched request, actor or intent; neither stored hashes nor old frozen requests are rewritten. A version-1 request for an absent operation cannot bypass the new canonical preflight: it receives a typed upgrade/identity-required failure with zero write, while its existing-operation replay remains supported. Its same-actor committed status/receipt adds only a persisted continuation identity reference alongside the plan ID; it does not return a name or other customer data. Version2 stores the admitted canonical clientKey with the new plan and returns it unchanged. Version1 derives an immutable reference directly from the persisted row: party:<party_id> when stamped, otherwise contact:<crm_contact_id> as an explicitly tagged legacy alias. Do not backfill a party key from today's contact bridge or rewrite old plan authority; later relink would make such a backfill disagree with contact-only row membership. A version-1 durable account continuation that contains `contact:<id>` is never used to dispatch again. Recovery looks up the unchanged operation ID first. On a committed receipt it compare-updates only the continuation to the returned persisted reference, preserves the frozen request and operation ID, then performs callback-only projection repair without replaying POST. A legacy contact reference is resolved through the ordinary authorized account read, which returns requestedClientKey, current canonical clientKey and the exact plan ID in the same bounded snapshot. The continuation may refresh that projection only if it contains the receipt's exact plan; it must never adopt an unrelated account just because the contact currently points there. If the current form is for a different canonical account, show the exact persisted account link and require explicit navigation before repair; do not replace the current customer automatically. If the exact plan is beyond the bounded page, use a narrowly filtered authorized plan projection instead of treating truncation as absence. Missing identity, removed permissions or an unavailable plan remains visibly committed with blocked projection repair, never permission to create again. Cancelled stays cancelled. Absent/unknown/conflict cannot prove which identity a create might still use, so the record remains blocked for HC035's explicit cancellation workflow; it is not silently rewritten from the contact's current bridge. A newly confirmed request after cancellation is a new operation. A live owner may repair a record before its first fetch only when it has local proof that this owner just admitted it and `fetchInvoked` is still false.

   Read resolution remains truthful when the soft identity row is gone. An organization-owned contact-only POS row whose contact is missing or soft-deleted remains visible under `contact:<uuid>` with `identityStatus: 'missing_contact' | 'deleted_contact'`; a dual-facet row remains under its authoritative persisted party. A persisted missing party remains visible under `party:<uuid>` with `identityStatus: 'missing_party'`. A contact pointing at a missing party is returned under that authoritative party key with `identityStatus: 'missing_party'`. Names may be null. A valid active organization identity with no POS rows still returns an empty active account for existing deep links. A foreign or random key with neither an active organization identity nor an organization-owned POS row remains indistinguishable from absent. Ordinary top-up, spend, new plan, new grant and new ticket mutations reject a non-active identity with typed `wallet_identity_unavailable`; they never adopt a similarly shaped party/contact. A historical ticket void may still append the exact opposing rows from persisted provenance and currency. It does not claim a new identity. No automatic orphan transfer or historical rewrite occurs; the release inventory reports orphan counts, and any production orphan transfer requires a separately reviewed append-only compensation.

   All code uses one global lock order: keyed HC035 plan operation (when present), organization POS settings, organization identity map, canonical `{organization, party-or-contact, currency}` wallet, grant-source authority, then relational row locks. Create and cancel retain the existing operation-key helper described above; cancellation needs no money/identity lock. A path that does not need an earlier class skips it; no path may acquire an earlier class after a later class. Sale plus every default-currency ledger or plan mutation takes the shared settings lock. `updatePosSettings` takes its exclusive form. Account list/detail takes shared settings and identity locks. Identity resolution and all new account-owned row writes take the shared identity lock. Bridge writers take exclusive identity locks for the complete affected organization set. Every ledger mutation, including negative adjustments and persisted-row void compensation, takes the exclusive canonical wallet lock before reading or appending that wallet/currency. Grant creation and any ticket source-authority mutation then take the grant-source key before row locks. An operation that touches several keys computes the complete distinct set first and acquires each class in deterministic binary tuple order; it never discovers and locks another earlier-sorting key after mutation begins.

   The migration owns schema-qualified `public.pos_advisory_key_v1(lock_kind text, org_id text, subject text default '', currency text default '')`. It accepts only `settings`, `identity`, `wallet` or `grant-source`, rejects null/empty organization IDs and requires a non-empty subject for `grant-source`. It hashes `pg_catalog.jsonb_build_array('minion.pos.lock', 1, lock_kind, org_id, subject, currency)::text` with `pg_catalog.hashtextextended(..., 0)`. Application code and triggers call this same database helper; they do not reimplement PostgreSQL hashing. The function has a fixed `pg_catalog` search path, no dynamic SQL and explicit execute privilege for `app_ledger`. Separate tuple members prevent intentional overlap. Hash collisions may reduce concurrency but cannot weaken serialization. Multi-organization writers acquire the complete distinct organization set in deterministic binary order before any wallet or grant-source key. A deadlock aborts the whole transaction and must never be caught as partial success.

   The forward migration, rather than a service convention, is the authority for identity-map serialization. Separate statement-level transition-table triggers cover every `crm_contacts` INSERT and DELETE and every UPDATE whose old/new `id`, `org_id`, `party_id` or `deleted_at` differs. Equivalent triggers cover every `parties` INSERT and DELETE and every UPDATE whose old/new `id` or `org_id` differs. Each trigger gathers distinct old and new organization IDs, sorts them in the same binary order and acquires the exclusive transaction identity lock once per organization. Non-identity party/contact updates take no map lock. Separate transition-table triggers on `pos_settings` INSERT, UPDATE and DELETE acquire the exclusive settings key for all affected old/new organizations, so raw SQL cannot bypass the sale/config fence. The trigger functions are schema-qualified, use a fixed `pg_catalog` search path and no dynamic SQL. Known Hub writers acquire the same complete lock set early when it is knowable, but triggers remain the correctness backstop for raw SQL, migrations and other repositories.

   Account list and detail run at `READ COMMITTED`. Statement 1 acquires the shared settings lock and statement 2 acquires the shared identity lock; neither statement reads application rows. One subsequent bounded SQL statement produces the complete response snapshot. The detail statement returns balance buckets, at most 200 ledger rows, 100 grants and 100 plans plus their aggregated progress; it reports a per-collection `hasMore` bit from a limit-plus-one read. The list statement returns at most 500 canonical accounts and all bounded currency buckets for those accounts. Do not replace this with parallel service calls or plan N+1 reads. Do not switch to `REPEATABLE READ` and acquire the advisory lock as its first statement: PostgreSQL may establish that transaction snapshot before a waited-on writer commits. The post-lock data statement must obtain its snapshot only after both locks are held.

4. Add explicit boolean `drawsOnCredit` to the persisted payment method contract and an explicit read-side transition state to settings, cashier option projection and the shared ticket validator. Ordinary legacy methods without the field normalize to explicit false. A bare legacy string `credit`, or an object whose `id` is `credit` and whose field is absent, reads as `drawsOnCredit: null` plus `requiresCreditDecision: true`; it must never be coerced to false before the manager sees and resolves it. A disabled ambiguous row remains unavailable and visibly unresolved; an enabled ambiguous method is rejected when selected in preview or submit. Never silently turn that method into external cash or assume it remains stored value. Existing tickets remain readable and voidable. Newly created methods explicitly save false by default.

   The settings write contract has field-presence semantics. When `methods` is omitted, the SQL update does not include that column and the stored JSONB value remains unchanged; it must not round-trip the read-side `null` through a normalized full object. The settings UI omits `methods` for an unrelated save. When `methods` is present, every row must carry an explicit boolean `drawsOnCredit`; resolving an ambiguous row therefore requires an intentional methods write. A malformed, missing or null field on that write is a typed validation error. Mounted UI keeps the draft and shows a localized configuration-required state.

5. Only configured, enabled methods may be used in preview or submit. Sum credit payments across every explicitly flagged method, never by identifier spelling. Credit methods cannot take physical tender/change; reject contradictory settings before saving. Customer-required and available-credit UI mirror server rules. Preserve existing SUNAT/document policy and historical payment labels.

   Settings reads expose an opaque `paymentPolicyRevision` covering every ticket-admission setting, including currency, methods, customer/document requirements, price-override policy and emission defaults. It is the 64-lowercase-hex SHA-256 of a versioned, deterministic JSON projection: object keys are fixed by the serializer, method array order is retained, and read-side legacy normalization preserves the explicit false-versus-ambiguous null distinction. A missing settings row uses the same projection of defaults and therefore has one deterministic revision. Browser ticket POST and assistant confirmation echo the revision they displayed or received from preview. Under the shared settings lock, submit re-reads settings inside the same money transaction, compares the revision and reruns the shared validator before any insert. A mismatch returns typed `pos_settings_changed` with zero ticket, payment, ledger, grant, redemption or provider effect; the caller reloads and asks for confirmation under the new policy. The assistant preview response includes the revision, and `confirm:true` without the matching revision cannot commit. This prevents a stale method identifier from changing from external tender to wallet spend, and prevents a stale PEN screen from being committed as USD.

   `updatePosSettings` acquires the exclusive settings lock before reading or upserting, including when no settings row exists. A submit or default-currency top-up that acquired the shared lock first may finish under its matching revision before the manager write commits. If the manager owns the exclusive lock first, the operation waits, observes the new revision and fails `pos_settings_changed` rather than using the old policy. Standalone ledger writes with an explicit currency still validate that currency inside their transaction; writes with omitted currency resolve the current configured currency only after taking the shared settings lock. Historical void compensation uses persisted currency and does not consult current settings.

6. A forward migration runs `REVOKE UPDATE, DELETE ON TABLE public.pos_client_ledger FROM PUBLIC, anon, authenticated, app_ledger`. Current source grants the table only to `app_ledger`; the broader explicit revoke prevents an ambient/default grant from preserving mutation access and does not grant `anon` or `authenticated` SELECT/INSERT. `app_ledger` retains tenant-scoped SELECT and INSERT and remains `NOINHERIT`, `NOSUPERUSER` and `NOBYPASSRLS`; this table migration does not alter role membership or attributes. Ordinary-role attempts to update/delete either same-org or foreign rows fail with PostgreSQL permission denial; append/reversal remains possible. Database-owner disposable cleanup and future audited owner migrations are separate from application privileges. Do not change historical migrations or weaken RLS.
7. Unsupported/corrupt currency or amount remains a typed, sanitized error through the existing money boundary; never normalize it to zero. Failed financial admission occurs before any external stock/provider effect.

The account service owns one post-lock list statement and one post-lock detail statement instead of composing independent service transactions. The forward migration owns the matching exclusive contact/party statement triggers and the versioned SQL key helper.

Keep package-grant currency in the existing immutable source-ticket relation rather than adding a second nominal field. Extend the existing same-transaction `requireGrantSourceCurrencies` boundary to every grant read, return its result as required `GrantView.currency`, and update every grant-unit-value consumer to use that field. The forward migration adds the ordered `grant-source` lock class and both sides of the source relation fence: blocking pre-lock plus post-wait validation in known services, no-wait trigger serialization for raw SQL, same-organization source validation on grant INSERT/source change, and referenced-ticket identity/organization/currency immutability while grants exist. Migration and native tests use the production grant/ticket DDL and exercise service and raw-owner writes.
