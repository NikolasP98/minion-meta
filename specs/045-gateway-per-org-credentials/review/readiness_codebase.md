# 045 readiness: codebase-details goldfish

Checked at hub `dac2ac03`, gw `45e34c02583`, site `dev@7f4c3b2`.

## 🔴 Blockers

1. **"Dedicated" can't be computed the way §3.1 says.** `gateway.org_id` is one nullable column, and `url` is unique (`@minion-stack/db/src/pg/schema/gateway.ts:15,25`). `gatewayBelongsToOrg` compares that single column (`gateway.pg.service.ts:381-394`). So `count(distinct org_id)` over one gateway row is always 1, every org owner/admin gets `admin`, and I4's shared-gateway row never fires. No table maps several orgs, or several rows, to one gateway process. The design needs a real source of truth, such as a gateway-side `multiTenant.dedicatedOrgId` or rows grouped by `hubMetrics.serverId`.
2. **`auth.refresh` gets around the `gatewayId` binding.** §3.4 puts the check in `resolveJwtAuth`. But `auth.refresh` validates through its own `deps.validateJwt`, and only against the first issuer (`server.impl.ts:1617-1627`). It then overwrites `userId`, `role`, `orgId` and `scopes` on the live socket (`auth-refresh.ts:56-65`). It never checks that the new JWT has the same `userId`, `orgId` or `gatewayId`. Example: a user connects to shared gateway B as `org_admin`, then refreshes with their `admin` JWT for dedicated gateway A, and the B socket becomes admin. Answer to Q4: yes, refresh already re-applies scopes and claims. §3.4 describes that as new work, but what's actually missing is the binding.
3. **`org_admin` = `approvals`+`pairing` on a shared gateway reaches across tenants.** `PAIRING_METHODS` includes `device.pair.approve`, `device.token.rotate` (caller picks the scopes, and nothing caps them: `devices.ts:148-153`, `device-pairing.ts:523-533`) and `node.pair.approve` (`server-methods.ts:75-87`). The `device.pair.*`, `node.pair.*` and `exec.approval.*` events go to every client with that scope, with no org filter (`server-broadcast.ts:9-16,48-64`). An org admin could approve another org's nodes or exec requests. Keep shared-gateway `org_admin` at read+write, or add org scoping first.
4. **`auth.token.refreshed` goes to every socket.** `context.broadcast` (`auth-refresh.ts:68-73`) has no guard in `EVENT_SCOPE_GUARDS`. With a 10-minute refresh on every client, every org on a shared gateway receives every other org's `userId`, `orgId` and `connId`. A1 must target the event to the refreshing connection.
5. **`requireGatewayIdClaim` breaks server-side JWT callers.** `mintOrgGatewayJwt` calls `issueGatewayJwt` (`organization-provision.service.ts:184-186`) and sends the result next to the token (`gateway-rpc.ts:245`). A JWT is checked first (Case 1, `ws-jwt-auth.ts:56-68`), so a provisioning JWT with no `gatewayId` will be rejected once the flag is on. "mintOrgGatewayJwt unchanged" (§3.1) is therefore false. A2's TTL and role changes also flow into provisioning.

## 🟡 Majors

6. **Q2, plugins: §1.1 is wrong, and A4 targets the wrong repo.** No plugin UI opens its own socket. Each one stores `authToken` and then calls a no-op `connectRpc` (`extensions/telegram/ui/src/lib/rpc.ts:1-17`, and the same in discord, alert-watcher and whatsapp). Every RPC goes over the host's socket through `forwardRpc` (`PluginIframe.svelte:23,313-319`). The UIs live in `minion/extensions/*/ui` (alert-watcher, discord, meta-graph, studio, telegram, voice-call, whatsapp), not in `minion_plugins`, which is a Claude Code marketplace with no gateway UIs. A4 shrinks to "stop sending `authToken`". The token still reaches the iframe today, posted with targetOrigin `'*'` when the iframe is sandboxed (`bridge-protocol.ts:102-104`). Also, `settings/plugins/+page.svelte:505` shows "no host" whenever `authToken` is empty, so A3 must remove that check.
7. **The PTY path is dead code.** `(app)/terminal/+page.server.ts` redirects 307 to `/cloud/terminal`, which uses `shells` access tokens (`RemoteTerminal.svelte:57,75`), not the shared token. Delete `terminal/+page.svelte` instead of adding JWT support to PTY in A1 and A3. Fix the path in §1.1 as well: it's `src/gateway/server-core/server-http.ts:970-993`, and it also accepts tailscale and trusted-proxy.
8. **§1.1 overstates what browsers can do today.** When a JWT is present, Case 1 wins even with a valid token, and scopes become `mapRoleToScopes(role)` (`message-handler.ts:943-971`). In prod (`PUBLIC_GATEWAY_JWT_AUTH=true`), a non-platform-admin's dashboard is already read+write only. Admin power is reachable only by leaving the JWT out (hand-crafted, or the 60 s fallback). The claims "FACES does not regress" and "a FACES admin can pair WhatsApp" need evidence of what FACES users have today: `profiles.role`, and whether FACES `oidcIssuers` is set.
9. **Q1, site: the token is mostly ciphertext, and the panel is already broken.** The layout selects `servers.token` but not `token_iv` (`members/+layout.server.ts:20`). The hub writes encrypted values (`server.service.ts:92-105`), so the browser gets ciphertext, or plaintext for legacy rows with an empty IV (`server.service.ts:191`). The client connects with `role:'member'` (`member-gateway.svelte.ts:30`), and the gateway closes any connection whose role isn't `operator` or `node` with "invalid role" (`message-handler.ts:378-385`). So the panel can't work anyway, and A0/OQ2 costs nothing. Separately, §3.3's "site runs Better Auth" is only partly true: `AUTH_PROVIDER=supabase` is the documented default (`.env.example:30`, `hooks.server.ts:86-121,186`), which uses the same GoTrue as the hub. Prod reachability depends on Vercel env (not checked).
10. **Q3: the role source isn't specified.** The org role can come from `member_roles` (owner, admin, manager, staff, viewer) or from the legacy `organization_members.role` (`rbac.service.ts:20-22,163-168`). `effectiveGatewayRole` has to name which one it uses. It must also say whether the `gatewayId` claim is `legacy_server_id` or `gateway.id`, because the client keys by `legacyServerId ?? id` (`gateway.pg.service.ts:353`) and `hubMetrics.serverId` is free text (`zod-schema.ts:757`).
11. **Q5: other admin-equivalent or cross-tenant paths that §1/§6 miss:**
    - Case 2 grants admin to `tailscale` and `trusted-proxy` connections too (`ws-jwt-auth.ts:120-144`), and `allowTailscale: true` is the default (`docker/default-config.json:11`).
    - `/mcp` OAuth hands out admin refresh tokens to anyone who enters the shared secret. They are in memory and never expire (`mcp/oauth/handlers.ts:12,298`, `store.ts:111-138`). Rotation (I7) must restart the gateway to clear them.
    - `logs.tail` and `config.get` are READ methods with no org filter (`logs.ts:48-71`, `config.ts:335-341`), so a `user` JWT reads gateway-wide logs and config on a shared gateway.
    - The device token from `device.token.rotate` comes back in plaintext (`devices.ts:161-171`). It is harmless only while `oidcIssuers` is set, because the JWT check rejects a device token alone.
    - No Sentry or PostHog leak found. The token endpoint logs only the length (`+server.ts:129`), and `gwTrace` logs `hasToken` as a boolean.
12. **Q6: callers.** All of them go through `fetchHostToken`: `gateway.svelte.ts:679` (connect), `:751` (`cutoverToHost`, a second connect path that A3 must also convert), the dead terminal page, `settings/plugins/+page.svelte:94` and `PluginControlCenter.svelte:59`. No callers in site, paperclip, pixel-agents or the gateway.
