# D → E shared interfaces (version 1)

D is the provider; E stacks its branch on D's implementation commit before changing shared files. Names below are proposed new APIs, not claims they exist in the source pin. D and E development must retain these semantics; renaming requires coordinated update to both plans/tests.

## Background jobs

`enqueueJobInTransaction(tx: JobTransaction, input: {tenantId,userId,type,refId,cursor?}): Promise<string>` inserts once inside a caller-owned bookkeeping transaction. It has no idempotency of its own: caller first locks/looks up the domain unique key. It performs no transaction start/commit and no network work. Existing `enqueueJob` delegates through its existing outer handle.

`runSelectedTick({tenantId,ownerProfileId,types,budgetMs,maxCandidates?}): Promise<{advanced:number}>` requires explicit nonempty immutable selections from trusted server config. `types` is constrained to registered Pulse handlers `pulse_dispatch` and, after E, `pulse_digest`; default candidate cap is 20, maximum 20. Candidate SQL ANDs tenant, owner (`bg_jobs.user_id`), type, due time, queued/expired-running state before ordering/LIMIT. Atomic claim independently repeats due/state/generation and exact selection binding. Direct `advanceJob` also enforces due time; it cannot bypass postponement. Existing callers may ignore a new typed advancement result; only successful ownership acquisition plus handler invocation contributes one advanced count. No handler/failed claim/quiescing contributes zero. Global `runTick` preserves its API/default route behavior and existing handlers' retry semantics.

A registered Pulse handler can return `{done:false,postponeUntil:number,cursor?:unknown,commitPostpone:(tx:JobTransaction,current:BgJob)=>Promise<void>}`. The callback is a short DB-only domain update, never external work. It must be finite, strictly future, at most 30s after now, and ownership fenced. Runtime reacquires `withOwnership`, invokes `commitPostpone` (which uses `withOrgCoreTransaction` for its domain count/time write), restores bookkeeping role, atomically writes cursor/due time, status queued, clears lease, increments generation, and returns without another loop. Other handlers cannot opt into this result by name accident; test explicit registered family support. Domain `attemptCount`/nextAttemptAt and bg-job due time update in that SAME runtime-owned transaction through `commitPostpone`; do not write them as independently committed facts. Existing result shapes remain source-compatible. Postponement is admitted only for handlers registered with explicit Pulse retry support, not every arbitrary handler returning a similarly named field.

Extend execution with a monotonic deadline/`remainingMs()` or equivalent immutable budget observable by handlers. E's 30s call must not be clamped by the current generic 25s step cap: selected runtime passes the remaining selected budget, while legacy global tick retains 25s. Pulse admission requires its full external bound plus bounded local settlement allowance within the remaining tick budget. A callback deadline is enforced with AbortSignal, not only while-loop checks; loss is not proof remote work stopped.

## Proposal contract

D supplies proposal `revision`, `decidedAt`, nullable `ownerProfileId` and nullable immutable internal run/policy/input/result binding. D's list/count/detail/recent readers restrict bound-owner rows even for another same-org profile; unbound informational legacy rows retain existing org access. D approval response includes `{proposalId,revision,decision,receiptId?,dispatch?}`. E consumes that view without changing approve/dismiss meaning.

E implements `insertInternalPulseProposalTx(tx, scope, input): Promise<{cardId,existing}>` in new `src/server/services/pulse-publication.ts`. The handle is the same domain transaction already nested in `JobExecution.withOwnership` via `withOrgCoreTransaction`. Input binds org/owner/run/policy/input/result hashes, immutable content hash, and stable `internal:dependency-digest:v1:` logical key. Same complete binding/content returns the existing card; mismatch throws and rolls back; never overwrite a decided card. D does not implement a speculative duplicate helper. E owns reserved-ingress rejection when it introduces internal publication.

Immutable revision means: user-editable pending executable content increments revision; decisions freeze the reviewed content; internal digest content never changes in place. E feedback references the immutable revision and must reject stale content. No extra general version-history table is required; frozen dispatch/run snapshots retain exact reviewed content.

## Tick and cancellation seam

D creates `pulse-tick.ts` and `/api/pulse/tick` plus cron-auth allowlist. It imports dispatch registration explicitly and runs only trusted configured owner/org/family. E extends this same route/service to collect due sources first and add digest family while retaining 50s total. Query parameters never select org/type. D's scoped cancellation service takes an existing transaction to cancel queued dispatch and bump matching job generations; E extends it for digest/admission collection rows after stacking. `user.service.ts` membership deletion and policy reconciliation call it; each worker also rereads authority before admission/publication.

No mutable runtime policy object changes identity during a tick. Freeze config revision once, then compare current revision before each write. Disabling or owner revocation fences active job and collection generations; admitted external effects remain evidence, never become replayable.
