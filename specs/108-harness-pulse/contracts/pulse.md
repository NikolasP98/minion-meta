# Pulse API, authority and dispatch contract

## Public authenticated routes

All browser routes use Supabase session, same-origin mutation protection, `requireCoreCtx`, Pulse capability and server-resolved personal-org check. Bound-owner read misses return 404. The existing `/api/pulse` write prefix and `/pulse` view/nav gates remain active; receipt read explicitly requires `pulse:view`, mutation `pulse:edit`. Field projection contains no tokens, raw provider errors or private payloads beyond the already reviewed owner content.

| Route | Input | Result / conflict |
|---|---|---|
| POST `/api/pulse/proposals/[id]` | `{action:'approve'|'dismiss',expectedRevision:positiveInteger}` | Stable decision projection and dispatch receipt for executable approve; 409 refresh-required for missing/stale executable revision or conflicting decision. Repeating identical approve by same owner/version returns existing receipt. |
| PATCH same | `{args:typedActionArgs,expectedRevision:positiveInteger}` | Updated pending proposal and incremented revision; 409 if decided/stale; no unconditional update. |
| GET `/api/pulse/proposals/[id]/receipt` | Path ID only | Current proposal revision/decision/decidedAt plus dispatch receipt/state/safe reason/remote ID if known; 404 outside owner/org. |
| Existing feed/count | Existing shape plus revision/owner-visible fields | Pending-only semantics; privacy filter shared with receipt readers. |
| Page recent decisions | `listRecentPulseDecisions(ctx,{limit,cursor})` | Keyset `(decidedAt,id)`, limit 1–50, same strict owner filter; no unbounded history fetch. |
| GET `/api/pulse/tick` | Exact `Bearer CRON_SECRET`; trusted configured owner/org only | Disabled/skipped or bounded selected advancement. Caller-supplied org/type/scope is rejected. No token in response/log. |

Unknown informational kinds preserve current non-executable decision semantics; they cannot gain dispatch by supplying a tool name. Legacy informational revision omission is allowed only through the same atomic pending-state transition; current UI always sends revision. A duplicate executable approval compares immutable action hash/actor/revision as well as status.

## Fresh authority and transport

Resolve server identity and target outside short SQL transactions. Before dispatch admission, transaction rereads organizations.kind/status, organization_members, member_roles/permission_rules, personal_agents, gateway lease/channel/ID and credential revision. Share `buildCapabilities` / `resolveMemberRoleKeys` semantics from rbac.service; cached `resolveCapabilities` alone is insufficient. Strict personal agent must already be active/bound, with canonical normalized agent ID; approval does not provision or repair it implicitly. Receipt exposes only safe IDs/status.

Add strict credentials/RPC option/helper in `gateway-rpc.ts`, used by both action preparation and worker. It requires explicit org/profile/channel/expected gateway ID and returns exactly that row's credentials; lookup/authorization error fails. It must not fall through to per-user alternate gateway, system credentials or environment. Existing other callers retain their current signature. Credential plaintext stays transient and never enters dispatch rows/logs.

Gateway qualification record is trusted deployment configuration, not client input: gateway ID/channel/endpoint, full source commit, exact build version, C binding-contract revision, verification evidence reference, expiry and enabled state. The CURRENT identity source is the authenticated existing `hello-ok.server` response: Gateway `src/gateway/server/ws-connection/message-handler.ts:1077–1078` emits `version` and `commit` (`GIT_COMMIT`). Add a strict transport preparation that opens the exact assigned socket, authenticates, validates nonempty exact version and full 40-hex commit against the qualified record, and exposes a one-shot dispatch closure plus close/abort. Missing/short/unknown commit, changed version, expired record, changed gateway ID/channel/endpoint/credential binding or reconnect invalidates preparation and rejects before `cron.add`. No semver-at-least check, cron probe, cached fleet guess or new wire field. Worker prepares this authenticated connection before the short admission transaction, rereads current assignment/config in that transaction, commits admission, then sends once on the SAME still-connected qualified socket; reconnect is not automatic. Approval also checks current qualification with a read-only connection before freezing its target. Qualification trusts the deployment-managed identity contract, not cryptographic remote attestation; a deployment with untrustworthy/missing GIT_COMMIT remains disabled. D tests a stub-qualified record; actual remote build qualification remains a deployment operation. C's [binding contract](../../107-harness-gateway/contracts/cron-binding.md) rejects explicit missing/deleted agent and cross-agent session at add/update/execution; omitted generic agent retains defaults.

## Action construction

`create_event` validates a frozen schema fixture taken from pinned Gateway `extensions/gmail-calendar/src/calendar-tools.ts` `CalendarCreateEventSchema`; store source commit and schema hash. Required title/start/end, real valid date semantics/end-after-start, optional fields only from installed schema, existing Pulse 16 KiB payload ceiling. A caller cannot smuggle gateway target, tool choice, template, or internal authority metadata. The schema's `approved` bypass flag is not accepted as client authority; preserve downstream configured approval: omit the `approved` bypass flag from server-authored arguments for this milestone. A subsequent tool approval prompt is not an execution receipt; no automatic confirmation call is added. Never report calendar creation from scheduling acceptance.

`reminder` is typed `{text,timezone,schedule}`; valid IANA timezone, future `at` time or supported bounded existing cron recurrence. Freeze the installed `CronScheduleSchema` revision, reject unknown keys/invalid dates, and cap text by the existing payload ceiling. Target agent/session/delivery are server fields. A server-authored fixed prompt names only the intended existing tool and wraps canonical JSON arguments as untrusted data; instruction-like text remains data. Existing tool authorization/approval stays enforced. Do not claim the LLM template guarantees one downstream tool invocation.

One-shot execution wrapper: explicit `agentId`, `sessionKey` (canonical origin), `scope:'session'`, `sessionTarget:'isolated'`, `wakeMode:'next-heartbeat'`, one-shot `at`, `deleteAfterRun:true`, typed server-authored agentTurn and `delivery:{mode:'none'}`. Send the flat job fields directly as `cron.add` params, as pinned Gateway `src/gateway/protocol/schema/cron.ts:200–212` requires `additionalProperties:false`; do not retain the current Hub `{job:...}` wrapper. Test actual serialized request through C's handlers. The actual isolated execution session is `agent:<id>:cron:<job>` and is not mislabeled as the origin session.

## Admission and outcomes

Approval transaction freezes decision and queues work; no RPC is inside it. Worker current authority check plus `queued→admitted` is atomic under `withOwnership`. After commit issue at most one cron call. Validate returned remote job ID before scheduled settlement. Any error after admission without definitive validated negative acceptance evidence is indeterminate; conservative handling may fence a definitely unsent post-admission crash too. Never infer retry safety from an error string containing or lacking “request sent”. Retry only before admission when no remote dispatch could have occurred; 5s/30s cap three.

Positive verified operator reconciliation may record remote receipt with actor/reason/evidence audit. No reset route; absence in cron.list, job deletion, canceled state or a guessed ID cannot prove no effect. Owner/policy revocation cancels queued work and fences job generation; admitted work retains evidence. Authorization linearizes at admission; generic accepted cron does not promise execution-time end-user revocation.
