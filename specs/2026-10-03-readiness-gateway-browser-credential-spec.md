# Gateway browser credential boundary

## 0. Product

Close GW-024: a linked ordinary user must be able to use the exact assigned gateway without receiving a platform/operator credential. Hub and Site browser sessions use short-lived, challenge-bound, target-bound tenant JWTs as the WebSocket credential. Static gateway bearer/password/device credentials remain server-side operator credentials for explicit platform, CLI and service use.

The user authorized the readiness security fixes. Implementation still requires this two-pass specification, independent source review, human merge, staged release and production credential rotation. Local qualification uses synthetic credentials only. No production secret is read, sent, rotated or tested by this work.

## Out of scope

- Redesigning every Gateway operator credential or removing supported CLI, native device, Paperclip, service-account, Tailscale or trusted-proxy authentication.
- Treating `connect.client.id`, client mode, platform, browser user agent or network location as an authorization fact. They are self-asserted or transport context.
- Redesigning the operator/service-account method matrix. This slice adds a separate default-deny tenant-JWT matrix, migrates every current Hub browser caller into it or behind a canonical server broker, and may not widen the existing operator/service paths.
- Solving arbitrary browser XSS. A stolen tenant JWT remains sensitive, but it is short-lived, one target, one tenant, one canonical actor and never platform root.
- Claiming the finding closed when code is merged. Every static credential previously reachable from Hub or Site remains exposed until its production gateway and every server-side consumer have rotated and the previous value is proven rejected.

### Observable authority bypass

1. Hub's POST token endpoint verifies the active organization and a non-admin's `user_gateway` or legacy `user_servers` link, then decrypts and returns the gateway's static credential as `{ token }`. The link authorizes gateway use; it does not turn the linked user into a platform operator.
2. Hub's main browser client always supplies that token. A Hub JWT is additive and best-effort. Fetch failure sends the token alone. JWT rejection sets `jwtAuthDisabled`, reconnects with the token alone and restores the full unscoped operator path after a cooldown.
3. Gateway `resolveJwtAuth` intentionally maps token, password, Tailscale and trusted-proxy authentication without JWT to role `admin`, `operator.admin`, and no user/org. This remains legitimate for a real operator who holds that credential. It becomes an escalation because Hub gives the same credential to an ordinary linked user.
4. Site selects `servers.token` into member layout page data, stores it in browser state, submits it to Gateway, and includes it in the input that `/api/device-identity/sign` signs. That signing route also accepts browser-supplied role, scopes, client id and client mode rather than deriving them from canonical authority.
5. Hub's terminal sends the shared credential as the `/pty` WebSocket subprotocol. Hub plugin pages post the same credential to plugin iframes as `host:hello.authToken`, even though the host bridge already supports parent-mediated RPC.
6. Server-side Hub transport uses the same static credential for two different trust classes. `gatewayCall`/`gatewayCallToInstance` are platform operations; `gatewayCallAsUser` also sends the static token and optionally adds a JWT. The latter falls back from per-user to system and environment credentials.
7. Current tenant JWTs contain user, role, agent IDs and organization, but no target gateway or challenge. The unbound `/api/gateway/jwt` route takes no target. Gateway's early shared-auth/device gate runs before tenant JWT resolution, so a JWT alone cannot currently establish the browser connection.
8. `connect.client.id`, mode and platform are provided by the caller. They cannot distinguish a browser that has stolen a token from a CLI or service holding the same token.

## TO-BE

### D1. One explicit credential class per connection

Gateway classifies a connection from verified evidence, before pairing or client publication, into exactly one of:

1. `tenant-jwt`: signed Hub issuer credential, with mandatory subject, JTI, expiry, organization, canonical target gateway, purpose and challenge nonce;
2. `service-account`: exact configured service-account key, retaining only its configured role and agent assignments;
3. `operator`: configured token/password, paired device token, or an explicitly configured operator trust path such as trusted proxy or Tailscale;
4. unauthenticated: rejected.

A tenant JWT is a complete credential, not identity decoration on a static bearer. JWT-only browser admission must work without `auth.token`, password or device pairing. Presence of the `jwt` field owns admission before service-account or operator matching. An empty, malformed, expired, revoked, wrong-target, wrong-challenge, incomplete or unverifiable JWT rejects the handshake even if another credential is also present. A service-account or operator frame must omit `jwt`; its token is considered only when the field is absent. There is no retry/downgrade from a rejected JWT to token-only authority.

Gateway advertises `gateway-tenant-session-v1` in `connect.challenge.payload.authPurposes` only after the strict validator, local canonical identity and revocation store are ready. `authPurposes` contains at most eight unique ASCII tokens of at most 64 characters. The additive shared runtime and declaration contract makes the field optional for older consumers. New Hub and Site clients require the exact token and send the new JWT without a static bearer; absence produces a typed upgrade-required state. They never attempt legacy auth.

If a no-downtime rollout is required, a separate root-owned `legacyAdditiveJwtUntil` timestamp may be enabled for at most 24 hours around caller cutover. Before that absolute deadline only, a JWT with no `purpose` claim may enter the old additive path after its signature, issuer, audience, expiry and legacy required claims validate; it still requires the old operator token and retains the old authority semantics. A JWT declaring `purpose: "gateway-tenant-session-v1"` always enters the strict new validator, and any failure rejects without legacy or token fallback. A malformed/unverifiable JWT never enters legacy classification. The flag is disabled immediately after Hub/Site cutover and cannot be extended in place; a new reviewed maintenance window is required. Coordinated maintenance with no overlap is permitted and preferred.

The deadline alone cannot distinguish an old token-only browser from a real operator. The cutover plan therefore updates every retained operator/service consumer, rotates the previously exposed static credential, and closes every socket authenticated by its old generation no later than the legacy deadline. If that rotation cannot complete, the release remains blocked; client metadata is never used as an ersatz browser denylist. Final browser frames contain no static bearer. Operator-only and service-account flows remain independently supported with the new server-held value; they are not selected from self-asserted browser metadata.

`connect.role`, `connect.scopes`, `connect.userId`, client id/mode/platform and display name never override the verified credential. Tenant scopes derive from the signed canonical role. The existing shared-auth proxy `userId` path remains an operator compatibility feature and is never used by Hub/Site tenant sessions.

### D2. Target- and challenge-bound tenant JWT

Add a versioned tenant-session JWT contract with these required claims:

- normal `iss`, exact configured `aud`, `sub`, `iat`, `exp`, and nonempty unique `jti`;
- `purpose: "gateway-tenant-session-v1"`;
- `userId`: canonical profile identity and equal to `sub`;
- nonempty canonical `orgId`;
- canonical Hub build `channel` for this row binding;
- strict canonical `role`;
- bounded, deduplicated `agentIds` for this actor on this target only;
- `gatewayId`: canonical Hub gateway-row UUID for this organization/channel binding;
- `physicalGatewayId`: root-adopted immutable physical Gateway UUID;
- `bindingRevision`: positive integer revision of the local physical-to-row binding set;
- `challenge`: exact current Gateway `connect.challenge` nonce, a lowercase canonical UUID generated by `randomUUID()` and exactly 36 ASCII characters.

The JWT lifetime is at most ten minutes. Clock skew allowance is at most 30 seconds. Claim strings are at most 256 Unicode scalar values; `agentIds` is at most 256 entries and each entry is at most 128 characters. Overflow, ambiguity, unavailable authority or an unmigrated target fails issuance rather than truncating or falling back. The tenant role is derived from current canonical authority: only a canonical global profile `admin` with current membership in the target organization may receive tenant role `tenant-admin`; every other active member receives tenant role `tenant-user`. Both are organization- and target-scoped. `tenant-admin` reaches only the enumerated tenant-admin methods in D7 for the signed organization and assigned target. It never receives `operator.admin`, pairing approval, host terminal, root config, fleet broadcast, credential rotation or another organization's agents. Organization labels, caller fields and client metadata do not become platform authority. A genuinely operator-owned bearer/device credential remains compatibility platform root; a canonical global administrator reaches retained browser management features only through the fresh server-brokered operations defined below.

Gateway has a root-owned immutable `gateway.multiTenant.physicalGatewayId` and a root-owned versioned binding set. Each binding is the exact tuple `{ gatewayId, orgId, channel }` for one canonical Hub gateway row. The adoption ceremony writes the physical identity and complete binding revision through the reviewed root-owned Gateway configuration/deployment path, reads them back from the exact physical instance, and records a nonsecret receipt before Hub enables issuance. One physical Gateway may intentionally hold several bindings for different organizations. One Hub gateway row may bind to only one active physical identity/revision, and a tuple may occur only once in a revision. The set is never derived from URL, connect fields, browser input or Site assertion.

Hub issuance loads the requested row's adopted physical identity and binding revision and signs both. Gateway admission requires `physicalGatewayId` to equal its local immutable identity and the signed `(gatewayId, orgId, channel, bindingRevision)` tuple to occur in its current root-adopted binding set. A valid tuple for organization A cannot authorize organization B, another row or a standby physical instance. Binding removal/revision advance closes affected tenant sockets and rejects old-revision refresh. The existing metrics/Hub REST legacy server ID is not reinterpreted as either identity; migration writes both the physical identity and each canonical row binding explicitly. Missing, duplicate, stale or cross-bound adoption is a typed unavailable state rather than a compatibility fallback.

JWT validation is part of the startup-owned user/auth subsystem. It receives the current lifecycle abort signal and a finite deadline. After every asynchronous JWKS, revocation or user-subsystem wait, the handshake rechecks that admission remains open before any pairing write, presence update, client publication, `onAuthenticated` callback or background provisioning. A paused authentication is included in the existing P1 drain and cannot publish after shutdown or generation replacement.

### D3. Fresh issuance authority in Hub

Replace unbound `GET /api/gateway/jwt` and browser token retrieval with one target route, for example `POST /api/servers/[id]/session-credential`. Its body is at most 1 KiB and contains only the current Gateway challenge nonce, using the exact lowercase 36-character canonical UUID schema from D2. All other identity, organization, channel, target, role, scopes and agent inputs come from server state.

Direct Hub and Site-broker issuance share one durable canonical-user/target rolling-minute limiter. Admission uses a short reservation so concurrent server instances cannot each observe spare capacity:

1. in one transaction, take a transaction-scoped advisory lock for the canonical `(userId, gatewayId)` pair, use the database clock, delete at most 500 expired reservation/issued rows, count all `reserved` rows whose 15-second deadline is live plus all `issued` rows created in the prior 60 seconds, reject at 30, and insert one random reservation id with state `reserved`;
2. commit before key loading/signing. No network request or cryptographic work runs while the lock is held;
3. on signing failure, delete that exact reservation in a new bounded transaction. A process crash conservatively consumes capacity only until its 15-second reservation deadline;
4. after signing, atomically change that exact live reservation to `issued` with the database timestamp. If this finalization fails or the reservation expired, discard the in-memory JWT and return `503`; never return an uncounted credential; and
5. retain issued rows for at least 60 seconds and at most five minutes. Store no JWT, challenge or signing material in the limiter.

Lock acquisition/query time is at most two seconds and each transaction at most three seconds. Capacity returns bounded `429`; unavailable, timed-out or corrupt authority returns `503`. There is no process-local fallback. Retries after an ambiguous HTTP response consume another slot because the prior signed credential may have been delivered.

The route:

1. requires the authenticated Hub user and active organization;
2. resolves the path id to a canonical gateway UUID and requires that gateway to belong to the active organization;
3. resolves the request's current server-side build channel and current `(org, channel)` lease; when a lease exists, the requested target must be its live holder;
4. freshly confirms canonical active organization membership and the current gateway link for an ordinary user. Preserve the existing platform-admin-in-active-org policy only where it is already explicit; an admin cannot bypass target organization ownership;
5. loads the canonical role and only the agent assignments valid for this exact target;
6. signs the exact challenge and canonical target; and
7. returns only `{ credential, expiresAt, gatewayId }` with `Cache-Control: no-store`, never the static credential.

A missing canonical gateway bridge, stale lease selection, inactive/removed membership, removed gateway link, target mismatch or authority outage returns a bounded typed denial/unavailable result. It never tries a legacy Turso link to disclose a token, never chooses the first gateway or organization, and never falls back to system/environment credentials.

The issuer remains server-only. No signing key, gateway operator secret, Site exchange key, session cookie or raw provider error enters a response, log, Sentry event, browser storage, HTML or cache. JWT/JTI telemetry uses bounded hashes or stable nonsecret IDs.

### D4. Hub browser and secondary caller cutover

The main Hub `GatewayClient`, its auto-reconnect path and its backup/cutover client request the tenant credential inside `onChallenge(nonce)` and send `jwt` only. Remove JWT prefetch that cannot bind the live challenge. Missing/denied/unavailable issuance, Gateway JWT rejection, refresh rejection and target/identity changes fail closed with a typed UI state. They never call `fetchHostToken`, set `jwtAuthDisabled`, reconnect with `auth.token`, or reuse a credential for another host/org/user/challenge.

Integrate with the reviewed session lifecycle work:

- capture user, active org, target gateway and lifecycle generation before the issuance await;
- recheck them before returning the challenge response and before authenticated-session publication;
- call `onAuthenticated` exactly once for the current client/session;
- fence stale open/close/event/hello callbacks and pending bootstrap work;
- a backup client may be promoted only after its own JWT-authenticated `hello-ok` and current-generation check;
- losing the candidate leaves the old connection only while its own credential remains current and authorized; it never manufactures a token fallback.

JWT refresh uses a Gateway-issued, canonical-lowercase-UUID, one-use, 30-second refresh challenge bound to the active connection and lifecycle generation. Each connection has exactly one live refresh nonce; replacement atomically revokes the prior nonce. Redemption compare-and-clears it before any signing-key, revocation or authority await, and failed validation never restores it. Close, expiry, shutdown, generation replacement and binding revocation clear it. The nonce lives on the bounded connection record rather than an independent global collection. Hub signs it for the same actor/org/physical target/row binding. `auth.refresh` permits no identity, organization, physical target, gateway row or binding-revision switch; it may update the freshly authorized role/agent set and retains the existing workshop-room reauthorization behavior. A definitive denial closes the client. Network ambiguity may leave the session only until its current JWT expires. Gateway enforces connected-socket expiry and durable JTI revocation.

Every Hub static-token browser consumer is removed:

- main/reconnect/backup WebSocket clients use the tenant credential;
- `/api/servers/[id]/token` returns a permanent bounded gone/not-supported response and never decrypts a token;
- the current `/pty` implementation is explicitly a host terminal: it launches the Gateway host login shell in `HOME` with the Gateway process environment. A tenant JWT, including `tenant-admin`, can never mint or redeem a PTY ticket. Any future tenant shell requires a separate isolation specification and implementation;
- to preserve the current global-administrator terminal UI without exposing the platform bearer, Hub adds a server-only `platform-terminal` broker. It freshly requires the canonical global-admin profile, active membership in the selected row's organization, exact current row-to-physical binding, live Gateway lease holder, and a root-adopted `platformTerminal` entitlement for that physical Gateway and credential generation. The entitlement states plainly that the resulting shell has host-level platform authority. Removal or revision advance denies new tickets immediately;
- the broker uses the server-held operator credential on a dedicated operator RPC to request a single-use, 32-random-byte (exactly 43 base64url characters), at-most-30-second PTY ticket. Gateway binds the ticket to the canonical actor, exact `physicalGatewayId`, binding revision, operator credential generation, broker request id and current lifecycle generation. It returns only the ticket and expiry to the browser. Hub never forwards the operator credential. Issuance permits at most two live tickets per canonical actor/physical target, 1,024 globally, ten per actor/target per rolling minute and 1,000 globally per rolling minute; saturation rejects before allocation. Redemption atomically claims and deletes the stored SHA-256 digest before any authority await or process spawn, so concurrent redemption has one winner. Expiry, entitlement removal/revision, credential-generation change, lifecycle-generation retirement and shutdown invalidate it. Cleanup scans at most 500 expired entries per pass, and a generation floor keeps delayed physical deletion unusable. `/pty` accepts this exact platform-terminal ticket or an independently authenticated operator/device credential; it never accepts a tenant JWT or platform bearer from browser code;
- plugin iframe `host:hello` removes `authToken`. Plugins use the existing parent-mediated RPC bridge and inherit the parent JWT connection's Gateway authorization. Direct iframe WebSocket fallback is unavailable rather than receiving any bearer;
- browser host state, props, page data, postMessage payloads, local/session storage and error text contain no platform credential.

The bridge protocol change is versioned. Old plugin UI that requires `authToken` receives a clear upgrade-required state, not an empty-token direct connection or shared-secret fallback.

### D5. Site browser exchange and session adoption

Site member layout returns server id/name/URL and assigned agents only. It never selects or serializes `servers.token`; `memberState.serverToken` and token-based member connect are removed.

Site obtains the same Hub-signed target/challenge tenant credential through a server-to-server broker. The browser request is at most 2 KiB and may contain only the selected assigned target id and current Gateway challenge; both are untrusted selectors that the server re-resolves:

1. the Site route derives the current authenticated user and active organization solely from `locals`; body/query fields cannot name a user, org, role, scopes or agents;
2. Site signs a 30-second, one-use EdDSA workload assertion with a dedicated Site server key. It includes issuer `minion-site`, audience `minion-hub-gateway-session-exchange`, key revision, JTI, the authenticated Site user id, active org id, exact target and Gateway challenge. It is sent server-to-server over TLS and never returned to the browser;
3. Hub pins the Site public key/revision, atomically claims the assertion JTI before signing, maps the Site identity to one canonical profile (`supabaseId` directly or the unique canonical `legacy_user_id` bridge for Better Auth), and independently re-runs the D3 membership, target, link, role and assignment checks;
4. an absent/ambiguous Better Auth bridge, missing active org, invalid session/assertion, unknown key revision or canonical mismatch fails closed. There is no first-org, global server, environment or raw-token fallback;
5. only the resulting tenant JWT returns through Site to the authenticated browser.

The replay claim is a durable Hub row keyed by `(issuer, key_revision, sha256(jti))` with the assertion expiry and no raw assertion. In one transaction, Hub takes the global replay-cap advisory lock and then the issuer/revision lock, uses database time, deletes at most 500 oldest expired rows, checks both caps, and inserts the unique JTI row. Rows are retained for five minutes past expiry. Admission is capped at 5,000 live rows per Site key revision and 50,000 globally. Lock acquisition/query is at most two seconds and the transaction at most three seconds. A full, locked, corrupt or unavailable store returns bounded `503` before tenant-JWT issuance; a duplicate returns bounded denial. After the JTI claim, Site issuance uses the same canonical-user/target reservation protocol and 30-per-rolling-minute capacity as direct Hub issuance. Failed authority or signing does not make the consumed one-use Site assertion replayable. No process-local cache can satisfy replay or rate authority.

Key adoption/rotation is server-side and reviewed: old and new public revisions may overlap for at most 15 minutes, every accepted revision has its own pinned public key and cap partition, private keys remain only in Site secret storage, and an old revision is rejected after the overlap. A symmetric gateway token is not reused as the Site workload credential. Assertion, exchange and tenant-credential responses are each at most 16 KiB; redirects, HTML and oversized/non-JSON responses fail closed.

Site's current device-sign route is not an alternate admission path. Remove/retire it after the member client cutover; it must not sign caller-provided token, role, scopes, client id or mode. If a later device proof is required, its own specification must derive every claim from the authenticated canonical session and bind the proof to the Gateway challenge and target.

The Site client preserves the reviewed shared-client `onAuthenticated` lifecycle: exact once for the current client/session, stale event/close/hello fencing, failed initial authentication feeding bounded auto-reconnect, and complete timer/host/auth-scope teardown. Reconnect always obtains a fresh challenge-bound credential and never replays mutations.

### D6. Server-side RPC trust separation

Freeze and classify every Hub Gateway caller before refactoring:

- `gatewayCallAsUser` is user-delegated. It resolves only the exact current target URL, obtains a challenge-bound tenant JWT for the supplied canonical actor/org, sends no static token, and fails if actor, organization, target or gateway link is unavailable. It cannot fall back to a system gateway, environment token or another channel.
- `gatewayCall` is an explicit platform operation. Its call-site inventory is reviewed method by method; it may use the server-held operator credential and must never accept browser-supplied actor/org as authority.
- `gatewayCallToInstance` remains an explicit fleet/platform operation addressed to a reviewed instance and server-held credential.
- Organization provisioning, shell access/readiness, artifact reads, Pulse actions, channel sync and plugin listing use the appropriate classified path. Existing user-delegated calls that currently pre-mint an unbound JWT move to the challenge callback and exact target.

Use distinct client telemetry labels for server platform and user-delegated calls, but labels do not grant authority. Platform token/password/device flows remain unscoped admin by design. Only when the `jwt` field is absent are service accounts matched before operator-token resolution. If `jwt` is present, the tenant-JWT branch owns the frame and a valid service or shared token cannot rescue any JWT failure. An exact no-JWT service account retains its configured role/agent IDs and never falls into a missing-user legacy-admin broadcast path. Paperclip/OpenClaw adapters, CLI, native device clients and local service operations retain their reviewed operator/service credential flow.

### D7. Gateway method and HTTP boundary

The Gateway tenant-JWT path is a distinct credential role and never calls the current `mapRoleToScopes('admin')` or enters the generic `operator.admin` bypass. `src/gateway/auth/tenant-method-policy.ts` is the runtime source of truth generated/checked against the Hub manifest above. It exports the exhaustive method/role/parameter policy and an event-audience policy. `authorizeGatewayMethod` branches on verified `authMethod === 'tenant-jwt'` before the operator ladder; any method or parameter form absent from the tenant policy is denied. `tenant-admin` contains the `tenant-user` set plus only the extra rows above. Direct handler checks remain mandatory: the central allowlist cannot make an unscoped handler safe. CI ratchets the policy against every registered core and plugin method and invokes each handler with cross-org, unassigned-agent and missing-selector fixtures.

The path keeps `orgId`, `userId`, assigned agents, JTI, expiry, physical target, gateway-row binding and credential generation on the published client. Required-claim or revocation-state failure rejects admission. Connected JWT clients close on expiry, exact JTI revocation, binding removal or credential-generation retirement. `auth.refresh` repeats target, revocation and lifecycle checks and cannot change identity/org/gateway. Broadcasts use a separate default-deny tenant event manifest; every admitted event is filtered by exact org and, where applicable, assigned agent/session before serialization. Current admin-only debug, approval, pairing, config, credential and fleet events never reach tenant sockets.

`/pty` uses only the D4 platform-terminal ticket or a separately authenticated operator/device credential. A tenant JWT cannot request or redeem it, and caller-declared role/client metadata cannot select the platform path. Plugin iframe traffic stays on the parent's authenticated RPC connection and is constrained by the same tenant method policy. Any other browser-facing HTTP/WS endpoint that currently consumes the platform bearer is in the checked-in caller manifest and either validates the tenant JWT with the same target/revocation policy or uses a named server-brokered one-time capability. Static source discovery and a runtime network trace prove no browser request carries the operator credential.

Origin allowlists and secure contexts remain defense in depth. Tailscale or reverse-proxy location is transport context, not ordinary-browser authorization. An operator-owned client may still deliberately use those configured trust paths.

### D8. Previously disclosed static credential rotation

Code deployment does not invalidate credentials already delivered to browsers and plugin iframes. The rotation authority is the physical Gateway identity, not an individual Hub row. Every row in one root-adopted physical binding set shares one operator-credential generation and therefore belongs to one indivisible rotation cohort.

For every physical Gateway ever reachable through Hub or Site:

1. freeze the complete current binding revision and inventory by nonsecret `physicalGatewayId` every bound Hub/Site row across organizations and every static copy/consumer: Gateway root config or secret manager, canonical Hub encrypted gateway rows, legacy Turso server rows/fallbacks, Vercel/bootstrap environment fallback, Hub platform RPC, Gateway-to-Hub machine REST config, Paperclip adapter, CLI/service deployment and every other registered operator client;
2. provision one new high-entropy credential and monotonic generation for the physical cohort through a root/operator-owned channel. The exposed old credential alone cannot authorize its replacement. Store no plaintext in the ledger, logs, tickets or shell history;
3. before cutover, publish the sealed new value plus generation and fingerprint to **every** retained bound row/copy/consumer as an inactive next-generation slot. Every copy is read back through its owning server/operator boundary and must match the same physical fingerprint/generation. The Gateway continues to accept only the old generation during staging. A missing row, mixed fingerprint, late-added binding or consumer that cannot hold the staged generation blocks cutover;
4. remove stale PG/Turso/environment fallbacks so lookup cannot resurrect the old value. Server consumers select a credential by the root-authenticated physical generation advertised during their server-side challenge, never by URL or browser data;
5. under the maintenance gate, atomically advance the physical Gateway once to the staged generation. That single advance makes the old value invalid for every bound row and closes every connection authenticated with the prior token/password generation, including old Hub/Site tabs, plugin sockets, platform-terminal tickets and PTY sockets. All prepared consumers then activate the matching staged slot. If a consumer activation or verification fails, repair forward with the already staged new generation; never roll the Gateway or any row back to the exposed value. A binding-set change during cutover aborts before advance or starts a new reviewed cohort revision;
6. from an isolated trusted verifier, prove every bound organization/row reaches the same physical generation through its intended platform path, the old credential is rejected by Gateway and Hub machine-auth paths, no old-generation socket/ticket remains published, and Hub/Site tenant JWT paths work without either value; and
7. record physical identity, complete binding revision/row set, credential generation/fingerprint, affected consumer revisions, timestamps and bounded pass/fail receipts. Never record the credential. Retain the prior nonsecret generation/fingerprint and cutover evidence for audit.

The release test includes two organizations bound to one physical Gateway: both new copies must exist before the one generation advance; an omitted or mismatched row blocks it; the advance closes old-generation connections for both; and a post-advance repair can only move the missing consumer forward. All linked users and old open tabs are treated as having received the prior value. Rotation covers every affected physical Gateway, not only one row observed in the synthetic proof. GW-024 remains `implemented-awaiting-release` until every cohort ledger is complete and independently reviewed.

### D9. Error, logging and privacy contract

Public failures use bounded classes such as `gateway_session_denied`, `gateway_identity_unavailable`, `gateway_upgrade_required`, `credential_exchange_unavailable`, `token_expired` and `token_revoked`. Invalid JWT details, JWKS bodies, DB/provider messages, static tokens, tenant JWTs, workload assertions, session cookies, PTY tickets and device signatures never appear in UI copy, logs, analytics, Sentry metadata or close reasons. Log nonsecret gateway/org/user IDs only when the existing telemetry policy permits them; otherwise use bounded hashes.

No code path returns a static credential length or value to a normal request. Credential write/rotation endpoints return only generation/fingerprint receipts and are restricted to existing reviewed platform-admin authority plus exact target ownership.
