# A20 Gateway and Hub cron binding

## Existing fields and semantics

Use current `cron.add` / `cron.update` fields; no public wire addition. `CronJob.sessionKey` is the origin namespace for reminder delivery/wake routing (`src/platform/cron/types.ts:103`), while isolated execution intentionally uses an agent-owned `cron:<jobId>` session. Preserve this isolation; canonical origin binding and execution session are distinct evidence.

Group D supplies explicit nonempty personal `agentId`, canonical origin `sessionKey`, `scope:'session'`, `sessionTarget:'isolated'`, typed `agentTurn` payload, `delivery:{mode:'none'}` and its exact selected gateway credentials. `delivery:none` alone is not a guarantee against arbitrary downstream tool actions; existing permissions remain. D never uses an implicit default owner, universal scope, or ambient credentials.

## Validation and execution

Add one current-config binding validator callable by actual add/update and execution paths. An explicit nonempty agent ID must match a configured agent after existing ID normalization; unknown/deleted values fail with a safe invalid-binding error, never default. Reject explicitly supplied empty/whitespace-only `agentId` and `sessionKey` before normalization can delete them. This is a new presence-preserving validation requirement, not a claim about the current schema. Explicit null in add retains the current API meaning of an omitted optional field; explicit null in update retains the current API meaning of clearing an optional field. D never sends null. A supplied canonical session must belong to the effective agent and must not be `global`; cross-agent values reject rather than rewriting to main. General callers with omitted ID retain the current default-agent behavior and valid session aliases. D always sends canonical `agent:<id>:...` form.

At the actual `src/gateway/server-methods/cron.ts` add/update boundary, validate raw binding presence in the object selected by the existing `src/platform/cron/normalize.ts` unwrap logic before lossy string normalization; retain the original invalid value for schema rejection or return INVALID_REQUEST. Apply the same invariant to direct service callers before `service/normalize.ts` drops optional values. Omitted fields and valid legacy aliases keep their current meaning; add-null retains omission/default semantics, and update-null retains clearing semantics. At add, validate the effective normalized record before store mutation. At update in `src/platform/cron/service/ops.ts`, clone the full stored job (including nested state/payload/delivery/schedule), apply the patch to the candidate, then validate under the store lock before replacing the live job or persisting. Never mutate the stored object before validation. Rejected effective patches leave both in-memory state and disk bytes unchanged. Reject changing agent while retaining another agent's session. Preserve the already-public optional `scope` field through `service/jobs.ts:createJob` and `applyJobPatch`, including persisted reload; explicit `scope:'session'` must not disappear. Omitted scope retains its existing default and allowed universal behavior. At execution, reload current config and validate explicit binding before workspace/auth/provider/tool setup; repeat on main-system-event and isolated-agent paths, including direct isolated runner entrypoints. Deletion after admission records a failed/skipped invalid-binding outcome and zero provider/tool invocations. Omitted-ID jobs preserve default behavior. Existing explicit invalid jobs are inventoried/reported; do not silently rewrite stored jobs.

Isolated execution uses the validated agent and existing isolated session construction, and preserves the validated origin session on the stored job for routing. Test both against two-agent fixtures; a success receipt's execution session must be in the same agent namespace. `scope:universal` remains a general-cron feature; D rejects it for Pulse. A bound explicit session must still be validated even if universal routing would otherwise discard it. Scheduled acceptance remains distinct from actual execution and cannot promise execution-time user RBAC revocation after generic job acceptance.
