# Canonical admission and durable receipt contract

## Canonical source and authority

Use installed source type `TransportSourceProvenance {version:1,sources:readonly CanonicalTransportSourceUnit[]}` from `src/plugins/types/hooks.ts`. Read inbound and received `event.metadata.sourceProvenance`; received context fields are `channelId`, `accountId`, `conversationId`, `agentId`, not guessed `chatId`. Carrier comes only from authenticated channel intake. RPC JSON and flow `meta`, `runId`, `nodeId` or receipt strings never create trusted provenance.

Source key is the versioned ordered tuple `[1,channel,accountId,rawConversationId,providerMessageId,providerRevisionOrNull]`. Preserve exact provider text/caption, including whitespace; never hash trimmed, composed envelope or merged batch text as the original. `sourceHash = SHA256(canonical source snapshot)` includes exact source bytes and stable provider attributes. Store separately `inputHash = SHA256(canonical effective classifier input)` and `policyHash = SHA256(effective prompt, rubric, categories, language, schema, requested model and policy revision)`. Object keys use stable lexical ordering; ordered arrays retain order. No hash or raw text enters general analytics.

Stable admission tuple is `[1,authorityNamespace,watcherPolicyId,sourceKey,reevaluationGeneration]`. It excludes current model/rule hashes. `authorityNamespace` is the stable local gateway state-store/account namespace, independent of mutable org ownership. Pin current sorted org ownership IDs separately in the admission snapshot, or explicit local-gateway authority for a genuinely unscoped account; missing/ambiguous resolution is not treated as a new authority. Use the source-qualified watcher authority adapter below; the existing fail-open helper pair alone is insufficient. Recheck that bound ownership has not changed before dispatch/settlement. A later reassignment changes the authority check, never the admission key, and does not authorize old-owner replay. Stable configured watcher policy ID is `alert-watcher:default` within this namespace for current single plugin configuration; both channel/agent subscriptions share it. A distinct future policy requires a distinct explicit ID, never inferred from config hash.

Look up admission key first. Exact redelivery resumes frozen snapshot. Same stable source identity with changed original bytes yields `identity_conflict`; it cannot overwrite or recall. Verified provider edit revision changes source key. Explicit authorized reevaluation increments generation and links the prior receipt with actor/reason; ordinary config changes do not. No customer-facing reevaluation/retry RPC is added. Local operator retirement/reevaluation must use current owner checks and retain audit evidence; no automatic retry for indeterminate requests.

Certification: Telegram producer raw+received+debounce fixtures only. Other raw hook adapters may normalize structural fields but remain uncertified unless producer evidence proves identity/original units. Idless/unqualified/flow calls use fresh invocation identity and baseline behavior, excluded from cross-hook dedup and A30. Existing legacy flow gate behavior remains a separate compatibility path. Watcher dedup cache may cache completed receipt identities only; pre-call seen marking is removed from certified hooks.

### Source-qualified watcher authority

Implement a narrow `extensions/alert-watcher/src/authority.ts` adapter returning `{kind:"scoped", source:"db_mirror"|"json_config", orgIds, evidenceHash}` or `{kind:"local_unscoped", source:"json_config", evidenceHash}` or `{kind:"unavailable", reason}`. Bind channel/account, source mode and sorted owner IDs in the work snapshot; evidenceHash covers only authority fields, never credentials. Mutable refresh timestamps establish freshness but are not replay keys. Re-read current config/source evidence before admission, each dispatch, received-state local materialization and recipient settlement; unavailable or changed ownership/source mode fences publication and new effects, while terminal usage/effect evidence is still retained. It never creates a new admission key.

Use actual `orgScopeSource()`, `getMirrorEntry()` and `mirrorMeta()` from `src/gateway/channel-mirror.ts`, and installed channel registry/config adapters at execution boundaries. In DB scope mode require an exact channel/account mirror entry, matching type/account, a valid nonempty org ID, enabled projection and a successful snapshot timestamp no older than the existing five-minute mirror interval (300000 ms; future/absent timestamps fail closed). A miss, malformed/null ownership or stale/unavailable snapshot returns unavailable, with no fallback to `channels.accountOrgs`. Existing hydration retains last-good data on empty/failing refresh; an old snapshot must not remain valid indefinitely. This is a bounded cache observation, not a claim of instantaneous DB revocation; this change neither adds remote hydration nor alters general channel fallback behavior.

In JSON scope mode require an actually registered/enabled/configured account at the exact channel/account plus an own-property `channels.accountOrgs[channel][account]` array. A nonempty valid string array is scoped; an explicit empty array is local-unscoped. Missing/malformed mapping, missing account or ambiguous normalized aliases is unavailable. Account enumeration alone is insufficient: Telegram `listTelegramAccountIds` can synthesize `default`; require a real channel config section with exact account configuration (or configured top-level default) and its `resolveAccount`/`isConfigured`/enabled evidence. Never persist credentials. Apply existing plugin/org enablement to a successfully resolved scoped result; an empty/missing list from `resolveAccountOrgIds` is not proof of unscoped authority. Preserve uncertified/manual legacy behavior separately.

Tests use DB mirror miss with stale JSON org A, mirror reassignment A→B, stale last-good mirror, malformed/null ownership, absent JSON mapping/account, and a valid installed JSON account with explicit `[]`. Run these through actual certified hook admission and received-state settlement, asserting zero new provider calls/publication on unavailable/changed authority and retained terminal accounting.

## SQLite data model

Add only `classification_work` and `alert_delivery_receipts` to alerts.db. Use SQL CHECKs, unique indexes, prepared parameters and short `BEGIN IMMEDIATE` transactions; never hold a DB transaction across await. Read/claim/update helpers take the exact owner and expected generation; no unfenced generic update helper.

`classification_work`: UUID; authority namespace; policy ID; stable source key/hash; explicit reevaluation generation and optional prior work ID; immutable policy/input hashes; bounded nullable raw snapshot; state; leaseOwner/generation/expiresAt; attemptCount (0..3); nextAttemptAt; admitted/received/completed times; bounded terminal SDK result/usage; cost status and coverage; safe error; source-counted and first-confirmed-sent markers with original acceptedAt; optional complaint ID; immutable reply-flow snapshot/binding; suggestion subreceipt; retention/redaction and namespace-retired markers. Unique stable admission tuple and unique computation key derived from bound admission/input/policy. SQL checks require admitted timestamp/attempt identity for admitted/indeterminate, retained terminal response or redaction marker for received/completed/failed-after-response, and failed state for invalid results rather than negative classification.

`alert_delivery_receipts`: UUID (also queueId); work ID/result revision; normalized channel/account/recipient identity plus hash; delivery policy/hash; immutable bounded nullable payload/hash; state; lease owner/generation/expiry; admission/settlement times; queue generation and bounded provider receipts; safe reason; redaction/tombstone metadata. Unique `(work,resultRevision,deliveryPolicyHash,recipientIdentityHash)`; scoped parent binding must match. `sent` requires positive provider/queue evidence; `indeterminate` requires admitted timestamp/reason. Never cascade-delete admission tombstones with complaint rows.

Bounds: raw input/config snapshot <=64 KiB; terminal SDK result <=64 KiB; suggestion result <=16 KiB; recipient payload <=64 KiB; safe error code <=128 characters; capped attempt array <=3 records with no raw prompt/error stack. Validate byte bounds before persistence/dispatch. Oversized required snapshot terminates with explicit failure, never truncates classified source bytes. Existing transport-level limits still apply.

### Classification transitions

| State | Authorized next action |
|---|---|
| queued | Claim due work under one current owner/generation and revalidate authority; commit admitted attempt before provider dispatch. |
| admitted | Persist bounded terminal SDK result/usage as received under matching generation; after process death/expired ownership, mark indeterminate, never recall. |
| received | Validate/materialize locally without classifier call; negative → completed; SDK/schema-invalid → failed with cost preserved; positive awaits bounded suggestion disposition then atomic complaint/recipient materialization. |
| failed/canceled/completed/indeterminate | Terminal, no automatic provider call. Only positive evidence reconciliation or explicitly authorized new reevaluation can create a distinct outcome. |

Proven pre-dispatch transient failure may return queued under persisted attempt cap and due time; retry at 5s then 30s, maximum three dispatch attempts. Failure after provider invocation is conservatively ambiguous unless the adapter proves no external request occurred. SDK `NO_API_KEY` before any candidate request can qualify; generic network exception cannot. Max attempts exhaustion fails. A stale generation cannot publish, settle, release a successor lease or append another attempt. Persist supplied terminal SDK error before watcher-local validation; SDK already validates output, so raw pre-validation provider text is not promised.

Dispatcher: one active classifier per plugin instance, poll 5s, lease30s, renew10s, scan<=10 due candidates/tick. Actual SQLite claim independently repeats due/state/generation predicates. Lease loss aborts cooperatively and prevents local completion; abort is not proof remote stopped. Stop waits boundedly for local settlement then closes DB; new start recovers using persisted states. Retention work is bounded within the same lifecycle.

### Suggestion and delivery transitions

Suggestion subreceipt is `not_requested|queued|admitted|received|indeterminate`, with one attempt ID, frozen input/model, times, bounded result and known/unknown usage. Admission precedes one invocation; received result is persisted before recipient payloads. Ambiguous admitted recovery records indeterminate and uses `suggestions:[]` plus `suggestionsUnavailableReason`; known errors also degrade to explicit empty suggestions. Neither case recalls automatically. Positive classification remains valid.

In one transaction: materialize complaint and recipient rows from frozen intended recipients and final suggestion disposition. Current recipient permission is checked before queue admission. Destination authorization uses the trusted current configured destination set, normalized channel/account/recipient and unchanged ownership binding; it never uses an envelope string as a grant. Config changes cannot redirect old work. Revoked queued recipients cancel; prior admitted execution has only best-effort revocation.

Delivery protocol:

1. Under receipt lease/generation, commit `queued→admitted` with its UUID queueId and exact payload/recipient hashes.
2. Call existing `deliverOutboundPayloadsWithOutcome` with `durability:'required'`, `queueId`, `completionPolicy:'caller'`, the persisted `callerRetention` guard below, frozen channel/account/to and payload. Actual exported signature must be used; do not substitute runtime channel direct-send helpers.
3. Inspect typed provider/durability/uncertainty outcome. Commit sent/failed/indeterminate and provider receipts in SQLite under the owning generation. A receipt is sent only with accepted provider evidence; a suppressed payload alone is not a delivered alert. In the first confirmed-sent transaction, also settle cooldown and the idempotent pending reply described below. Provider-complete with pending caller acknowledgement is a known send, not a reason to resend.
4. Only after SQLite settlement call `acknowledgeCallerManagedDelivery(queueId,stateDir)`. Preserve minimal queue identity tombstone when payload bytes are removed.

Recovery acquires the existing queue entry lease, reads actual entry/generation, verifies queueId/channel/account/recipient/payload binding, and reconciles matching terminal accepted evidence. Pending safe entries continue through the existing queue recovery path under its lease and the persisted expiry guard, never a fresh enqueue. Missing/mismatched evidence after SQLite admission becomes indeterminate. Uncertain payloads stay withheld. Queue success followed by SQLite failure retains terminal queue bytes. SQLite success followed by acknowledgement failure retries only acknowledgement. No provider action is duplicated to resolve uncertainty.

Reuse the current provider checkpoint protocol: `deliver.ts:1095` durably checkpoints each payload `pending→in-flight` before any provider call; `checkpointQueuedPayload` increments generation/attempt and `writeEntryAtomic` fsyncs/renames. `deliver.ts:1139–1159` checkpoints accepted evidence after success. After death between these boundaries, `markRecoveredInFlightUncertain` (`delivery-queue-store.ts:219–239`) converts in-flight to uncertain and generic recovery (`delivery-queue-recovery.ts:144–153`) withholds replay. This already handles send-success/crash-before-terminal; no second queue or new provider-attempt service is needed. Preserve this ordering and require real subprocess kills immediately after the stub accepts but before accepted checkpoint, after accepted checkpoint but before SQLite settlement, and after SQLite settlement but before caller acknowledgement. Checkpoint failure or ambiguous provider outcome remains withheld, never reset pending merely because a process exited.

Count each admitted canonical hook source once toward existing window semantics and persist the marker with its admission. Reconstruct relevant window state from bounded receipt timestamps on restart. Stamp cooldown once in the transaction settling the first confirmed sent recipient; later settlements do not restamp. Restore cooldown from persisted first-sent timestamps after restart. Legacy flow gate has its existing behavior and no certified delivery promise.

### Preserve owner reply materialization

The certified hook path must retain existing `index.ts:788–800` → `reply-flow/store.ts:insertPending` → `reply-flow/handle-reply.ts:handleOwnerReply` behavior. Extend existing `pending_replies` additively with nullable `receipt_binding` (SHA-256 of work/result identity), `payload_expires_at` and `redacted_at`; a partial unique index on non-null receipt_binding guarantees one row. No third work table. A new keyed helper in `extensions/alert-watcher/src/reply-flow/store.ts` uses insert-on-conflict/read-and-verify for certified work; legacy unbound callers keep their old insert behavior.

Freeze reply-flow enablement/window, complaint ID, origin channel/account/chat, original intended owner destination strings, final suggestions and language with the work. On the first positively confirmed recipient settlement, the same short SQLite transaction writes the sent receipt, once-only firstSentAt/cooldown and keyed pending row if reply flow is enabled and has valid authorized destinations. Set created_at from that queue receipt's persisted acceptedAt, and expires_at to `min(firstSentAt + frozenWindowMs, payloadExpiresAt)`; recovery never starts the window at recovery time. Later recipients/repeated recovery cannot insert another row, replace suggestions, reset the window or clear claimed/forwarded/redacted state. A bound row with conflicting immutable values quarantines the local materialization instead of overwriting it. Queue acknowledgement follows this entire transaction.

If already expired or required payload was redacted, retain the settled sent receipt and a closed/redacted reply binding, never reconstruct an open reply from hashes. `findOpenPendingForSender`/`claimPending` exclude expired/redacted bound rows; preserve existing owner selection parsing, first-claim and forwarding semantics. Two-recipient tests plus crash/restart prove exactly one local pending row, stable expiry, no lost confirmed-send reply integration and identical selection interpretation through actual `handleOwnerReply` with stubbed forward transport. This does not claim exactly-once forwarding by the legacy reply handler or redesign it.

## Retention, legacy cutover and retirement

Default raw source/SDK/suggestion/recipient payload retention is seven days from the frozen work admission, never seven days from retry/recovery. The bounded dispatcher redacts at most ten due records/tick while running; admission rejects work whose retention workload cannot fit its configured bound. A stopped process cannot promise physical deletion on time. The enforceable restart rule is that expired bytes cannot be reused or dispatched, even before watcher startup. Queued work missing required expired snapshot cancels; admitted uncertain work retains minimal identity/state without reconstructing payload.

Persist an opt-in `callerRetention` object through `QueuedDeliveryParams`, `QueuedDelivery`, `parseV2` in `delivery-queue-types.ts`, `delivery-queue-store.ts:createQueuedDelivery`, `deliver.ts` parameters and recovery context:

```ts
{version:1, owner:"alert-watcher", namespaceHash:string, receiptId:string,
 payloadHash:string, recipientHash:string, expiresAt:number}
```

Hashes are lowercase SHA-256, receiptId equals the preallocated queue UUID and expiresAt is a positive safe-integer UTC millisecond deadline bound to the work snapshot. Require `completionPolicy:"caller"` and exact payload/recipient/namespace binding; partial, malformed or unknown guard versions quarantine/fail closed rather than strip the guard. These fields are internal queue metadata, not public authorization. Existing unrelated entries without this opt-in retain current behavior; no previous watcher queue entry is invented during migration.

Under the existing entry lease, check the guard before generic recovery considers terminal/pending work, again after any backoff, and in the actual resumed/initial send path before `pending→in-flight` and each provider invocation/chunk. The latter uses the persisted entry's guard, not a caller-supplied replacement; retain the lease through dispatch. A payload crossing the boundary during hook/adapter preparation cannot send. Expiry after a provider call began cannot undo it: stop new chunks, abort cooperatively where supported and keep accepted/uncertain evidence. No plugin lookup or running watcher service is required to enforce this persisted deadline.

On expiry, first atomically/fsync write the minimal retained tombstone under that lease, then redact/unlink queue payload, mirror, routing-address and error copies; tombstone checks in enqueue/read/recovery prevent a surviving raw file from sending even if cleanup crashes. Preserve queue/payload IDs, binding hashes, generations, original acceptedAt and accepted/uncertain disposition plus bounded receipt hashes so SQLite can reconcile known effect evidence. Pending with no possible effect becomes expired/canceled; in-flight or uncertain remains indeterminate, never falsely unsent. Tombstone/write failure blocks dispatch; physical cleanup retries without sending. Bridge recovery reads matching tombstone evidence, settles known sent state without reopening an expired reply, and never reenqueues a tombstoned ID.

Cleanup inventory includes new work/result/suggestion/recipient snapshots, queue payload/mirror/error files, optional usage copies, existing `complaints.content/summary/chat_id/from_sender` and bound `pending_replies` origin/destinations/suggestions/reply_text/claimed_by copies. Retain minimal receipt/claim disposition and identifiers/hashes, not raw text/addresses; set redacted markers and safe empty placeholders for existing NOT NULL columns. Reads never expose redacted copies or make them actionable. Legacy unrelated/manual rows keep their existing policy; receipt-bound rows obey this contract. Test actual generic recovery with an unredacted expired watcher file before starting the plugin and while disabled, expiry during backoff/pre-send and between chunks, tombstone/cleanup fsync failures, unexpired watcher delivery, and unrelated legacy caller compatibility. All expired pre-dispatch cases must record zero provider calls.

Add a narrow queue tombstone path under its existing state directory: minimal queueId, payload/recipient binding hashes, settled/uncertain disposition and retirement time, no raw body/address. Queue enqueue rejects a retained tombstone ID; recovery never sends tombstone entries. Atomic filesystem write/rename/fsync and entry lease protect redaction/acknowledgement; generic callers retain current policy. SQLite and queue tombstones survive until the bound source/policy replay namespace is explicitly retired. Retirement first blocks new admission for that namespace, then permits owner-scoped deletion; deleting raw payload is not retirement.

Old complaint rows lacking recipient history get `legacy_unreconciled` disposition, retain visibility, and never enter the new recipient queue. Pause/fence old boot catch-up before enabling dispatcher. Migrate twice safely on a disposable old schema; do not invent sent receipt from notified_at alone. Rollback leaves old fan-out disabled and preserves receipt/tombstone readers. No reset-to-queued for admitted/indeterminate work.
