# POS plan operation identity (HC-035)

Status: Standards PASS and final whole-contract Spec PASS. Implementation authorized by the all-findings scope; independent implementation review remains required. Owners: root server/database; Hub client worker controller/UI.

## 0. Product

When opening a payment plan returns an uncertain result, a clerk can check exactly that operation without opening a duplicate agreement or adopting another clerk's identical agreement. Recovery needs the existing create permission only.

## AS-IS

`PlanOpenForm.svelte` issues one POST and updates the cart through a callback. A connection failure does not establish whether the transaction committed. `createPlan` inserts a random ID and atomically links a booking, but stores no caller operation identity. The collection GET requires `pos:view` and returns a bounded page, so enumeration/body matching cannot establish ownership or absence.

## TO-BE

1. Optional UUID `operationId` is additive to POST. The UI freezes one UUID and canonical payload per submission. It never retries a POST after an unknown result. Existing callers without a key retain current behavior.
2. Forward migration adds nullable `operation_id uuid` and `operation_hash text`, a paired-null/64-lowercase-hex check, `operation_id IS NULL OR created_by IS NOT NULL`, and partial unique `(org_id, operation_id)` where the ID is not null. Existing rows remain null. No historic row is rewritten; no RLS policy or role grant is widened. Install the additive migration before serving the new application.
3. Keyed requests require the authenticated `ctx.profileId`. Persist `created_by` from that authority, never a caller-supplied actor override. Within `withOrgCore`, acquire a transaction advisory lock derived from the org plus operation UUID; collisions may serialize but cannot change identity. Then read the key under the same transaction and RLS scope. An existing row with the same actor and immutable request hash returns its original checked plan; a different actor or payload receives generic 409 `operation_conflict`. No booking relink or settings lookup runs on this replay path.
4. Hash a deterministic versioned object of normalized request intent: null-normalized client IDs/product/booking/note; trimmed nonempty title; exact rounded principal decimal as currently accepted; validated stable date-sorted due schedule with exact decimal amounts; explicit canonical currency when supplied, otherwise a distinct omitted marker. Normalize UUIDs consistently. Hash excludes presentation name and the operation ID itself. A settings currency change must not change an omitted-currency retry's identity. Persisted plan changes such as cancellation do not change the hash.
5. For a new keyed or legacy plan, obtain/validate configured currency only after an existing-key/tombstone lookup misses. Read settings through an in-transaction helper using the SAME locked `withOrgCore` transaction, never a nested call to `getPosSettings(ctx)` or pool hop. A replay/cancel path performs zero settings reads. Insert the key/hash and plan, plus the guarded booking link, in one transaction. Booking failure rolls both back. Advisory locks release with transaction; partial uniqueness remains the storage backstop. Operation ID/hash are internal persistence fields: define an explicit public plan projection which strips both from every plan-returning service/route, including create/list/detail and booking/account facets. Response regressions must assert neither field is serialized.
6. GET `/api/pos/plans/operations/[operationId]` requires authenticated org context, enabled POS module, explicit `pos:create`, a valid UUID and a profile ID. It returns exactly `{plan:{id}}` on same-org/same-actor hit or 404 for absent/foreign identity. All success, absent and error responses carry `Cache-Control: private, no-store`; a cached absence must not conceal a later commit. It performs no mutation and exposes no money, client identity or document body. POST also explicitly checks `pos:create` as defense in depth. Permissions are rechecked at recovery time.
7. Client controller is a separate rune module with a bounded deadline, immutable org/user/scope generation, and late-result fencing. A successful POST or exact lookup hit invokes the original cart callback once, then reconciles the original global action. Callback failure preserves committed identity and allows callback-only repair. Lookup absence/failure leaves unknown blocked; it does not invite replay. UI disposal/org change ignores late completions. Input drafts are frozen while unresolved. Local read repair does not create an ever-growing global action list.
8. Resolve a never-committed intent through explicit POST `/api/pos/plans/operations/[operationId]/cancel`, also guarded by `pos:create`, active POS, org and authenticated actor. Add an exact anchored operation-UUID/cancel POST rule in `apiWriteCapability`; the current central hook otherwise classifies this path as `pos:edit` and rejects a create-only clerk before the route runs. Do not broaden unrelated plan mutation authority. Under the same advisory lock, an existing own plan returns `{status:'committed',plan:{id}}`; the UI must repair it rather than abandon it. Otherwise insert an immutable cancellation tombstone and return `{status:'cancelled'}`. Retries of an own tombstone return cancelled. Other-actor identities return generic409. All responses are private/no-store. This is cancellation of admission only, never cancellation of an existing agreement or money.
9. Forward DDL also creates `pos_plan_operation_cancellations` with `(org_id,operation_id)` primary key, nonnull authenticated actor UUID and timestamp. RLS uses the existing org-GUC policy and app_ledger receives only SELECT/INSERT; no app UPDATE/DELETE. POST create checks a tombstone before inserting under the shared operation lock and rejects it with409 `operation_cancelled` without any other effect. Tombstones have no automatic expiry: a delayed original POST can never outlive the cancellation fence. Unrelated plans and legacy callers remain unchanged. Native two-connection create-vs-cancel tests must prove either one committed plan with the same returned ID or one tombstone with zero plan/booking effects; never both.

### Durable client continuation

10. Keep persistence separate from transport. plan-open-persistence.ts owns exactly one versioned localStorage slot for each authenticated actor/org pair; plan-open-operation.svelte.ts owns transport deadlines, action attention and callback repair. Derive both the storage key and Web Lock name from the canonical page.data.user.id and page.data.activeOrgId opaque IDs. Every initialize, admission, stage update and clear runs inside an exclusive navigator.locks.request for that pair and re-reads the slot after acquiring the lock. Every lock acquisition receives the current bounded owner AbortSignal. A timeout, scope change or disposal before acquisition produces a visible fail-closed result, executes no lock callback and sends no request; the callback also rechecks the signal before touching storage so a late implementation callback has no effect. Lock, storage, serialization or byte-identical readback failure produces a visible fail-closed state before any POST. Never hold the lock across a network request.
11. The version-1 record contains only: version; actorId; orgId; operationId; stage prepared, unknown, committed_refresh, continuation_pending or continuation_applied; the frozen POST intent; optional planId; and one continuation union. The frozen intent contains null-normalized partyId, crmContactId, bookingId and product references, trimmed title, checked principal, the omitted-versus-explicit currency state, validated stable date-sorted due rows and note. The account continuation contains kind account plus the originating client key. The sell continuation contains kind sell, partyId, bookingId, an exact ordered preCart, and an optional exact ordered postCart, using rows with productId, product kind, raw quantity, unit-price and discount drafts, plus bookingId, redemptionId and planId. It never stores customer name, document, phone, email, product label or tender details. A due schedule is capped at 365 rows, a sell continuation at 250 cart rows, and the complete UTF-8 JSON encoding at 131072 bytes. Exceeding a count or byte bound visibly blocks before creating a UUID, writing storage or dispatching a request. Corrupt JSON, an unsupported version or an actor/org mismatch is never deleted automatically and blocks admission with recovery guidance. Raw records, request intent, note and customer or product identifiers are never logged, toasted or sent to telemetry; diagnostics may carry only the version, stage, encoded byte count and a fixed error category.
12. Admission is a compare-and-set under the actor/org lock. An existing slot always wins: the caller adopts its operation state and sends no create POST. Only an empty slot may receive a prepared record. The writer must read it back byte-for-byte before releasing the lock, then may dispatch exactly one POST for that operation. A storage event promptly freezes another tab's matching form, but submit still re-reads under the lock, so simultaneous tabs cannot both admit. There is no local expiry, age-based eviction, overwrite or second pending plan for the same actor/org.
13. Remount and reload hydrate visible plan fields from the frozen request instead of current defaults. Account repair may run only from the original client key in the same actor/org; another account view shows the pending origin and stays locked. Sell repair first compares the ordered minimal preCart with the live cart. A mismatch cannot silently adopt, discard or replace either cart. The clerk must explicitly choose a restore-pending-sale action and confirm replacement of the live cart; reconstruction resolves each productId against the current sellable projection. A missing or inactive product keeps the operation blocked with a visible error. An org or actor switch detaches the old UI owner and leaves its slot unchanged.

    After create acknowledgement or exact lookup, persist and verify planId with committed_refresh before invoking any continuation. Account continuation is projection-idempotent: it must observe the exact plan in the originating account before it may persist continuation_applied. Sell continuation must stop relying on a later reactive effect. It obtains the exact created-plan instalment, derives and persists postCart with continuation_pending, then writes the canonical per-org cart localStorage value and reads it back byte-for-byte before updating the live cart and resolving the callback. Recovery accepts exactly three cart states: preCart applies postCart, postCart advances without applying twice, and any third state blocks for explicit clerk resolution. Once the exact target projection is visible, persist and verify continuation_applied before clearing. Thus a crash before planId, between the phase and cart writes, after the cart write, after callback completion or during deletion either resumes one idempotent transition or recognizes completion; it never restores an already-applied cart or repeats a create.

    The postCart instalment is a synthetic plan row, not a catalog sellable. The ordinary per-org cart loader must retain rather than discard a serialized row whose productId is exactly `plan:${planId}`. After loading the stored selected party, it reconstructs that row only from the authenticated account projection when the plan belongs to that party, remains open, and its exact current instalment amount matches the stored quantity, unit price and zero discount. A wrong client, missing or closed plan, unavailable projection or changed amount blocks checkout visibly and preserves the serialized cart for repair; the eager cart-persistence effect may not overwrite it with an empty cart. This projection-backed loader remains sufficient after continuation_applied and operation-slot deletion, so a reload restores the exact instalment without the durable operation record.
14. Clearing is another compare-and-delete under the lock and succeeds only when the stored operationId still matches. Before fetch invocation, a locally proven no-dispatch validation, bound, lock or persistence failure may compare-delete only a record this owner just admitted; any uncertainty retains it. After dispatch, the only create response that proves no plan effect and permits clearing is the authenticated own-operation operation_cancelled 409 backed by the server tombstone. Every other 4xx, including operation_conflict, plus every 5xx, fetch rejection, abort, timeout, malformed success or stage-write failure retains the slot for lookup or explicit cancellation. Successful continuation requires verified continuation_applied; deletion failure is safe because recovery recognizes that phase and exact target projection, skips the callback and retries only the matching clear. Callback failure persists planId with committed_refresh or continuation_pending and permits callback-only repair without another create POST. Failure to persist a plan ID, phase or target projection never authorizes clearing: the original durable UUID remains recoverable through exact server lookup.
15. Lookup 404 is informational and leaves the slot intact. It exposes an explicit Cancel unresolved request action which POSTs /api/pos/plans/operations/[operationId]/cancel under the same scope, deadline and late-result fences. A committed receipt stores the returned plan ID and enters callback-only repair. A cancelled receipt compare-deletes the slot and resolves the original in-memory create action as definitively not committed. A rejected or transport-unknown cancellation keeps the slot; cancellation may be retried with the same operation ID, but the create POST may not. This server tombstone is the only safe disposition for a crash after prepared persistence but before a locally observable fetch. Time, 404, unmount, reload, tab close and scope change never dispose of the operation locally.

## DELTA and verification

- Pure canonical request identity cases: equivalent normalized input, changed payload, explicit/omitted currency, sorted schedule, exact decimals, malformed UUID/actor, settings-independent hash.
- Native PostgreSQL with actual forward DDL and app_ledger/RLS: two independent concurrent same-key requests produce one plan and same ID; changed payload/actor conflicts; two distinct operation IDs with identical body remain distinct; same key in other org is isolated; booking failure leaves no operation; cancellation followed by replay returns original; missing currency replay survives changed settings.
- Native constraints reject keyed plans without actor/hash and app writes cannot update/delete cancellation tombstones. Concurrent create/cancel serialization proves no delayed write after confirmed cancellation; replay cancellation is idempotent, and cancellation of a committed key returns the original plan without changing it.
- Route tests use actual capability policy and verify create-only recovery succeeds, view-only/no-profile/disabled-module rejection, 404 foreign operation, malformed key, exact minimal DTO, and POST gate. The exact cancel-POST central mapping gets create-only versus edit-only real-hook cases. An early narrow no-store hook covers all operation-route responses, including authentication/capability errors before the handler runs; actual full-hook tests assert those headers. Public plan responses never serialize operationId or operationHash.
- Mounted client production controller/component: POST committed but response lost, lookup found/404/failed, callback failure and callback-only repair, two clerks' identical payloads, original attention cleared only after exact completion, 140 read repairs bounded, deadline and late response, org switch/unmount, no duplicate POST.
- Persistence/controller tests use a contract-faithful Web Lock plus storage harness and two controller instances. They prove persistence and byte-identical readback precede fetch; a held lock times out with zero requests and its late callback cannot run; storage/readback failure sends no request; remount/reload adopts one UUID; simultaneous tabs and storage events produce one POST; actor/org slots remain isolated; corrupt/version-mismatched records fail closed; 365/250/131072 bounds hold at both edges; mismatched account/cart contexts cannot continue; explicit cart restoration requires the current product projection; and compare-and-delete cannot clear a replacement operation. Response tables prove only a locally known no-dispatch path or own operation_cancelled tombstone can clear; conflict, other 4xx, 5xx, timeout, abort, fetch rejection and malformed success remain pending.
- Continuation crash-cut tests stop after each durable planId, continuation_pending, cart write/readback, live-cart update, continuation_applied and compare-delete boundary, then remount. Exact preCart advances once, exact postCart never reapplies, a third cart state blocks, and a failed delete retries only deletion. The production sell callback does not resolve before both the actual cart replacement and byte-identical cart-storage readback.
- Sell reload tests delete the completed operation slot, remount from only the canonical cart plus selected-party storage, and reconstruct the exact open-plan instalment through the authenticated account projection. Wrong-party, missing, closed, changed-amount and failed projections preserve the serialized row, show a blocking error and never write an empty replacement cart.
- Cancellation tests cover an absent create becoming cancelled, create winning and returning committed, transport loss followed by same-key cancellation retry, other-actor conflict, crash immediately after prepared persistence, and late original create fenced by the tombstone. A lookup 404, deadline, unmount or scope change never clears local state.
- Re-run shared check, origin/master design debt gate, tokens, affected POS unit/native suites and hosted CI. Record migration rollout and rollback compatibility.

## Out of scope

No automatic retry of unknown writes; no client matching by body or collection enumeration; no financial charge or ledger change; no history repair; no authority expansion; no database migration against production in this work session. The old app can read the additive schema, but new app requires migration first. Reverting the app leaves operation columns/data intact.
