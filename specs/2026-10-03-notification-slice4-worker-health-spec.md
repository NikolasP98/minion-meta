# Notification Slice 4 — durable worker scheduling and truthful health

## 0. Product

Approved implementation contract. Implements Slice4/D5 of the approved notification platform. Depends on the accepted Slice3 catalog/outbox migration and APIs; it cannot claim production readiness until the real projector in Slice5 is registered and qualified.

## AS-IS and scope

Hub `eb6867db` has `/api/notifications/tick`, which authenticates CRON_SECRET, discovers all enabled legacy organizations and processes them inside the request. Its loop has no persistent worker identity, lease or heartbeat. Failures log raw exceptions and the route still returns aggregate success. `bg-runtime.ts` is a different job mechanism and its handlers, deadlines and generation semantics do not establish a notification worker. The separate adapter-node worker already has a graceful lifecycle in `src/server/worker-lifecycle.ts`; Vercel is a distinct deployment.

Slice3 adds immutable source events and indexed per-row outbox claims. It deliberately starts no loop and has no source-to-audience projector. This slice adds bounded row-state discovery, an organization scheduler, worker leases and health.

## Out of scope

It does not invent an audience, mark an event projected without its projection, send a message, change legacy tick behavior or deploy a worker. Existing legacy findings stay open until their replacement slices.

## TO-BE and ownership

A persistent adapter-node process may start this worker only when both DESKTOP=1 and NOTIFICATION_WORKER=1, outside build/prerender. Vercel imports start no timer, acquire no lease and publish no heartbeat. Reuse the compiled Hub server and its actual private environment/db modules rather than a second ad-hoc TypeScript interpreter. The bootstrap is idempotent per process and returns an owned lifecycle handle. It has one active scheduler tick, at most four active organizations and no unbounded in-memory work queue. The next tick is scheduled only after the previous tick settles. A failed startup produces finite sanitized telemetry and no healthy worker record. A bootstrap generation and AbortController are registered synchronously before the first awaited catalog or database operation; shutdown can therefore quiesce an incomplete startup.

A worker is runnable only when its installed catalog manifest is valid and it has the actual qualified projection adapter for that catalog revision. Importing a module, enabling an environment flag, receiving an HTTP tick, a dry-run fixture or a recent generic jobs heartbeat cannot establish this fact. Before Slice5, the production adapter remains absent and health reports `projection_unavailable`; a controlled qualification adapter may operate only in a marked disposable fixture and must not be admitted by production configuration. Source HTTP mutations request work only by atomically committing Slice3 event/outbox evidence. This slice adds no operator wake endpoint and no HTTP-driven background promise. The health route only reads.

### Durable control state

Add an organization-bound control row with organization FK, next_due_at, live owner UUID/generation, claimed_at, lease_expires_at, hard_deadline, renewal_count, last_completed_at and a finite result code. The row has one primary key per organization and forced RLS. All organization lease fields are null in idle state and complete in running state. Add a failure_streak integer constrained to0..4, last_failure_code from the reviewed finite vocabulary, and an optional last_success_at. Increment the streak only on a live failed completion, saturate at4, and reset it on a successfully completed page; busy/unsupported observations neither increment nor reset it. Persist next_due_at so process restart retains the same backoff. Lease generations are nonnegative bigint with checked arithmetic and no decrease. No browser/assistant/service role can read or write control rows directly. This is operational scheduling state, never a provider or projection receipt.

Source mutation APIs remain unchanged. They insert only their immutable event and outbox row; they never lock or update a shared organization scheduling row. Otherwise transaction A could prevent independent same-org transaction B from committing its event, defeating the Slice3 commit-inversion contract and adding contention to business writes. No backfill or timestamp-based adoption step is needed: every committed pending or processing row remains discoverable directly.

Scheduling control rows are created lazily by the coordinator after it discovers an eligible organization. A new event committed while an organization is processing remains in the outbox and is found on a later discovery pass. Idle/backoff timestamps may delay a future observation; they cannot erase eligibility. Source deletes, expiry cleanup and retention remain outside this slice.

### Discovery and privilege separation

A dedicated non-login/non-bypass coordinator role sees operational control rows and only the reviewed outbox organization/state/catalog/lease columns needed for discovery, never notification event payloads or business tables. Its intentional global control-table and column-restricted outbox SELECT policies are explicit and cannot be assumed by app_ledger, notification_worker, event trigger, browser, service or assistant roles. A narrowly trusted backend login receives the role only after transitive membership admission equivalent to Slice3. A worker organization transaction still uses the exact existing RLS worker wrapper and canonical organization GUC; discovery does not grant cross-tenant business reads.

Use the existing state-specific outbox indexes to seek distinct organization IDs without scanning all events of a hot organization. For each state separately, query `organization_id > last_org ORDER BY organization_id LIMIT 1`; after observing that org, the next seek uses `> observed_org`, skipping the entire prior organization's index range. Processing discovery deliberately does not filter lease expiry in this global seek, because expiry is not the first index key. Its exact organization/catalog expiry probe is a separate bounded indexed query. Use the same organization-scoped eligibility probes for supported pending catalogs. No DISTINCT/GROUP BY over all event rows, OR over states, or unbounded in-memory organization list is allowed.

Two durable discovery cursors, one per state, advance through organization IDs and wrap at the end. They are fairness hints only; every sweep wraps, and a late event in an earlier org is discoverable on the next sweep. Neither cursor references an event timestamp/ID or establishes consumed work. A seeded singleton cursor row, locked FOR UPDATE SKIP LOCKED, serializes the short discovery transaction; zero returned rows means explicit coordinator_busy. There is no new advisory key and no collision with Slice3's per-org advisory locks. Candidate organization control rows use FOR UPDATE SKIP LOCKED. Claim at most four organizations and inspect at most16 candidates per tick, with at most64 SQL statements and a3second monotonic admission budget. Stop admitting additional probes before that budget is spent, commit the observed fairness cursor and any already-admitted claims, and let later ticks continue. Each SQL statement has a timeout no larger than the remaining transaction budget, and lock_timeout is at most250ms. Query errors roll back the whole short discovery transaction and are typed unavailability, not empty health.

A control row's next_due_at prevents repeated empty/unsupported/error probes from creating a hot loop. Do not discard a newly discovered org because it lacks a control row: insert the row through reviewed coordinator authority, then claim with database time. A newly committed event waits for its next eligible discovery pass, including backlog and any bounded organization backoff; report observed pending age rather than claiming a fixed end-to-end latency. There is no pushed wakeup. Return bounded immutable organization lease receipts, never payloads. Native EXPLAIN with100000 rows, including one hot organization and many other organizations, proves index range seeks and exact-org eligibility probes. A removed index or reintroduced DISTINCT scan must fail the gate.

An organization lease starts at 30 seconds with a hard deadline at 60 seconds and at most one renewal to that deadline. Every organization renewal and completion compares owner, generation and live expiry. Persistent worker heartbeats use the separate global lease below. A stale lease cannot keep a process healthy, clear work, postpone another owner's work or write success. Reclaim increments generation and resets the whole lease tuple. Worker identity is a per-process random UUID; process restart never recovers authority from a previous process ID.

### Bounded processing and wakeup races

For each claimed organization, check live scheduler ownership, then invoke the actual Slice3 claim API and the registered projector within its own bounded transactions. Process at most one 250-event page per organization claim. Projector ownership remains the event's own lease; scheduler ownership is not authority to settle a stale event. No outer scheduler transaction spans projection or future network work.

After the page settles, finish the organization claim with its exact live lease. An indexed remaining-eligible probe decides whether another page remains. If so, the control row is immediately eligible for a later fair pass. If empty, set a short bounded next poll (at most5seconds). A new pending event that races this decision is discovered after that delay; no source watermark or cleared wake flag can lose it. Unknown future catalog rows remain pending with an explicit unsupported-catalog health flag and at most60seconds before a compatibility recheck. A busy event-claim result schedules a retry and is not recorded as a completed page.

A failed page retains source/outbox evidence and schedules bounded backoff of 5s, 30s, 2m, then 5m capped, with failure class only. It cannot mark an event projected, delete a pending row, advance a source-time cursor or retry an unknown external effect. Database outage prevents a success heartbeat. An overdue backlog is visible. Timezone/civil slots and their 100-slot/7-day catch-up ceiling remain Slice7; this scheduler does not fabricate civil-time work before that implementation exists.

### Lifecycle and health

Integrate the owned notification lifecycle with the existing worker's signal quiesce/drain sequence. Signal handling immediately prevents new discovery/claims and cancels pending timers. Every in-flight SQL operation and projection callback is retained until actual settlement; no Promise.race frees a slot early. Drain finishes before closing cache or PostgreSQL pools. A cancelled/replaced generation cannot publish late success. Tests exercise startup rollback, repeated install/shutdown, no-work shutdown and shutdown during a delayed query/projection. A production process never uses process.exit to hide an unresolved operation.

Expose organization-scoped health through a fresh `comms:manage` read: unsupported catalog, installed worker/catalog revision, last live heartbeat/completion age, pending age/backlog, finite failure code and runnable/degraded reason. Do not reveal global org counts, other organizations, bodies, destinations, account IDs or raw database errors. Counts/age queries must use reviewed indexes, bounded SQL timeouts and aggregation receipts; a read failure returns explicit unavailability, never zeros. The existing notification settings page consumes this health in this slice and visibly warns when no current runnable worker exists. The exact UI and legacy distinction are specified below; an endpoint alone is insufficient.

Sentry reports finite failure classes with rate limits and immutable release metadata; PostHog records only bounded lifecycle/health counts and durations with existing privacy controls. Monitoring failure cannot change transaction outcome, release capacity or hide an operational failure. No raw event/recipient data enters either service.

## Durable coordinator and persistent worker identity

Migration seeds two distinct singleton rows with a boolean primary key constrained totrue and schema_version fixed at1. Ordinary callers cannot insert/delete/reset these rows. Missing rows, an unknown schema version, invalid field tuples or exhausted bigint generations produce typed unavailability; runtime never repairs them by resetting history.

`notification_scheduler_cursor` stores pending_after_org UUID/null, processing_after_org UUID/null, next_state (`pending` or `processing`), and tick_generation bigint>=0. These are scan positions, not foreign keys or consumption positions. A deleted or empty organization remains a valid boundary. The short coordinator transaction locks this row with SKIP LOCKED and then locks/checks the worker singleton. Cursor updates, the next state, tick_generation increment and all admitted organization claims commit together. A crash before commit leaves all unchanged; a crash after commit leaves durable leases reclaimable. No separate cursor reservation transaction is allowed.

`notification_worker_runtime` stores the sole active worker's random process owner UUID, monotonically increasing generation, lease_expires_at, last_heartbeat_at, started_at, stopped_at, and immutable-for-that-generation build SHA, catalog revision/hash and qualified projector revision/hash. A valid release uses the existing validated commit-SHA convention; a package version or NODE_ENV is not build evidence. Qualified disposable builds record their exact artifact/source hashes separately and cannot be advertised as production release qualification. Idle/absent state has no live owner/expiry; previous bounded diagnostic identity may remain with a stopped/expired result. This singleton makes the four active organization ceiling global for this worker version. Other enabled processes are bounded standby candidates, not extra executors.

Startup can acquire/reclaim the global lease only after catalog/build/projector admission. Its initial lease is30seconds. One owned heartbeat loop runs at most once per5seconds and extends expiry to database now+30seconds only for the exact still-live owner/generation and unchanged build/catalog/projector tuple. A heartbeat cannot revive an expired generation. Healthy requires heartbeat age<=15seconds and live expiry; an idle worker can satisfy it without claiming an organization. Renewing this process-lifetime lease is intentionally different from the one-renewal/60second organization and event leases. Losing the global lease quiesces admission and signals the owned projector; late org/event publication still requires its own live lease. A stale process cannot resume by reusing its owner UUID: a new bootstrap creates a new random identity and generation.

A graceful shutdown releases only its exact live global lease after actual work drains and records stopped_at. A crash leaves the lease to expire. Global lease acquisition, heartbeat and release use dedicated bounded transactions. Native tests hold/release two competing sessions, prove idle health, expiry/reclaim, denial of old-generation heartbeat/completion, and persistence of organization failure streak across replacement.

## Discovery cadence and fairness

Each tick starts from persisted next_state and alternates pending/processing candidate seeks. Reserve up to8 candidate observations per state (16total), including empty/wrap observations. A state cannot consume the other's reservation. If one state reaches its reservation or wraps without a candidate, continue the other within its own reservation. The next state persists even when an earlier query exhausts the remaining statement/time budget. An observed candidate's cursor remains tentative until its complete bounded due/control/eligibility decision. A classified due=false, unsupported-only, busy control row or successful claim advances that state's durable cursor. Budget exhaustion before classification leaves its durable cursor at the previous classified organization, so the observed eligible candidate is revisited next tick without waiting for wrap. Wrap sets that state's cursor tonull and resumes from the lowest organization on the next eligible seek; it never establishes an end-of-stream marker. At most4 claimed organizations and64 SQL statements remain hard limits, including timeout-setting and final fencing statements; reserve final commit/fence statements before admitting another candidate. Before issuing a range seek, reserve the worst-case SQL statement cost of one complete candidate decision plus final fencing/cursor writes, counting timeout-setting statements and every supported-revision probe. Also require positive remaining monotonic budget. If time is consumed by an already-issued seek before classification, keep that candidate cursor tentative and stop; already classified skips/claims may commit after final fencing. A query timeout still rolls back the transaction. The next_state rotation may persist, but it cannot move an unclassified organization cursor. Partial discovery results never bypass live worker fencing.

The normal loop waits1000milliseconds after its previous tick settles. Empty/busy ticks use the same delay. Database failure uses 5s,30s,120s,300s capped plus bounded nonnegative jitter up to10percent; a successful DB tick resets this process-local outage sequence. Use monotonic timers for local scheduling and database time for durable leases/due dates. At most one tick and one heartbeat operation are in flight; both handles belong to the lifecycle. Cancellation clears waiting timers immediately. No retry uses a zero delay. Native and deterministic scheduler tests cover endless pending load plus expired processing work, cursor wrap and a new earlier org, an empty queue, coordinator busy, repeated SQL outage and recovery.

## Health schema, read role and bounded plans

Add immutable `enqueued_at` to the existing outbox as row-local queue provenance. For existing rows, adopt the joined immutable event.created_at; future trigger inserts use database clock time. This adds no shared organization lock or source API call. Make it finite/not-null and unavailable for producer, coordinator or worker UPDATE. Add partial indexes `(organization_id,enqueued_at,event_id)` for pending and processing health reads. Preserve the existing claim indexes and verify their native plans after migration.

Add `notification_health_reader`, non-login/non-bypass/non-inheriting, grantable only to the trusted backend owner after transitive membership checks. It can SELECT only the reviewed health columns on org control/outbox under exact-org forced RLS and the fixed worker singleton's operational fields. It cannot read event bodies, other organizations' control rows, cursor positions, claim/settle a row, or assume coordinator/worker roles. No browser, service, assistant, producer or event-trigger role gains membership. The coordinator may access only operational singleton/control fields and its existing reviewed outbox columns; neither role receives business-table authority. Revoke unexpected default ACLs on new objects and test exact column/function grants.

The health service uses the dedicated RLS pool, SET LOCAL health role and canonical org, statement_timeout3s, lock_timeout250ms and idle-in-transaction5s. No route runs a health read under the global coordinator role. Restore all connection state on success, callback failure and SQL timeout. The exact route is GET `/api/notifications/health`, with no arbitrary org/query selector, fresh `comms:manage` admission and no-store response. The settings loader uses the same authorized service. Errors return a fixed503 health-unavailable result, not zero counters; the existing editable rule list need not disappear when only health is unavailable.

For each of pending and processing, count a bounded indexed subquery with LIMIT5001. Return at most5000 plus a `lowerBound` flag when the sentinel exists; UI renders `5000+`, never an exact total in that case. Oldest enqueued time is a separate same-org/state index seek ordered byenqueued_at,event_id LIMIT1, so it remains exact despite capped count. Return age as a finite nonnegative database-clock duration with a future-time anomaly explicit instead of clamping a corrupted timestamp into health. Unsupported pending catalogs use the existing <=9 complementary indexed probes for <=8 supported revisions. A health response does not estimate p99 or queue completion time. Native EXPLAIN uses100000 same-org pending rows and mixed processing rows, proving bounded counts/oldest seeks/complement probes; remove the relevant index to demonstrate the regression gate fails. No COUNT(*)/MIN over an unbounded joined history is accepted.

Refactor `installWorkerLifecycle` into an idempotent process-owned registration returning a quiesce/drain/dispose handle. Preserve tracked HTTP requests and existing bg-runtime behavior. Duplicate install on the same emitter returns the existing owner rather than multiplying listeners; disposal removes only this owner's listeners after drain. Register the notification bootstrap generation synchronously before its awaited admission and add it to the same lifecycle. Signals abort startup, prevent timer/heartbeat publication, quiesce jobs/notifications immediately, then adapter-node shutdown drains actual request promises, background jobs and notification operations before cache/PG closure. Startup failure removes its own timers/listeners and releases only any lease it actually acquired. A late successful DB admission after signal must be awaited, fenced and released, never published as a running worker. No shutdown test may hide unresolved work with process.exit or a winning Promise.race.

Production admission has no runtime option to install a fixture projector. The fixture proves lifecycle behavior; it never certifies a production projector or send.

Show runnable, starting/absent, stale, catalog mismatch, projection unavailable and health-unavailable states with safe localized copy. Keep legacy rule editing available, but label that engine's delivery status separately as unverified until its actual tick/provider path is migrated and qualified. ## Standby and failed-admission observation

An enabled process that sees a live global lease becomes standby with exactly one owned cancellable timer and at most one acquisition attempt in flight. The database read returns a finite remaining-lease duration from database time. Schedule the next attempt after clamp(remaining,1000ms,5000ms) plus nonnegative jitter up to500ms. A recently released lease is therefore noticed by a later bounded poll; standby publishes no heartbeat or runnable claim. Database errors use the same5s/30s/120s/300s plus up-to10percent jitter outage backoff as scheduler admission. Cancelled standby never retries; signal cleanup clears its timer and awaits any actual acquisition. If a late acquisition succeeds after quiesce, release only that exact live generation and never install its heartbeat/tick handles. Compiled two/three-process fixtures prove busy standby, active crash, exactly one takeover after expiry, graceful-release takeover, repeated outage and shutdown while waiting.

Extend the seeded worker singleton with admission_generation bigint>=0, admission_owner UUID/null, admission_checked_at timestamptz/null, admission_code from a finite set (`catalog_invalid`, `catalog_mismatch`, `projection_unavailable`, `build_unavailable`, `startup_failed`), and separately bounded observed build SHA/null, artifact SHA/null, catalog revision/hash/null and projector revision/hash/null. The complete observation tuple is null before the first attempted admission; a recorded observation has canonical owner, finite time, incremented generation and finite code. Unknown source/build identity remains null; do not derive persistent-worker identity from the Vercel reader's build.

A failed process may publish this observation only through the coordinator's fixed admission-observation transaction: lock the singleton FOR UPDATE SKIP LOCKED, require no live worker lease, require database now at least30seconds after the last admission observation (or none), increment admission_generation with overflow checking, and atomically record the completed check's fixed tuple/code/time. The process must still own its current uncancelled bootstrap generation immediately before that write. No observation extends expiry, changes active-worker identity, publishes a heartbeat or claims an org. A concurrent healthy acquisition serializes on this row and prevents failed standby overwrite. A writer that loses the row lock or the30second observation window skips without queuing; it may recheck on its owned failed-admission timer after30seconds plus up-to3seconds jitter. At most one failed-admission check/write is active per process. An operational DB failure cannot be recorded as success and uses the outage cadence instead.

A failed-admission observation is current for90seconds, clearly labelled with its own checked time and artifact tuple. Health precedence is: matching live lease and fresh heartbeat => runnable; a live lease with stale heartbeat => stale; otherwise a current persisted admission observation => its finite degradation reason; otherwise a prior expired worker lease => stale; otherwise absent. Catalog compatibility is checked against the actual persisted worker tuple and the approved supported revisions; mismatches remain explicit. A web process cannot manufacture projection_unavailable just because it lacks worker-only modules. Health returns both last active identity and last admission observation only as bounded operational metadata, never arbitrary environment strings.

Native/compiled tests cover the seeded absent tuple, a real missing-projector admission observation, catalog/build mismatch, an artifact change, failed standby attempts against a healthy lease, observation contention/rate bounds, quiesce during a pending observation query, and recovery to a fresh live lease. A paused SQL operation that passed the final JavaScript generation check before a signal may finish its bounded failed observation; it cannot create live health. Drain still awaits it before closing pools. Add the cursor boundary regression: one eligible org observed just as the remaining time is exhausted plus a later org; the former is attempted on the next tick, while earlier classified skips retain their committed progress.
