# Formula column variables

## 0. Product

Let authorized users compose one custom column from ordered, named formula variables and format each value visually without changing its underlying numeric meaning.

## AS-IS

- `formula/contracts.ts` models one expression/AST/output/dependency list per formula. `custom-properties.service.ts` validates writes under an org/table graph lock, optimistic property version and catalog revision.
- `column-presentation.ts` v1 stores primary numeric formatting plus one external secondary property reference. `CustomPropertyManager.svelte` offers one expression; `ColumnPresentationEditor.svelte` edits those two display slots.
- `DataTable.svelte` derives accessors and local sorting from the property cell's scalar `effectiveValue`. External formulas reference one scalar descriptor per property. Bundles already resolve permitted formulas in batches.
- `CustomPropertyCell.svelte` preserves partial numeric content with one accessible explanation, neutral tone for incomplete values, one placeholder for wholly blank output, and legacy/error/restricted behavior.

## TO-BE: user flow

1. Formula column creation/editing shows column identity, then **Variables**, then **Formatting**, then combined preview. Manual text/number/select/date columns keep their current behavior in this confirmed formula-only slice.
2. Start with one formula editor, no required variable name. **Add variable** creates another editor and reveals editable names for all variables. Generate unique localized starter names; complex mode requires nonempty unique names. Simple/complex are derived from count, not separate modes that can disagree.
3. Each variable retains existing CodeMirror completion, scalar type inference and inline diagnostics against the permitted table/catalog sources. Variable names are formatting labels, not new formula symbols. No sibling-variable reference language is introduced.
4. Drag a variable to reorder display; provide keyboard-accessible move controls and announce the new position. IDs, expressions and formatting stay attached. Removing a variable removes its own formatting only. A visible **Value used for sorting** selector identifies the primary variable for complex columns; prevent removing the primary until another is selected. A single variable is always primary.
5. Formatting cards follow variable order and identify their variable by name; the simple case addresses its only variable without a name selector. Numeric controls retain auto/decimal/currency/percent, precision, currency symbol/code, percent scale and sign colors. Add normal/subtle emphasis for every scalar type. Non-numeric outputs use their existing type-appropriate display and expose emphasis only.
6. Preview renders outputs left to right with the same shared formatter as table cells. Editing any expression/config invalidates stale preview responses. Any invalid variable/name/format blocks save and points to that variable. Save persists one complete coherent snapshot.

## Frozen data and evaluation contracts

- Preserve FormulaRules v1. V2 is `{type:'formula', version:2, primaryVariableId:UUID, variables:FormulaVariableRules[]}`. Each variable has `{id:UUID,name:string|null,expression,languageVersion:1,ast,outputType,dependencies}`. Draft v2 omits compiled metadata. Do not duplicate primary compiled fields at the property top level; use shared primary/dependency helpers at legacy consumer seams.
- Variables count is 1..12. IDs are unique; primary ID must exist. Names have max 40 characters, trim before storage, and uniqueness is checked with NFKC normalization and lowercase. One variable has name=null; reducing a complex draft to one normalizes its remaining name to null on the explicit v2 save, preserving ID/expression/format. Complex columns require every name. Expressions retain existing length/node/depth/dependency limits and SQL allowlisting. No arbitrary SQL, HTML, CSS, or template execution.
- Formulas independently use the existing catalog, including external custom formulas' primary descriptors. They cannot reference sibling variables. External references target only primary variable nodes. Validate the primary dependency graph for true cycles, evaluate primaries topologically, then evaluate independent auxiliary variables against those primary results. Auxiliary dependencies participate in type/availability/archive validation but do not create false primary cycles: A auxiliary → B primary → A primary is valid. A primary → B primary → A primary is rejected. Author/preview compilation uses only actor-visible catalog sources. Under the existing org/table graph lock, re-read expectedVersion and catalogRevision, compile requested expressions from that visible catalog, and revalidate the complete canonical graph and transitive dependents, including hidden dependents, without serializing their identities. Submitted AST/types and projected snapshots are never trusted as canonical. Acquire the existing graph lock before row/version validation; reject a stale snapshot with 409 and retain the client draft for explicit refresh/retry rather than replaying a mutation automatically.
- Explicit formula/presentation mutations require catalogRevision plus expectedVersion for update; metadata-only omission preserves canonical rules/presentation. Reordering is a definition update, never a new property or a collection of child writes. One property consumes one custom-column quota slot and has one archive lifecycle.
- V2 presentation is `{version:2,variables:[{variableId:UUID,number:ColumnNumberFormat|null,tone:'none'|'sign',emphasis:'normal'|'muted'}]}`. Entry IDs are unique and belong to that same column. Missing entries use canonical auto formatting and no sign tone; primary defaults normal, others muted. Non-numeric outputs require number=null and tone=none. Existing money dimension/currency and precision rules remain. Formatting rounding never mutates numbers.
- Bundle cells add ordered `formulaVariables` with each variable's ID, permitted name, value and formula quality/currency metadata. Top-level `value`, `effectiveValue`, and `formula` mirror the stable primary variable. Dragging changes output order only, not sorting, exports, aggregates or references. Changing the explicit primary is validated as a possible property output-type change against all dependents.
- Preview v2 request is `{tableId,rules:{type:'formula',version:2,primaryVariableId,variables:[{id,name,expression}]},presentation?:ColumnPresentationV2|null,recordIds,propertyId?,catalogRevision}`; retain the v1 expression request. Response keeps existing top-level primary `outputType/dependencies/diagnostics/rows` and adds ordered `variables:[{variableId,outputType,dependencies,diagnostics}]`; each row retains primary `result` and adds ordered `variables:[{variableId,value,formula}]`. Variable diagnostics carry `variableId` regardless of display order. Optional presentation is validated against the inferred variable outputs before execution, and the UI formats with that same draft. Preserve existing row/record access checks and request limits. No per-cell or per-variable HTTP requests.
- Aggregate budgets across one property are 256 AST nodes,64 distinct dependencies and 50000 units under the existing deterministic SQL expansion metric, in addition to existing per-expression limits. Sum the same expansion measure used by formula-sql.ts before compilation, rather than introducing an incomparable rendered-byte count; every currently legal single v1 expression must fit one-variable v2. Reject complexity with a stable error before database execution. Preserve existing record caps and chunk SQL so each statement evaluates at most 500 variable/record pairs. Tests include 12 individually legal expressions whose aggregate exceeds the cap.
- The owning property version remains its CAS version. Bundle/evaluation fingerprints include every referenced source version/availability and the permitted catalog revision, including legacy presentation secondary dependencies; changing a referenced label/type/archive/version cannot retain stale adapted expressions or values.
- Partial numeric results remain visible but cannot receive success/danger tone. Show one accessible partial explanation per composite cell; do not repeat Partial text. Explicit errors and unavailable/restricted states remain understandable. If every output is blank, render one placeholder. Formatting never turns a failed or restricted result into a numeric success.

## Permissions and non-destructive compatibility

- Existing module/record/field permissions guard catalogs, previews, bundles and all definition mutations. A restricted primary hides the column as today. A restricted non-primary is removed from serialized rules, values, formatting and analyses; set `variablesRestricted:true` without exposing its ID/name/expression/dependencies. Canonical storage is unchanged. Visible but archived/unavailable/type-drifted dependencies remain represented with explicit diagnostics/repair state; only restricted variables are redacted. Mark redacted definitions as restricted so a projected snapshot can never overwrite hidden canonical fields.
- Callers with hidden stored variables cannot replace, clear or reorder variable/presentation snapshots. The UI disables those editors, and the server independently rejects explicit changes. Unrelated label/description saves omit protected fields and preserve canonical metadata. Use one projection across list/catalog/bundle/create/update/lifecycle responses.
- Keep v1 reads and unconfigured rendering compatible. Project v1 scalar formulas into one deterministic UUID variable without writes. Use UUIDv5 with the owning property UUID as namespace and UTF-8 name `minion:formula-variable:primary:v1`; the secondary name is `minion:formula-variable:legacy-secondary:<secondary-property-uuid>:v1`. These fixed discriminators never depend on label/order. Reject an adapter identity collision rather than overwrite a variable. Test stable IDs across reloads/renames and distinct IDs across slots/properties. For a visible, active, numeric legacy secondary, the edit adapter creates a second deterministic variable whose expression/AST references the existing secondary source by stable identity, rather than copying its formula or creating another property. Map existing formats and caption emphasis without changing results.
- Keep canonical definition.rules/presentation v1 on reads. Manager-capable legacy responses add `formulaEditor`: ready shape `{state:'ready',sourceVersion:1,rules:FormulaDraftRulesV2,presentation:ColumnPresentationV2|null}`; blocked shape `{state:'restricted'|'unavailable',sourceVersion:1,code,canClearLegacyPresentation:boolean}`. Codes are legacy_secondary_restricted/archived/unavailable/nonnumeric. Blocked projections expose no draft or hidden source identity. Restricted always forbids clearing. Authorized unavailable repair sends presentation:null only, retains v1 rules, then re-reads a ready single-variable adapter. V2 omits this transient adapter. Adapted names derived from column labels are capped 40 and deterministically disambiguated after normalization, so long/colliding existing labels cannot break conversion.
- Upgrade to v2 only during an authorized explicit variable/formula/format edit, atomically; v2 never implicitly downgrades to v1. Validate the resulting variable graph before any write; reject an actual cycle and preserve v1 with an actionable repair state. Test the common legacy A caption B / B primary depends on A primary case as an acyclic successful upgrade, and a true primary cycle as an atomic rejection. Unrelated metadata edits do not upgrade. Restricted, archived, type-drifted or unavailable legacy secondary targets must not disappear silently: retain canonical v1, explain the repair state, and allow only permitted explicit repair/clear before conversion. Existing independent secondary columns are never automatically archived or deleted.
- No bulk rewrite or production example mutation is required. Existing columns continue displaying after deployment; the user can edit them through the new flow. Database schema remains the existing JSON rules/presentation storage unless implementation proves a concrete migration necessary, in which case include QA seeds and review before applying.

## Out of scope

Manual variables in complex columns, formatting templates, native-column formatting, sibling-variable formula syntax, arbitrary colors/CSS/SQL, references to non-primary variables from other columns, and new server sort/filter/export capabilities. These are deliberate scope boundaries confirmed by the user or compatibility constraints; do not expose unwired controls.
