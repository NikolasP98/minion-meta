## What the video says (transcript read 2026-10-12)

- pi dropped its "no MCP" stance: MCP servers (stdio / streamable HTTP, OAuth) are
  configured in `mcp.json` or `pi.registerMcpServer()`.
- **codemode**: the model writes a JavaScript script that runs in an embedded QuickJS
  sandbox; the script calls pi's tools and MCP tools as functions, loops, parallelises,
  filters, and returns only the result to the frontier model. The "tool-call loop" the
  owner mentions is this: loops over tool calls run inside the sandbox, not in the model's
  context.
- **Progressive disclosure**: tools are not all declared; scripts find them with
  `searchTools()`, `describeTool()`, `describeNamespace()`.
- **System-1 models in the loop**: a codemode script can call `models.classify()` (Typesafe
  Jev, OpenJev, or any llama.cpp model via `/v1/systemone`) per item, so hundreds of small
  semantic decisions never reach the frontier model.
- Creator's benchmark (NHTSA MCP, 10 SUVs): plain MCP 95K uncached input tokens, $0.26,
  4/10 ranked; codemode 21K, $0.09, 10/10. VS Code issues ×100 with a local classifier:
  92K → 30K uncached, $0.35 → $0.14. These are the video author's numbers, not ours.

### The owner's JEV hook (the model to copy)

`~/.local/share/agent-calls/agent_calls/jev.py`, wired as a Claude Code
`UserPromptSubmit` hook. Two typed decisions per prompt: one `choice` over modes
(`project_work | system_admin | question | personal | other`), then one independent
`noul` ("does this request need X?") per manifest that applies to that mode, each gated by
its own threshold (0.5–0.85). Manifests above threshold have their `inject` text prepended
to the turn. Backend: Typesafe `systemone` when `TYPESAFE_API_KEY` is set, else
chat-completion logprobs over OpenRouter (letter labels, `max_tokens=1`). Fails open (an
error injects nothing). Every decision is appended to `jev-decisions.jsonl` with
probabilities, latency and cost for threshold calibration. Today's session log shows
`mode=project_work p=1.0; project_registry 1.0, project_memory 1.0, browser 1.0,
home_memory 0.095 (not loaded); 4.1 s; $0.0002` — the 4 s is the logprobs backend doing
parallel chat completions; the systemone backend is one request.

## Where it runs, and why

- G3 classifier call runs in a **hub server route** (`POST /api/assistant/route` →
  `{mode, manifests: {id: p}}`), not in the browser (the key cannot live client-side) and
  not in the gateway (the manifests are built from the user's hub permissions, which the
  gateway does not have). The client awaits it with a 1.5 s timeout before
  `sendAssistantTurn()`; timeout ⇒ full envelope. One credential surface: the hub's
  existing `OPENROUTER_API_KEY`, decisions endpoint, model `~typesafe/jev-latest`
  (already qualified). Log one PostHog event per decision (`assistant_route`) rather
  than a new table.
- G4 runs where the tool call is: the gateway plugin hook. Channels (WhatsApp, Telegram)
  get the same guard for free; for them the `pre_prompt_build` hook's
  `sections.include/exclude` is the equivalent of G3's envelope gating.
- G1/G2/G5 are gateway only.
