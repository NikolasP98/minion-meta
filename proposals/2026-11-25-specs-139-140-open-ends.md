# Specs 139 and 140: open ends after the go-live audits

Three Opus audit rounds per spec were run before merge (hub #728–#730 and #731–#733). The items below were known
and left open on purpose. Each one has a `TODO(handoff)` at its site.

## AS-IS / TO-BE / DELTA per item

### Spec 139 (reminder follow-up)

1. **Concurrent runs double the paid classifier call (R5e).**
   - AS-IS: two ingest runs, or a tick plus an ingest run at the same moment, both classify the same client answer. That is two paid calls, but only one message is sent.
   - TO-BE: each answer is classified once.
   - DELTA: claim the message (a `last_inbound_at` compare-and-set) before classifying, and release the claim if the classifier errors. Test with two concurrent `advanceAnswers` calls.
   - Site: `reconfirm-answer.service.ts`, before `handleAnswer`.
2. **An opted-out client reads as "message not confirmed".**
   - AS-IS: when the client opted out, nothing is sent, the case ends as `send_failed`, and staff read "No se confirmó el mensaje al cliente: revisa el chat". The drawer says the message may have gone out.
   - TO-BE: staff read "El cliente pidió no recibir mensajes: llámalo".
   - DELTA: title the case by its last system event's `error`. Test with an opted-out case.
   - Site: `reconfirm.service.ts`, the opt-out branch.
3. **A reply after staff cancelled is read by nobody.**
   - AS-IS: after staff cancel, a client's later "sí voy a ir" stays only in the WhatsApp chat. Master behaves the same after any cancel.
   - TO-BE: a reply to a cancelled booking's reminder raises one staff inbox item.
   - DELTA: an inbox rule over inbound messages that arrive after a staff close or cancel and within the reminder's 7-day window.
4. **Exact-text echo match.**
   - AS-IS: an echo of the agent's own message that differs only in whitespace counts as a staff message, and the agent stops. This fails safe.
   - TO-BE: normalize whitespace before matching.
5. **Grouped (merged) visits get the question but no slot offer**, because the strict move refuses groups. Site: `reconfirm-answer.service.ts`, the other-date branch.

### Spec 140 (record locks)

6. **Lifting a grouped external-lock row is not atomic.**
   - AS-IS: the UI sends one owner request per lock and stops at the first refusal, so a group can end up partly lifted.
   - TO-BE: one batch lift route that lifts the whole group in one transaction.
   - Site: `ExternalLocksSection.svelte`.
7. **A `locks` key outlives its owner's demotion.**
   - AS-IS: a key minted by an owner keeps the `locks` scope after that owner is demoted, as every API key does.
   - TO-BE: decide whether demoting an owner revokes the `locks` keys they created, or whether keys belong to the org, not the person. This is an owner decision.
8. **Cancel UI shows the English server text** (`PageBody.svelte`, `body.error`). Map the refusal codes to i18n messages, as corrections do.
9. **The spec docs are out of date.**
   - `data-model.md` still names the old unique indexes; migration `20261125120000` makes them per-key.
   - Plan task T047 doesn't say that cancel shipped early, in S2/S3, and that an org with a saved lock policy but no finance settings now refuses cancels (fail closed).
