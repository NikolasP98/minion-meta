## Server authority and safety boundaries

The [booking PATCH schema](<../../minion_hub/src/routes/api/scheduling/bookings/[id]/+server.ts>):53–89 has no expected-version field. [patchBooking](../../minion_hub/src/server/services/scheduling-bookings.service.ts):1425–1431 locks the booking row before component writes. That serializes writes to the same booking; it does not reject stale client intent by itself.

[rescheduleBookingInTx](../../minion_hub/src/server/services/scheduling-bookings.service.ts):1165–1254 validates positive duration, rejects cancelled/rejected bookings, checks active destination resource and buffer-padded overlaps, then updates. The overlap read does not itself lock all competing destination bookings. This audit did not inspect every DB constraint/isolation setting, so cross-booking race safety remains unproven, not a declared production bug. Resource membership, capacity, and different booking statuses need explicit acceptance criteria before broadening immediate drag acceptance.

The same function's existing TODO at :1243 says off-hours/holiday/leave reschedules are allowed but lack a warnings payload. An optimistic UI must not invent a warning-free approval or silently treat shading as enforcement.

[Atomic POS scheduling](../../minion_hub/src/server/services/scheduling-bookings.service.ts):655–782 locks ticket/line state and handles a legitimate retry against the claimed line. Preserve this domain guarantee when adding pending tray items; a generic optimistic create must not duplicate bookings or package redemption.

Status changes are not all cosmetic. [setBookingStatus](../../minion_hub/src/server/services/scheduling-bookings.service.ts):992–1028 writes status history and reverses package redemptions/release accruals for releasing states. [booking PATCH completion](<../../minion_hub/src/routes/api/scheduling/bookings/[id]/+server.ts>):125 onward can commit status while returning a stock warning; an existing TODO documents post-commit recovery limitations. Series cancellation can affect following bookings. Preserve explicit confirmation for these consequences.

## TO-BE policy

1. **Navigation and filters:** immediately update selected view/date/staff/kind and render cached data. Keep URL/history coherent; show a localized loading indicator only for missing windows. Preserve the current grid rather than blanking it. Stale responses may enrich their own cache key but cannot replace the active selection.
2. **Reversible booking properties:** autosave title/internal note/kind/tag changes with entity-scoped pending state, validation, retry and conflict recovery. Coalesce typing before transmission; serialize dependent writes. Changes to external-facing client notes require an explicit semantic decision if those notes trigger messaging. A shared mutation result must distinguish booking-save success from tag-save failure.
3. **Drag/resize:** apply a persistent optimistic overlay at pointer release and send immediately for ordinary single-booking changes. Show “saving” on that event; preserve interactive navigation. A rejected move rolls back only its own mutation, never a newer successful move. Use returned canonical booking/version to settle the overlay. Retain a confirmation/review path for series changes, capacity overrides, off-hours warnings when required, or financially consequential transitions.
4. **Create:** keep form confirmation. A calendar drop may create a visibly pending provisional event; it is not a confirmed appointment until the server acknowledges. Reserve/deduplicate the source paid line while pending. On conflict, retain draft intent and explain the specific failure instead of silently discarding context.
5. **Status and completion:** visually acknowledge the click immediately, but distinguish pending from confirmed. Cancellation, package reversal, stock realization and series actions remain explicit. Confirmed status plus stock warning is a partial outcome, not rollback of a committed status.
6. **Payment:** retain explicit charge. Animate a processing state without claiming payment, balance, stock, or receipt success. Settle only from the authoritative response. On ambiguous network failure, reconcile by idempotency/operation identity before allowing a retry that could charge twice. Never auto-retry a financial mutation merely because a read timed out.
7. **Motion:** use existing semantic duration/easing tokens and shared primitives under UI governance. Animate event movement/rollback and localized pending affordances; avoid full-page spinners, layout jumps and celebratory success before commit. Respect reduced motion, keyboard focus, accessible busy state and live-region messages. Do not add literal duration/easing values.
