## Existing foundations

- [createOptimistic](../../minion_hub/src/lib/utils/optimistic.ts), lines 4–38, overlays a keyed intended value until the commit callback settles. Keeping `await invalidate(...)` inside that callback prevents stale-value snapback. It catches rejection and returns false. It does not itself serialize overlapping runs for the same key: every completion deletes that key. Callers must currently block re-entry; a general autosave controller needs generations or serialization.
- [Toggle](../../minion_hub/src/lib/components/ui/Toggle.svelte), lines 10–15 and 52–66, already accepts pending, displays the intended value, blocks interaction, adds aria-busy and a spinner. Extend this existing contract to other controls rather than creating a second toggle system.
- [AsyncBoundary](../../minion_hub/src/lib/components/ui/foundations/AsyncBoundary.svelte), lines 2–8 and 41–95, distinguishes loading/ready/empty/error/forbidden/unavailable with aria-busy, status and alert roles. It replaces children during loading; background refresh needs a separate refreshing flag or stale-content variant.
- [ConfirmDialog](../../minion_hub/src/lib/components/ui/foundations/ConfirmDialog.svelte), lines 52–79, awaits confirmation, keeps failures visible and blocks dismissal while busy. Reuse for consequential actions.
- [FormField](../../minion_hub/src/lib/components/ui/foundations/FormField.svelte), lines 41–73, supplies error/helper IDs and aria-invalid. Autosave errors should use this infrastructure, not toast-only feedback.

## Shared implementation requirements for the specification

1. Define editing, queued, saving, saved, failed, conflict and offline/local-only separately. A successful write followed by failed invalidation is committed-but-stale, not a rejected write.
2. Key mutation state by tenant, entity and field/operation. Use generations or per-key serialization so old success cannot clear new pending state and old failure cannot revert newer data. Existing createOptimistic is suitable only with enforced non-overlap or after extension.
3. Keep acknowledged data and draft overlay separate. Broadcast/invalidate entity changes across all mounted consumers after acknowledgement; remote updates cannot silently overwrite an active draft. Resolve conflicts explicitly when server revisions disagree.
4. Preserve responsive local feedback independently of persistence. Delay cosmetic spinners enough to avoid flashes only through a shared presentation policy; never delay writes, acknowledgement or error delivery for an animation.
5. Read-only loads retain current content during refresh. Initial load may show skeleton; error retains available stale data with retry. Stable keys and scroll/focus positions survive updates.
6. Use polite, coalesced status announcements for saving/saved; actionable field errors use linked error text. Keyboard Enter/Escape/blur semantics must be explicit, including IME composition and navigation while pending. Do not announce every keystroke.
7. Keep explicit forms and consequential commands. Optimism never means speculative authorization, credentials, published content, sent messages, executed jobs or server-issued identifiers.

## Required verification

For each selected interaction family, test immediate local response; slow success; HTTP failure; network interruption; rapid repeated edits with responses reordered; refresh failure after write success; navigation with queued writes; remote update during editing; and tenant/entity switch during pending work. Assert latest intent survives and every mounted consumer converges on acknowledged data.

Exercise keyboard-only entry/commit/cancel, focus restoration, field error association, pending announcement and reduced motion toggled both before mount and while open. Confirm dialogs close and release scroll lock without waiting indefinitely for animation events. Read-only refresh must preserve rows and focus. For security/financial/external commands, assert no effective success before server acknowledgement.

This audit performed source searches and reads only. No tests or browser paths were executed. The concurrency and failure concerns above are code-based specification requirements, not claimed reproduced incidents.
