## What the sender consumes, unchanged

The 11-07 journal is used exactly as verified, with no schema, index or policy change:

| Call | Use on the durable path |
| --- | --- |
| `admit(admission)` | Record the receiver-issued admission before the ACP call. The existing `one_open_run` partial unique index enforces the same single unresolved run the bridge already advertises as `maxConcurrentRuns: 1`. |
| `observe(runId, observation)` | Record `unresolved`, `cancel_requested` or `cancel_unconfirmed` without touching the terminal. |
| `commitOutcome(outcome)` | Persist the immutable terminal and insert its outbox delivery row inside one transaction. |
| `pending()` | Enumerate terminals whose `receipt IS NULL`, in `event_id` order, for replay. |
| `acknowledge(receipt)` | Store the validated receipt, which is what makes the entry stop being pending. There is no delete API and none is added. |

The receiver side is likewise fixed: `shells.commit_outcome` already exists on the registered machine endpoint and returns a committed `ShellOutcomeReceipt` only after its own COMMIT; registration returns `durableOutcomeVersion: 1` only when the gateway has an open compatible store and the peer advertised v1.

## Accepting an admitted invocation

Add `SHELLS_METHODS.invokeDurable` to the bridge's `dispatch` switch. Its params are the canonical `ShellAdmittedInvoke` envelope — `{version: 1, admission: ShellRunAdmission, input}` — which the gateway mints from its own committed admission row and which no caller ever supplies.

The canonical package validates the admission but not the enclosing envelope: there is no `normalizeShellAdmittedInvoke` export. The bridge therefore checks `version === 1` and the presence of `input` itself, and delegates every identity, byte and Unicode rule to `normalizeShellRunAdmission(params.admission, SHELL_DURABLE_V1_OUTCOME_LIMITS)`. Do not re-implement identifier bounds, surrogate handling or digest rules. If root prefers a canonical envelope normalizer, that is a shared-package change in the 14-16 lineage, not this child.

`bridge.ts:226–228` currently mints `run_${randomUUID()}` and `Date.now()` for every invocation. On the durable path the bridge mints neither. `runId`, `startedAt`, `sessionId`, `invocationId` and `inputDigest` all come from the validated admission and are used verbatim as the `ActiveRun` identity and the journal key. An admission whose `shellId` is not this bridge's configured `shellId` is refused before any journal or ACP work.

Order is fixed: validate, then `admit`, then start the ACP prompt, then reply. The reply is strictly the four-field durable admission response — `{version: 1, durability: "required", runId, startedAt}` with the admission's own `runId` and `startedAt` — round-tripped through `normalizeShellsInvokeDurableResponse` before it is sent, so a shape the gateway would reject can never leave the bridge. Replaying the same admission (same `runId`, same `invocationId`, same input digest) while the run is active or already terminal returns that same response without a second ACP call; a conflicting admission for a known identity is a bounded conflict error. Refuse durable admission when the bridge is shutting down, when the harness is not running, or when durable mode is not configured — and never fall back to legacy behavior in that refusal.

## Terminal outcome, commit and receipt

When the ACP prompt settles as `final`, `aborted` or `error`, build the canonical `ShellRunOutcome` from the admission identity plus a fresh `eventId`, the observed `state`, `durationMs`, optional `stopReason` and a bounded public-safe `errorMessage`. `outcomeDigest` is SHA-256 over `shellRunOutcomeText(outcome, limits)` — the same fixed projection `run-journal.ts:176` verifies against — and is computed with that exported helper, never a hand-written projection.

`errorMessage` must be bounded, public-safe text. The canonical byte and shape validation is not redaction: a raw ACP error, provider payload, stack trace, path or credential must not be placed there. Where the bridge cannot produce safe text, omit the field rather than pass raw error text through.

Then, in this order: `journal.commitOutcome(outcome)` → `callGateway(SHELLS_METHODS.commitOutcome, outcome)` on the current registered v1 socket → validate the reply with `normalizeShellOutcomeReceipt` → `journal.acknowledge(receipt)`. The entry stops being pending only after the receipt validates against the stored event id, run id and digest; a malformed, mismatched, foreign or missing receipt leaves it pending. Nothing may be sent before the local commit, and nothing may be acknowledged on the strength of a send succeeding.

The durable path never emits `shell.final`. `emitFinal` and the `SHELLS_EVENTS.final` relay stay exactly as they are for legacy runs; a transient event creates no durable terminal at the receiver and must not be used as a delivery mechanism or a fallback when `commit_outcome` fails.

## Current socket, reconnect and replay

`register()` at `bridge.ts:246–272` currently discards everything in the registration response except `heartbeatMs`. It must additionally record whether that response carried `durableOutcomeVersion: 1`, bound to the actual `source` socket it registered on — not to a connection id, a timestamp or a mutable flag. Only that exact socket may carry a `commit_outcome`; after a reconnect the flag is not inherited until the new socket's own registration response accepts v1 again. A peer that omits the field stays legacy, and an explicitly malformed value is refused rather than treated as absence.

After a registration that accepts v1, replay every `pending()` terminal in `event_id` order through the same commit-then-acknowledge path. Replay re-sends only the stored terminal: it never re-runs a prompt, never re-mints identity, never re-admits, and never touches the harness. An exact duplicate commit returns the receiver's original receipt, which acknowledges normally. Replay must be bounded and must not block heartbeats or new admissions; a failing replay leaves the entry pending for the next attempt.

On startup the same replay runs before or alongside the first registration's normal work, so a terminal that survived a bridge restart is delivered without a new invocation.

## Timeout and cancellation truth

Requested cancellation, an expired local wait and a terminal outcome are three different facts and are recorded as three different things. `observe(runId, {kind:"cancel_requested", at})` records that the bridge asked. An expired local wait records `{kind:"cancel_unconfirmed"}` or `{kind:"unresolved"}` — it does not release the journal slot, does not produce a terminal, and does not assert that the harness stopped or that an already-sent effect was undone. `cancel_acknowledged` is written only from actual protocol evidence, which the current adapter cannot supply (11-04); until then it is not written at all. A terminal that arrives after a cancellation request wins and is committed normally; a cancellation request after a terminal changes nothing, which the journal's post-terminal observation guard already enforces.

- durable mode flag — off unless explicitly enabled; an unrecognized value is a `ConfigError`, never a silent default.

A relative path, a path with a `..` segment, or a path inside `harnessWorkDir` is a `ConfigError`. This is a configuration check; the journal's own trusted-parent, single-link and 0600 checks remain the real boundary and are not duplicated here.
- finite journal policy — `maxRuns` and `maxOutcomeBytes` as positive safe integers with explicit selected defaults, plus the fixed canonical outcome limits. These are logical rejection limits, not disk quotas or measured capacity.
