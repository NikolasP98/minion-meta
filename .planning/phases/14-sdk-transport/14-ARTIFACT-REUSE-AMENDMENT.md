## Minimal14-04 request identity amendment

Current `PluginBridge.call` uses `rpc-${++rpcSeq}-${Date.now()}` (`src/index.ts:332`); each new instance resets rpcSeq. Two actual instances in the same millisecond can issue identical first IDs. Reusing a WindowProxy and expected parent means an old valid response can then resolve the new instance's pending call. Hub's in-flight duplicate suppression can also drop the newer request, after which the old result matches the newer pending ID. This is a correlation defect, not fixed by source/origin checks or clearing the disposed instance's map.

### Recommended native identity policy

Create one private per-instance random namespace from **16 native cryptographically generated bytes**, formatted as32 hex characters, and append a monotonic instance-local sequence to form opaque IDs. Generate it lazily before the instance's first RPC using `globalThis.crypto.getRandomValues(new Uint8Array(16))` with the correct Crypto receiver. Do not add a dependency, public ID factory option, wire field or artifact-specific pending map. Date/time must not participate in uniqueness. Preserve nonempty string IDs as the public wire contract; consumers must not parse their internals.

Lazy initialization is the recommended minimal compatibility choice: bridges used only for theme/locale/ready do not require randomness, while RPC fails closed if native secure randomness is unavailable or throws. Obtain the namespace before adding pending state or posting. Return a safe local rejected Promise, with no weak fallback (`Math.random`, timestamp, process-local counter alone), no leaked native cause and no orphan pending entry. Allocate at most once per instance after successful generation; no reuse after dispose. Keep sequence arithmetic within safe integers and reject exhaustion rather than wrap.

A random namespace provides cryptographic collision resistance, not a mathematical guarantee of universal uniqueness. Within an instance, a nonwrapping sequence is deterministic. No claim that the identifier authorizes an RPC is permitted: host/source and method authority remain separate checks.

### Native availability and alternatives

| Option | Availability/correctness trade-off | Selection |
|---|---|---|
|`crypto.getRandomValues` per instance | Native API describes cryptographically strong random values; avoids requiring randomUUID specifically; feature-detect actual function and handle failure | Recommended |
|`crypto.randomUUID` per instance | Simpler string API, but installed DOM declarations explicitly mark it secure-context-only; requiring it may exclude a deployment where other native random APIs exist | Acceptable only with a verified secure-context support policy; unnecessary extra assumption here |
|Inject an ID factory into public PluginBridgeOptions | Makes tests easy but expands the public API and permits insecure production configuration | Reject for this slice; tests can stub the native API directly |
|Retain time-based IDs or add a handwritten artifact-level remapper | Does not fix general two-instance package correlation, or duplicates protocol ownership | Reject |

The local read-only probe reports Nodev22.23.2 with global crypto/getRandomValues/randomUUID functions. Installed TypeScript `lib.dom.d.ts:8438-8449` documents cryptographic getRandomValues and secure-context randomUUID. These are local API/tool facts, **not proof of availability in every supported iframe/browser**. Exact HTTPS/loopback opaque sandbox and any supported plain-HTTP host must be exercised later; no insecure-context or browser compatibility claim is inferred from Node. Require a generic local failure state where native entropy is missing, rather than silently weakening identity.

## Persisted-pageshow lifecycle selection

Recommend **fresh bridge lifetime after persisted pageshow**, dependent on the package namespace amendment above. Keep lifecycle ownership in the thin artifact adapter, not in a second protocol implementation:

- Initial script startup creates one PluginBridge, registers hello/theme/render callbacks and notifies ready. One supported hello triggers one context call in that lifetime; duplicate hello updates validated theme data without another context fetch.
- On pagehide, retire the current bridge and call dispose; clear the adapter's active-instance reference. Its render/failure continuations check that their captured instance is still the active one before touching DOM. A settled-before-dispose Promise must not render after retirement.
- Retain only the adapter's document-level lifecycle handlers needed for restoration. On pageshow with `persisted=true`, start one fresh PluginBridge if none is active, reset the one-context-request flag, handshake again and obtain fresh context. Initial nonpersisted pageshow must not create a duplicate initial bridge.
- The fresh package namespace prevents responses for a previous lifetime from matching new calls, even at the same time tick. Do not rewrite frames, maintain an extra request map, infer session from Date.now, or revive a disposed object.
- Expose an adapter final-dispose operation for controlled teardown/tests that removes lifecycle handlers as well as the active bridge. A destroyed document is ultimately released by browser lifecycle; no global timer or retained cross-document registry is needed.

This selects a lifecycle behavior; native BFCache proof still requires an admitted real browser. Synthetic persisted events are useful unit cases but do not establish that a browser cached/restored that page. The browser fixture must record the actual persisted flag and prove exactly one fresh context request and zero stale rendering after restoration. If that browser environment does not enter BFCache, report the native case unverified rather than replacing it with a synthetic pass.
