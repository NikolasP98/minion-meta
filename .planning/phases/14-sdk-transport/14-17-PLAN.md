## 1. Caller dispatcher and method-scope registration

Add exactly two caller methods in `minion/src/gateway/server-methods/shells.ts`, taking their names from the canonical constant through the 14-14 facade rather than new string literals:

| Method | Local gate | Generic dispatcher classification | Manager call |
| --- | --- | --- | --- |
| `shells.invoke_durable` | `requireAdmin` then `requireOrgScope` | Not added to `READ_METHODS` or `WRITE_METHODS`; `authorizeGatewayMethod`'s terminal fallthrough already answers `missing scope: operator.admin` | `invokeDurable(params, orgId)` |
| `shells.get_outcome` | `requireOperator` then `requireOrgScope` | Added to `READ_METHODS`, which accepts `operator.read` OR `operator.write` and is bypassed by `operator.admin` — exactly the D360-15 ladder | `getDurableOutcome(params, orgId)` |

The explicit local `requireAdmin` on durable invoke is deliberate belt-and-braces: today `shells.invoke`'s effective admin gate comes only from the generic default at `server-methods.ts:300`, while the local handler checks `requireOperator`. Durable invoke must not inherit that fragility. Do not change the classification of any existing `shells.*` method in this child.

Organization comes only from `requireOrgScope`, which reads `client.orgId` and nothing else. `client.orgId` is established at connect from a validated JWT (`auth/auth-jwt.ts`, `server/ws-jwt-auth.ts`, `server/ws-connection/message-handler.ts`) or set to the literal `service` namespace for a configured service credential. The backward-compatible shared operator token path grants `operator.admin` with `orgId` undefined; such a session must be refused by `requireOrgScope` with `organization context required` BEFORE `ensureMgr` and before any manager call. `params.orgId` is never read, never forwarded, and an explicitly supplied `orgId` in params must not change the outcome for any caller.

Both handlers pass raw `params` straight to the manager and let the canonical normalizers own validation. Do not pre-parse `shellId`, `sessionId`, `input` or `invocationKey` with the local `asString`/`asObject` helpers, do not copy byte or Unicode rules, and do not construct a `ShellAdmittedInvoke` in the dispatcher — that envelope is gateway-internal and is minted by the manager. Map `ShellsDurableError` codes to bounded protocol errors (`unavailable` → UNAVAILABLE, `unauthorized` → FORBIDDEN, `conflict`/`invalid` → INVALID_REQUEST, `forward_failed` → UNAVAILABLE) without leaking SQL text, raw provider errors, credentials or caller payloads. `shells.get_outcome` returns the canonical response as-is; a foreign-organization or absent run is the same `not_found` shape and must not be distinguished by error code, message or timing branch.

Legacy `shells.invoke` keeps its current behavior when durability is disabled. In required mode the manager already refuses it; the dispatcher must surface that refusal rather than retrying, downgrading, or synthesizing a legacy response. There is no code path in which a failed or unknown `shells.invoke_durable` is retried through `shells.invoke`.

Advertisement lives in two files. `BASE_METHODS` in `server-methods-list.ts` is the stable static RPC floor, consumed by `listGatewayMethods()`, the connect handshake, `plugins/capabilities.ts` and the committed `minion/capabilities.json`, whose drift is checked by `scripts/generate-capabilities.ts --check` inside `pnpm check`. Add both methods there and regenerate the artifact with `pnpm gen:capabilities`; hand-editing the JSON is refused. Note the distinction explicitly in code: appearing in the static floor asserts that the gateway implements the method, NOT that durability is live. Live readiness is answered only by the handler's `unavailable` refusal and, on the machine side, by the existing `durableOutcomeVersion: 1` in the registration response, which 14-12 already gates on an open compatible store plus a bilaterally negotiated peer.

## 2. Gateway configuration surface

Extend `GatewayShellsConfig` in `types.gateway.ts` and its strict zod object in `zod-schema.ts` with one optional field:

```
durability?:
  | { mode: "disabled" }
  | { mode: "required"; storePath?: string; maxRuns?: number; maxRunsPerOrg?: number }
```

Omitted and `{mode:"disabled"}` are identical and preserve legacy operation with no SQLite load. `mode` is a required discriminant inside the object: an object without `mode`, an unknown `mode`, or a bare boolean must fail schema validation rather than resolve to a default. No inferred default ever selects `required` — absence is always disabled. Keep the parent `.strict()` so unknown keys are rejected, and keep `shells.storePath` meaning the JSON registry path; `durability.storePath` is a different file and the two must never collide.

Numeric fields are optional positive safe integers with the selected D360-16 deployment defaults 4096 global and 1024 per organization, and `maxRunsPerOrg <= maxRuns` (the store constructor already refuses otherwise; the schema must refuse earlier with a readable message). The default required-mode path is `<stateDir>/shells/outcomes.sqlite`, resolved through the same `resolveStateDir()` the registry already uses, and is distinct from `shells/registry.json` and from the bridge journal. A configured `durability.storePath` must be absolute and canonical; a relative path, a path with a `..` segment, or a path resolved from the current working directory is refused at configuration time, before the store constructor's own trusted-parent checks run. Configuration validation is a schema/path check, not a filesystem trust proof — the store's owned-parent, single-link and 0600 sidecar checks remain the real boundary and are not re-implemented here.

Add regression cases to `config.schema-regressions.test.ts` for accepted and refused shapes. A schema test proves parsing, not durability.

## 3. Startup opening, readiness and shutdown

In `server.impl.ts`, the existing block at 574–612 constructs the exe.dev provider, access relay, `JsonShellsStore` and `ShellsManager` inside one `try` whose `catch` logs `[shells] manager init failed` and continues with `shellsManager = undefined`. That broad catch must not swallow a required-durability failure: when `durability.mode === "required"`, a store that cannot be constructed, is incompatible, or sits on an untrusted path must fail gateway startup loudly instead of silently degrading the subsystem to legacy. Disabled mode retains the current tolerant behavior exactly.

Ordering is fixed: construct `ShellRunStore` BEFORE `new ShellsManager(...)`, pass it as `durability: {mode:"required", store}`, and only then let the bridge WS endpoint attach at 1075–1082 and the caller handlers register at 1091. The manager must never be constructed with `{mode:"required"}` and a store the process has not opened, and the bridge endpoint must not be able to advertise `durableOutcomeVersion: 1` before the store exists. If store construction fails in required mode, the access relay and manager must be torn down on the same failure path rather than left half-initialized.

Shutdown is owned by `createGatewayCloseHandler` in `server-close.ts`, which today receives no Shells parameter at all. Add an optional injected hook — a single `shellsDurability?: { quiesce: () => Promise<void>; close: () => void }` shaped param, not the manager itself — and call it in a fixed position: after the bridge/client socket close pass so no new machine commit can enter, and before the HTTP servers finish closing. `quiesce` first (it sets stopping synchronously, revokes readiness and drains only entered local work), then `close`. Both are wrapped so a failure cannot abort the remaining shutdown, and `close` is idempotent. Never call `close` without `quiesce`, and never hold shutdown on a remote bridge forward — 14-12 already excludes remote waits from the drain obligation, and a forward settling after quiesce must find a refusing manager, not a closed-store access.

No health or readiness surface currently reports Shells durability: `server-methods/health.ts` builds its snapshot from `refreshHealthSnapshot`/`getStatusSummary` and contains no shells field. This child must not add a positive durable-ready claim to any of them. If root later wants an operator-visible readiness field, it is a separate decision with its own truthfulness test; the rule this plan enforces is that no surface may report durable-ready unless a compatible store is actually open, and both existing truthful surfaces (handler `unavailable`, registration `durableOutcomeVersion`) already satisfy it.

<threat_model>
| Boundary | Threat | Required control |
|---|---|---|
| Caller session / dispatcher | A shared admin token or a caller-supplied `params.orgId` acquires another tenant's runs or receipts | Organization read only from `client.orgId` established at connect; `requireOrgScope` refuses before the manager; params never consulted; negative cases for unscoped admin, foreign orgId and empty orgId |
| Method-scope registration | A new method silently inherits the wrong ladder — durable invoke reachable by operator.read, or the outcome query effectively admin-only | Explicit classification: query in READ_METHODS, invoke left to the terminal admin fallthrough plus a local `requireAdmin`; real `authorizeGatewayMethod` tests per scope and role |
| Durable mode selection | An inferred default, a partial object or a legacy retry path enables or downgrades durability without an explicit decision | Discriminated required `mode`, strict object, absence always disabled, required mode refuses legacy invoke, no retry of a durable failure through `shells.invoke` |
| Configuration path / store lifetime | A caller field, relative path or working-directory default opens a database, or a store outlives or precedes its owner | Absolute canonical path validated at config time under the store's own trusted-parent checks; store constructed before the manager and closed only by the injecting owner; required-mode failure fails startup instead of degrading |
| Readiness advertisement | A static capability entry or a health field is read as proof that durable storage is live | Static floor documented and tested as an implementation claim only; live readiness stays the handler `unavailable` refusal and the store-gated `durableOutcomeVersion`; no positive durable-ready field added |
| Error surfaces / query results | SQL text, credentials or caller payloads leak, or a foreign row is distinguishable from an absent one | Bounded mapped error codes with no raw text; identical `not_found` payload for foreign and absent runs, asserted on the same code path |
</threat_model>
