## Design contract

### Trusted filesystem boundary

- This slice protects against caller-controlled paths/SQL and pre-existing filesystem aliases. It assumes that the admitted resource directories, their relevant ancestors and configured root pointers are controlled by the operator and are not concurrently mutated by hostile same-UID processes.
- Prove the locally checkable portion: existing POSIX directories/resources belong to the gateway effective UID or root, and writable directory components are not group/world writable. Explicitly document any necessary sticky-directory ancestor handling for a private owned temp fixture; do not exempt writable directories below the admitted root.
- Metadata checks do not prove that another process with the same UID is trustworthy. Deployment in a shared writable agent workspace is blocked until the operator/runtime evidence establishes this boundary or a separate isolation plan supplies an OS-enforced broker/sandbox. No source or README may call the result generally race-proof. The sidecar and clean-runtime/schema/function qualification requirements below are part of this trust boundary, not waived by a main-file path check.
- Keep path validation and the corresponding synchronous operation adjacent, with no user callback/await between them. This reduces the check/use window and prevents JavaScript re-entry; it does not close concurrent OS-process races.
- Node 22's current `DatabaseSync` API opens by pathname; it does not expose an fd, `openat2`, `SQLITE_OPEN_NOFOLLOW`, or an authorizer option. Do not improvise `/proc/self/fd` SQLite paths, change journal modes or pass undocumented SQLite open flags. These would need separate WAL/locking/cross-platform qualification.
- Use built-in Node filesystem APIs only. If the platform cannot enforce the chosen no-follow/ownership checks, return a stable unsupported-path-policy error rather than silently claim the POSIX guarantees. Do not infer Windows ACL safety from mode bits.

### Roots and resource identity

- Operator configuration (`pluginConfig`, startup environment and the already-open message-ledger handle) defines trusted roots. Per-node `config.dbPath`/`config.path` does not define a root or exception.
- Canonicalize an existing operator-configured root once per admitted root identity; an explicitly configured root symlink may identify its canonical operator-trusted target. Validate ownership/mode of that target. Reject symlink traversal **below** the canonical root, including links pointing back inside it; there is no caller symlink exception.
- Default database resource remains `MINION_MESSAGE_LEDGER_PATH` or `<stateDir>/message-ledger.db`. Explicit `ledgerPath` outside stateDir remains an exact operator-admitted database resource, not permission to access sibling files or its whole directory.
- A shared ledger opened from gateway configuration may differ from the env default. Resolve its actual main path with the existing trusted `PRAGMA database_list` seam and apply the same exact-resource checks before opening the independent reader or executing a consume/write. Do not close or mutate the shared writer. In-memory shared-ledger reads keep the existing fail-closed behavior.
- Other caller database paths must resolve below the admitted canonical stateDir; file writes must resolve below the admitted canonical fileWriteDir. Preserve existing relative/absolute/`~` expansion only when the result is admitted. Reject NUL, path traversal, root-as-file, devices, FIFOs and directories as final file targets.
- Reject hardlinked final database/output files (`nlink > 1`) in caller-controlled paths and cover the exact configured ledger policy explicitly. A hardlink is an object alias even though `realpath` stays inside the root. Do not silently trust hardlinks as ordinary files.
- For missing outputs/database write targets, walk and validate every existing ancestor, then create missing directories one component at a time under the admitted root with restrictive modes. Never fall back from failed `realpath` to unchecked lexical acceptance. Revalidate before the operation. A missing read database is an error and must not be created.
- Existing `scan-paths.ts` falls back to lexical paths on missing targets; it cannot supply this guarantee unchanged. `fs-safe.ts` shows useful descriptor/inode checks, but its asynchronous read API is not a drop-in write or SQLite opener. Do not create a misleading wrapper around either.

### File and SQLite operations

- For file overwrite/append, open with `O_NOFOLLOW` where supported; verify a regular file and expected identity before truncation/writing, write through that descriptor, and close in `finally`. Avoid `O_TRUNC` before verification. Existing-file substitution must be rejected or leave only the originally admitted file descriptor affected; do not re-open by caller pathname after validation.
- New-file creation and SQLite pathname opens retain the trusted-ancestor-writer assumption described above. Tests must not label this stronger than it is.
- Treat a SQLite resource as the admitted main file plus its known `-journal`, `-wal` and `-shm` companions. Before opening or reusing a connection, validate any existing companion with the same no-link, single-link, regular-file, ownership and trusted-ancestor policy; missing companions may be created only by the qualified engine beneath that admitted parent. Do not unlink or repair suspect sidecars, discard recovery data, or change journal modes to pass validation. Add actual-engine rollback-journal and WAL positive controls plus linked, hardlinked and nonregular companion negative fixtures; preserve outside sentinel bytes and directory entries. A cached/shared handle can already hold sidecar descriptors, so accepting it also requires the clean-runtime provenance boundary below.
- SQLite can use statement journals, temporary databases and materialization/sort storage outside the main database directory. This slice must not claim all SQLite I/O remains beneath stateDir. Those engine-managed channels require an explicitly operator-controlled temporary-storage/profile and exact Node/SQLite/VFS qualification; caller SQL cannot select the location. Unknown temporary-storage provenance remains a deployment gate. Do not force memory-only storage or change durability/journal settings to hide these channels.
- Run DB admission checks before opening a new handle **and** before reusing a cached handle. Reject aliases; do not let a once-valid path become a reusable authority token after it points elsewhere. Key owned handles by admitted canonical resource and validate the on-disk identity as needed. Never close the shared ledger handle. Avoid adding another permanent cache.
- Keep 09-02's independent `readOnly:true` reader, full `statement.sourceSQL` equality and explicit separate consume writer. Apply the new resource checks to consume marking as well as direct reads/writes.
- Narrow caller `db.exec` to one prepared `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, or `WITH` statement. The prefix restriction defines the writer API; it is not a general SQL parser. SQLite grammar/prepare plus full `sourceSQL` equality determine statement boundaries. Reject standalone/appended ATTACH, DETACH, VACUUM, PRAGMA and schema/connection-management SQL before effects. Do not split on semicolons inside literals.
- Only admit connections with known trusted initialization and schema/function/extension provenance. The read-only reader is fresh, but its database schema and process-global SQLite state still require this boundary. For extension-owned handles, record source-proven safe construction and reject unexpected schema/connection features using safe introspection where supported. For shared handles, establish the trusted initializer and allowed current schema/functions/connection policy before use; object identity, POSIX ownership or `database_list` alone is not proof. If evidence cannot establish that boundary within the owned files, fail closed with a bounded error and create an exact prerequisite plan; do not invent a caller-set trust flag. Never certify a process or database previously exposed to unrestricted SQL as clean merely because it has no attached database. A fresh exact-image process plus trusted data/schema/function provenance and operator-controlled temporary storage is a mandatory rollout qualification; restarting alone does not cleanse a persisted poisoned schema. Do not close, detach, reset PRAGMAs or otherwise sanitize another subsystem's shared handle as a workaround.
- Before executing on a writable/shared/cached connection, inspect trusted `PRAGMA database_list` and deny non-main/non-temp attached databases so an older poisoned handle is not retained as authority. Do not detach/mutate another subsystem's shared connection as a repair.
- Do not add extensions, SQL functions, schema DDL or authorizer dependencies. Preserve bound scalar CRUD operations and `WITH ... UPDATE`/read compatibility where they do not change the connection or filesystem. Unsupported legacy DDL/file-management flows require reviewed migration before rollout; they must not receive a compatibility bypass.
- Preserve RPC method names and current success/error envelope. Errors must be bounded and avoid disclosing resolved outside paths or raw filesystem exception text. Missing path/policy failures must be caught consistently in read, exec and file-write handlers.

## Required acceptance matrix

| Case | Required observation |
|---|---|
| Existing allowed SQLite file, bound SELECT and CTE | Real expected rows; later valid writer still works. |
| Configured external ledger exact path | Allowed only as operator-owned exact resource; sibling file denied. |
| Shared ledger opened at nondefault real path | Read uses independent reader over actual admitted main file; consume uses shared writer without closing it. |
| Shared in-memory ledger | Read fails closed; no accidental default file creation. |
| Missing read database | Error and no new file. |
| Allowed missing write database/output path | Restrictive in-root creation only; valid subsequent operation succeeds. |
| Existing final link, dangling link, parent link, missing leaf below parent link | Denial; outside sentinel bytes and directory entries unchanged. |
| Hardlinked final database/output | Denial under explicit resource policy; outside alias unchanged. |
| Existing linked/hardlinked/nonregular `-journal`, `-wal`, `-shm` companions | Denial before opening/reusing the database; outside sentinels unchanged; no recovery files deleted. |
| Ordinary rollback-journal and WAL resources | Real engine read/write/consume behavior remains valid without mode changes. |
| No attachments but untrusted shared/cached connection or schema/function provenance | Fail closed; absence of attachments alone cannot confer admission. |
| Engine-managed temporary storage or old unrestricted process/data | Explicit clean-process plus trusted-data/profile qualification gate; no claim that restart cleans persisted schema or confines all engine I/O beneath stateDir. |
| File overwrite, append, {date}, existing relative/absolute/~ in-root inputs | Existing contract retained; descriptor always closed. |
| Root/target directory, FIFO/device, NUL, traversal | Denial before data effects; no blocking FIFO open. |
| Unsafe directory ownership or writable permissions | Stable policy denial; no automatic permission mutation. |
| Cached handle after path/identity substitution | Denial rather than silent trust in the old path key; no shared handle closure. |
| VACUUM INTO outside path via binding | Denied; outside file absent. |
| ATTACH/DETACH/PRAGMA/DDL and trailing statements | Denied before execution; rows and connection attachment state unchanged. |
| Existing attached database on disposable writer | Denied without detaching it or modifying outside rows. |
| INSERT/REPLACE/UPDATE/DELETE and valid WITH, quote/semicolon bindings | Real expected changes, single statement only. |
| No-follow final-file swap injected before open | Denied before truncation/write; stable error. |
| Concurrent hostile ancestor mutation by another same-UID process | No race-proof claim; requires separate isolation/runtime trust admission and remains a deployment gate. |
