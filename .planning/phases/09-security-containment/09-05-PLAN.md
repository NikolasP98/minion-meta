## Source discovery and design contract

### Owner and receipt

`src/memory/sqlite.ts` only loads `node:sqlite`; it does not construct ledger handles. `openMessageLedger()` in `src/infra/message-ledger.ts` is the construction seam: `new DatabaseSync(dbPath)`, `applySqlitePragmas`, `INIT_SQL`, then publication to `ledgerState.db`. Modify this owner rather than introducing a global loader policy.

The current `__minion_message_ledger_state__` global intentionally preserves a raw `db` across reloads. A newly loaded module must not infer provenance for that pre-existing object. Maintain receipt authority in module-private state keyed by the exact freshly constructed object; never place a reusable receipt, receipt registry or mint function on `globalThis`, the handle or a caller-supplied object. An immutable read-only receipt view may be exported through a narrow owner inspection function, but flow handlers must obtain it directly for the exact handle on every admission. Node configuration/RPC input must never accept or supply trust fields. Copying a returned view cannot authorize another handle.

Issue a receipt only after this module's successful construction, existing tuning, supported profile inspection and file identity capture. Explicitly construct with the already-supported `allowExtension:false` option. Preserve current tuning/durability values; no undocumented SQLite flags or `trusted_schema`/journal changes without a separate compatibility review. Close a newly owned handle if initialization throws before publication; never leave a failed candidate in the global state.

Bind the private record to:

- the exact `DatabaseSync` object and owner state object;
- the currently published global state identity and `ledgerState.db` identity;
- a canonical main-file path and device/inode identity captured for a file-backed handle;
- a named, versioned supported initialization/schema profile, including the actual configured SQLite tuning;
- its live initializer lifetime, revoked before close/reset.

Inspection must deny when the global state object was replaced, the current handle differs, the handle was directly closed, the path no longer identifies the same file, or the supported profile no longer holds. It must not throw raw filesystem/SQLite details into RPC replies. Preserve the existing idempotent `openMessageLedger` behavior when a handle already exists, but never rebind its receipt to a different requested path or bless a foreign handle. Reload tests must prove that a module with no private construction record denies an inherited global handle; they must not imply that a JavaScript global is tamper-proof.

`:memory:` remains supported by internal ledger functions/tests. It gets no file-backed flow writer receipt and continues to be denied by flow data handlers without creating the default file. Revocation occurs in both `closeMessageLedger()` and `resetMessageLedgerForTest()`. Receipt state must be bounded by live owned handles, with no growing historical handle cache.

### Supported persisted schema

The current authoritative schema is `outbox` with its nine declared columns and three indexes: `idx_outbox_unsynced`, `idx_outbox_client_id`, and `idx_outbox_delivery_account`. The last index legitimately uses `json_extract(payload, '$.channel')` and `json_extract(payload, '$.accountId')`. `sqlite_sequence` is an expected AUTOINCREMENT internal object. This compatibility must be exercised against the actual engine; rejecting every expression index would break the current ledger.

Extract the canonical initialization SQL and named profile into the new `message-ledger-profile.ts` only as needed to keep ownership coherent. The helper may inspect/compare schema; it must not mint receipts or accept a caller trust override. Derive expected SQLite catalog facts from canonical initializer-owned SQL or explicit reviewed constants. Check required column/default/key semantics and index definitions, including expression definitions; `CREATE IF NOT EXISTS`, matching object names or `schema_version` alone do not prove compatibility. Reject unknown triggers, views, virtual tables, attached databases and temp schema objects. Avoid permissive SQL normalization that discards meaningful literals or expressions.

The initial supported profile is the canonical outbox schema plus its required indexes and engine-created internal objects. A compatible older outbox missing the current delivery index may qualify after the existing initializer creates that index; preserve rows and prove that upgrade with a fixture. A same-name incompatible table/index, additional user tables/indexes or unexpected temp objects does not qualify. Do not drop/recreate objects, rewrite persisted rows or silently migrate unknown schemas to obtain a receipt. Unknown profiles can retain the existing raw ledger API behavior where initialization succeeds, but shared flow writes remain denied. An inventory-backed additional profile or migration requires a separately admitted amendment; mixed historical `messages` databases are not silently declared compatible.

Recheck the supported profile before borrowed writes, in addition to the existing connection anomaly checks. Do not treat the existing function/module fingerprint comparison as callback identity attestation: in-process raw-handle consumers can register functions or replace methods. Receipt evidence establishes constructor history only under trusted-process conditions.

### Flow admission and compatibility

`data-nodes.ts::resolveDb()` currently rejects `shared && !readOnly` unconditionally. Replace only that denial with direct inspection of the initializer-owned record, then require existing exact-ledger admission, matching canonical file identity, companion checks and `assertConnectionPolicy` before returning the borrowed writer. A receipt is necessary, not a replacement for filesystem or connection admission. Do not insert the borrowed handle into the extension's owned-handle map or close it on success/failure.

The shared ledger's actual main path can differ from the environment/default path. Preserve that mapping to one exact operator-admitted resource. An explicitly supplied sibling path must remain denied; no receipt broadens stateDir/ledgerPath authority. Retain all 09-04 main/sidecar checks and the trusted-directory-writer assumption.

`handleDbQuery()` also rejects borrowed consume before opening a reader. Replace this with shared-writer admission before reading when consume is requested, including a zero-match query, and revalidate the writer at the existing marking seam. Reads still use a fresh `DatabaseSync(..., {readOnly:true, allowExtension:false})`, close it in `finally`, and never borrow the writer for SELECT. Marking remains an explicit separate operation with validated identifiers and bound IDs; no new atomic-select-and-mark or cross-process claim is introduced.

Preserve the existing handler method names and response envelopes, one prepared statement checked via full `sourceSQL`, bound values, SELECT/WITH reader restriction and CRUD/CTE writer restriction. Unknown provenance remains a bounded policy error with no path/SQL payload disclosure. Receipt failures must not detach databases, reset PRAGMAs, unregister callbacks, close someone else's handle or repair files.

### Trust and release boundary

The plugin runtime exposes `messageLedger.getDb`, and the SDK exports `getMessageLedgerDb`. Those callers already possess raw database authority. This slice does not constrain a hostile same-process plugin, a compromised Node/SQLite runtime or concurrent same-UID filesystem mutation. A private construction receipt is not an OS capability boundary and cannot prove that an arbitrary function callback is safe.

Release remains gated on exact candidate/image, Node/SQLite/VFS identity, trusted same-process plugins and filesystem writers, reviewed persisted schema/data provenance and controlled engine temporary storage. Current `temp_store=MEMORY` is a recorded connection setting; it does not prove that all SQLite I/O remains in memory or inside stateDir. Clean restart alone does not clean a poisoned persisted database. If those conditions cannot be established, maintain denial or supply an independently implemented broker/process isolation boundary; do not offer an `allowUnsafe` or operator-checkbox bypass.
