3. Explicit createJobRequest/revokeJobRequest revision changes clear the current head manifest atomically with existing domain mutation/enqueue semantics. Also reset it on the existing bindSourceJobRequest branch that changes sourceHash and creates a new revision; leaving an old manifest attached to a new revision is a defect. This nullable-head design deliberately does not retain a historical whole-manifest record after reset; do not claim a complete forensic manifest archive. Record that limitation in a TODO/proposal rather than adding another table or row kind in this slice.

4. Existing non-manifest callers remain compatible only on unbound heads. Once a head has manifest_hash, effect admission/commit APIs require the matching manifest assertion; an omitted option cannot bypass it. The existing generic withJobRequest remains a trusted server transaction helper, not a capability sandbox. Brain uses a manifest-asserting wrapper/helper for every manifest-dependent effect/publication/progress boundary, including zero batches. Finance uses heads only and must remain behaviorally unchanged.

5. Canonical brain manifest commits the pipeline/chunking version, complete ordered canonical chunk payloads (or ordered hashes and counts with an unambiguous encoding), and an explicit embedded/disabled/empty mode. Embedded mode includes the actual resolved endpoint, model, normalization and dimensions. Hashes/counts are persisted; source text, keys, authorization headers and vectors are not added to the head. Existing3000/300 chunk policy,64-input batches, at-most1024-batch limit and1536 dimensions remain. Preserve the distinction between canonical chunk identity and raw fetched bytes: two sources producing identical canonical chunks under the same policy may share a manifest; no raw-byte immutability claim.

6. Preserve runJobEmbedding's existing private preparation. Add a backwards-compatible optional contract containing expectedManifestHash, expectedProvider (endpoint/model/normalization/dimensions), and a database-only domain guard. Validate and snapshot this contract; compare expectedProvider synchronously with the actual freshly prepared descriptor before the first await or SQL admission. The same existing private prepared object then supplies both the durable receipt and executeEmbeddingRequest; never resolve it again or accept a caller-supplied prepared object. Each call receives the immutable canonical batch from the complete manifest's pieces and prepares that actual payload. A configuration change between the caller's manifest construction and a later batch's preparation conflicts before admission; a change after synchronous validation cannot mutate the already pinned request. Key rotation alone is not a new persisted semantic identity. Existing private preparation already pins exact credentials/body and snapshots the text payload. No new accessor, public prepared-object API, provider choice or alternate-provider retry.

7. Choose the explicit atomic readiness invariant: no missing effect row is admitted once the current document is ready. Add the optional trusted database-only domain guard inside runJobEmbedding's owned transaction after head/manifest verification and before missing-receipt admission. It locks/validates the domain row and returns or throws a typed already-published disposition that the brain handler handles as successful canonical completion, not indeterminate provider failure. Matching received/committed replay stays available; an existing admitted row remains indeterminate and readiness cannot assert its remote request never ran. Assert expectedManifestHash again during response persistence and final publication; an admission check alone does not grant permanent authority. Existing APIs without a guard remain valid for unbound callers.

8. The brain handler rechecks ready between calls and at shared binding/publication, stops further batching on the typed completed disposition, and uses canonical stored progress. Final publication asserts the shared manifest and exact complete batch set under head/domain locks; chunks, ready state, receipt commits and progress share the existing transaction. Empty and disabled publication also bind/assert the manifest and participate in the same readiness serialization. Disabled/empty duplicates cannot supersede an already bound embedded manifest. A first accepted disabled/empty manifest remains authoritative until explicit reingest.

9. Already-ready documents can finish duplicate jobs without loading new content, making new receipts or backfilling an uncertain manifest. Received responses from already dispatched requests may be retained only under current ownership and exact receipt identity; they do not authorize another batch or overwrite a completed publication. Cancellation cannot undo a remote request already dispatched. In-flight ambiguity and retention policy remain unchanged.

API contract for admission: preserve existing positional parameters and append optional arguments. Define ExpectedEmbeddingProvider as Pick&lt;EmbeddingDescriptor, 'endpoint' | 'model' | 'normalization' | 'dimensions'&gt; and DomainGuard as (tx: CoreTx, current: BgJob) =&gt; Promise&lt;void&gt;.

Validate/snapshot supplied hashes and provider fields at runtime, reject malformed partial contracts, and preserve existing callers on unbound heads. For a manifest-bound embedding call, both expectedManifestHash and expectedProvider are required. The domain guard is trusted host policy and may throw a local BrainAlreadyPublished error; root catches that precise type as canonical successful completion. It is not a new foundation error code or an error-message comparison.

bindJobManifest holds the current head lock and invokes the source/domain guard before binding, so ready observed during loading exits without a new binding or publication. If the guard continues, null plus prior effects rejects and only a matching/full newly bound hash can save progress. In runJobEmbedding, matching existing admitted receipt remains indeterminate before the ready guard; matching received/committed results replay, and the guard runs before inserting a missing receipt. Response persistence reasserts the manifest but does not discard a valid already-dispatched response merely because another worker published; it still requires current ownership.
